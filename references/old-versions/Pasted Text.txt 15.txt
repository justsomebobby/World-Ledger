Audited Roadmap: 10.0A-R3 Clean Completion Phase

R3A — Safe Mode Policy Correction

Why this comes first

The current source has:

* autoSafeModeEnabled: true
* safeModeFailureThreshold: 5
* safeModeCardWarningThreshold: 6
* safeModeQuarantineThreshold: 30
* safeModeDiagnosticThreshold: 180

That means long harness runs can push the script into safe mode through diagnostics/card pressure even when gameplay is not actually broken. That corrupts later testing because card generation/update behavior may be suppressed while we are trying to test card generation/update.

Exact fix

Replace current “auto hard safe mode” behavior with two stages:

Soft pressure mode

* Can defer expensive optional work.
* Does not flip features.safeMode = true.
* Does not set generated card creation to zero by default.
* Records pressure only.

Hard safe mode

* Only activates after real runtime failures, repeated card API failures, corruption risk, or explicit user/manual setting.
* Must explain why through /safemode.
* Must not silently disable the core memory engine during normal long play.

Owners touched

* SafeModeController
* FeatureDefaults
* CommandRenderer for /safemode
* Acceptance rows

Must not touch

* Parser
* Reducers
* XP
* Cards except deferral policy

Required proof

* Long normal story does not hard-safe-mode.
* Repeated fake API failure does trigger hard safe mode.
* Soft pressure can exist without disabling card creation.
* /safemode explains exact pressure source.

R3D — Effort Reward Resolver / XP Calibration

Why this is a blocker

The current source can parse explicit XP and has thresholds, lanes, and domain XP. It also has anti-farm budgets. But the story tests show that organic effort is not producing enough character, ability, or domain XP. The roadmap already expected XP budgets to include repetition decay, risk/contribution multipliers, and hard fights rewarding more, while combat rewards should be risk-based.  

The fix is not lowering thresholds. The fix is awarding bounded XP for validated effort.

Exact fix

Add EffortRewardResolver, or fold that name into ProgressionSystem + XPBudgetSystem if we want fewer system names.

It should convert validated actions into small rewards:

* training
* sparring
* real combat participation
* ability use
* summon-command use
* study/research
* crafting/labor
* exploration/discovery
* quest progress
* social victory
* domain-project milestone

Suggested scale:

* minor practice: 1–2 XP
* meaningful training/use: 3–5 XP
* risky fight contribution: 5–12 XP
* major discovery/project milestone: 10–25 XP
* repeated farming decays sharply

Owners touched

* EventScanner for effort observations
* CanonValidator for effort eligibility
* XPBudgetSystem for anti-farm/risk/contribution
* ProgressionFormulaSystem for XP application
* CombatRewardResolver for fight contribution

Must not do

Do not let parser directly add XP. Do not let commands/cards/context grant XP.

Required proof

* A 50-turn training/combat/research mini-story produces at least one character level or very visible progress.
* Repeating the same low-risk action decays.
* Third-party XP does not become player XP.
* No “+999 XP” from debug/card/context text.
* Domain XP and ability XP grow from relevant effort.

R3E — Ability / Skill / Passive / Style Lifecycle

Why this needs refinement

The current code already supports ability, skill, talent, passive, domain, and category transfers. It also has transfer logic where skills need success/training evidence and passives are weak unless supported.  

So we should not rebuild it. The missing piece is a clearer lifecycle and better preservation of style/weapon evidence.

Exact fix

Formalize lifecycle:

raw attempt → candidate evidence → progression domain XP → practiced ability/style → stable ability → skill/passive/talent only through evidence or player guidance

Rules:

* Messy candidates are acceptable if they never promote.
* Weapon/style evidence should persist even before becoming a skill.
* Skills/passives require repeated use, training, or explicit player/player-like guidance.
* Named styles and weapon identities should be preserved as style evidence.

Owners touched

* AbilityGrowthSystem
* AbilityLifecycleSystem
* AbilityDevelopmentMatrix
* AbilityCostSystem
* ProgressionDomainSystem

Must not do

Do not turn every weapon mention into a skill. Do not auto-promote passives.

Required proof

* Slime Control develops as ability/domain evidence.
* Manual Labor develops as domain/skill evidence after repeated labor.
* Mana Surgery develops after actual practice/research.
* Saber/buckler/spear/shield/brawler/Persuader-style evidence persists.
* Junk candidates can exist but do not promote.

R3F — Power Plausibility / Overreach Gate

Why this is separate from XP

AinurLindalë’s issue is not that the script made the player level too much. It is that the story permits impossible early authority: undead armies, elite domination, huge magic, no cost, no training.

The script must respond to unsupported scale claims as attempts, not stable truth.

Exact fix

Add PowerPlausibilitySystem or OverreachGate.

It classifies claims as:

* supported success
* partial success
* unstable attempt
* overreach
* ritual-scale claim
* denied as durable canon

Evidence required for high-scale claims:

* prior ability/domain level
* ritual setup
* mentor/training
* time investment
* material/corpse availability
* mana/EP/HP cost
* artifact/tool
* divine/lore permission
* risk/failure consequence

Owners touched

* CanonValidator
* AbilityGrowthSystem
* SummonSystem
* ControlledEntitySystem
* CombatThreatSystem
* MatchupSystem
* CombatOutcomeSystem
* ContextBudgeter

Must not do

Do not rewrite story text. Do not force the AI to undo prose. Just refuse to persist unsupported impossible claims as stable state.

Required proof

* “You raise 30 undead soldiers at the start” → overreach; no army/30 summons/control records.
* “You attempt to raise one corpse without training” → unstable candidate/failure/risk.
* “After weeks of necromancy study and ritual setup, you raise one skeleton” → bounded summon/ability evidence.
* “You beat an elite knight with no training” → no stable dominance; threat/matchup remains dangerous.

R3G — Summon / Familiar / Follower / Group XP Contribution

Why this needs its own chunk

Summoner playstyles must work. A magical summon/familiar is effectively the player’s ability expression. Followers are not.

Exact fix

Add contribution rules:

Summon / magical familiar

* action under player command grants player contribution XP.
* bounded by threat, risk, control cost, ability level, anti-farm.

Follower / party

* tracks presence and aid.
* XP only for player participation, command, support, or shared risk.
* no XP just for being nearby.

Group / army

* tracks force presence and outcomes.
* no full player XP from passive group victory.

Pet / trap

* usually no full XP unless actively trained/commanded/placed/triggered.

Magically bound servant

* can count like summon if magical control is established.

Owners touched

* SummonSystem
* ControlledEntitySystem
* PartyFollowerSystem
* CombatRewardResolver
* XPBudgetSystem
* ProgressionFormulaSystem

Required proof

* Penpen under player command grants bounded player contribution XP.
* Mira independently kills enemy while player does nothing → little/no player XP.
* Player commands a party tactic and participates → partial XP.
* Passive trap with no player involvement → minimal/no XP.
