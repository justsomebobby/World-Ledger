AIDRPG Build Chunk 2 — File and Module Layout Plan

0. Document status

Document name: AIDRPG Build Chunk 2 — File and Module Layout Plan
Build target: AIDRPG Core MVP v0.1
Purpose: Define the exact script organization, section order, module boundaries, call rules, and append-safe layout before any final script code is generated.
Status: Practical build document.
Follows: Build Chunk 1 — Implementation Start Packet.
This document does not contain final script code.

This chunk exists because previous versions became difficult to maintain when fixes were layered into scattered patches, wrappers, late repair systems, and large tangled code blocks.

Core MVP v0.1 must be organized so future build chunks can add systems without breaking the foundation.

⸻

1. Purpose of Build Chunk 2

Build Chunk 2 locks the internal layout of the future script.

It answers:

* what sections the script should contain
* what order those sections should appear in
* what each module owns
* what each module must not own
* which modules may call each other
* which modules must stay read-only
* where future systems will attach later
* how to avoid patch-pile growth
* how to keep the file buildable in single-message chunks

This chunk still does not write the final script.

It prepares the code layout so script generation can start safely later.

⸻

2. Core layout doctrine

The first script must be structured as one clear engine, not a patch pile.

Doctrine:

One root namespace.
One state root.
One runtime contract.
One command router.
One audit layer.
One ledger.
One owner module per truth type.
No direct parser writes.
No card-to-canon path.
No context writes.
No generated cards in MVP.

The script may physically exist as one AI Dungeon script file, but internally it must behave like modules.

⸻

3. Single-file reality

AI Dungeon scripts are often edited as one large script body.

Therefore, the build should use a single-file modular layout.

That means:

* sections are clearly labeled
* module objects/functions are grouped together
* future chunks append or fill designated sections
* no random code is inserted between unrelated modules
* section order stays stable
* every future chunk declares touched sections

Do not create a scattered script where functions are pasted wherever convenient.

⸻

17 CONTEXT BUILDER LITE SHELL
18 CARD SYNC LITE SHELL
19 CLEANUP MANAGER LITE SHELL
20 HOOK ENTRY POINTS
21 RESERVED FUTURE APPENDICES / DO NOT ACTIVATE

This order is intentional.

Foundational utilities and state come before runtime.

Runtime comes before commands.

Commands come before advanced parsing.

Parsing/validation/reducers are shells at first.

Context/Card/Cleanup shells come after the state and audit systems they depend on.

Hook entry points come last.

30. Append-safe coding policy

Future build chunks should be append-safe.

Each coding chunk must declare:

Touched sections:
New functions added:
Existing functions modified:
Why modification is required:
Tests affected:
Deferred systems still disabled:
Rollback note:

30.1 No silent rewrites

Do not rewrite the full script unless the build explicitly calls for a consolidation version.

30.2 No hidden patches

Do not add surprise modules like:

FinalFixSystem
EmergencyPatchSystem
RandomRepairLayer
PolishEverythingSystem

Every fix belongs to an owner module.

30.3 No ambiguous insertion instructions

Avoid instructions like:

Find the old function and replace part of it.

Prefer:

In Section 05 StateManager, replace function StateManager.ensureDefaults with this full function.

or:

Append this function at the end of Section 08 OperationLedger.

31. Line budget policy

The final code should remain manageable.

31.1 Per production chunk budget

Recommended:

Target max per coding chunk: 700 lines
Absolute max per coding chunk: 800 lines

If a coding chunk would exceed the limit, split it.

31.2 Per section caution

If any section becomes too large, future chunks should consider:

* sub-section labels
* helper extraction
* shell now, expansion later
* separate later build chunk

31.3 No giant all-at-once script

Do not attempt to generate the entire final AIDRPG script in one response.

The first code version should be foundation only.

34. Initial implementation sequence after this layout

Once this layout is accepted, actual code should be built in this order:

1. Header / constants / feature defaults
2. Utility helpers
3. State schema defaults
4. StateManager init/repair
5. AuditLogger basic caps
6. Runtime hook metadata/fail-soft
7. OperationLedger shell
8. CommandRouter + command renderers
9. ReleaseCheckLite
10. Hook entry points
11. Inert scanner/proposal/validator/reducer/context/card/cleanup shells
12. Run first tests

Do not code advanced parser/reducer systems before the foundation tests pass.

35. Build Chunk 2 acceptance tests

These are planning/layout acceptance tests, not runtime script tests yet.

BC2-001 — Section order exists

Expected:

* final code plan has sections 00–21 in the required order

Fail if:

* modules are unordered or scattered

BC2-002 — Each module has one owner role

Expected:

* StateManager owns state init/repair
* Runtime owns hook metadata
* CommandRouter owns commands
* AuditLogger owns audits
* OperationLedger owns dedupe

Fail if:

* multiple modules own same core truth without boundary

BC2-003 — Forbidden call paths listed

Expected:

* parser cannot call reducers directly
* context cannot call reducers
* cards cannot feed canon
* commands cannot mutate gameplay in MVP

Fail if:

* forbidden paths are unspecified

BC2-004 — Deferred systems reserved but inactive

Expected:

* economy/crafting/investigation/domain/absorption/generated cards are reserved only

Fail if:

* layout implies they are active in v0.1

BC2-005 — Append-safe policy defined

Expected:

* future chunks must declare touched sections and modified functions

Fail if:

* future edits can be pasted randomly

BC2-006 — Line budget defined

Expected:

* coding chunks target 700 lines, absolute 800 lines

Fail if:

* no production size control exists

BC2-007 — Hook entry points last

Expected:

* platform-facing hooks appear after all internal modules

* hook logic appears before dependencies or contains direct state mutation

BC2-008 — Shell modules are honest

Expected:

* parser/validator/reducer/context/card shells do not claim full automation yet

38. Final Build Chunk 2 doctrine

AIDRPG must be built as a controlled engine, not as a growing pile of fixes.

The final rule is:

Stable section order.
One owner per truth type.
No forbidden call paths.
No hidden patch systems.
No active deferred systems.
