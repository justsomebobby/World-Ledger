AIDRPG Build Chunk 4 — Command Output Format Lock

0. Document status

Document name: AIDRPG Build Chunk 4 — Command Output Format Lock
Build target: AIDRPG Core MVP v0.1
Purpose: Lock the exact command output formats for MVP commands before command rendering code is generated.
Status: Practical build document.
Follows: Build Chunk 3 — State Schema Lock.
This document does not contain final script code.

This chunk exists because commands are one of the main ways the player will inspect whether the system is working.

Commands must be:

* readable
* honest
* consistent
* non-mutating
* safe from parser feedback
* clear about disabled systems
* useful for testing
* useful for debugging

Command output must not become gameplay truth.

⸻

1. Command output doctrine

The doctrine is:

Commands inspect.
Commands explain.
Commands do not play the game.
Commands do not mutate gameplay state.
Command output is non-canon.

A command may display:

* inventory items
* quest rewards
* ability names
* actor names
* card warnings
* migration warnings
* debug reasons

But that displayed text must not create or alter state.

Example:

/inventory displays Rusty Dagger.

This must not add another Rusty Dagger.

Example:

/quests displays Reward: 15 gold promised.

This must not pay 15 gold.

Example:

/abilities displays Shadow Step — candidate.

This must not make Shadow Step stable.

⸻

2. Required command suppression rule

Every command output must set or preserve:

runtime.commandActive = true
runtime.suppressEventScanForCommandOutput = true
runtime.lastCommandName = commandName
runtime.lastCommandHash = hash(commandOutput)
runtime.lastCommandTurn = runtime.currentTurn

The Output hook must recognize command output and suppress event scanning.

If command output is later passed through Output hook, it must be ignored as story.

⸻

3. Global command format rules

All command outputs should follow this general style:

[AIDRPG] Command Name
Status: <short status>
<section heading>
- <line>
- <line>
Notes:
- <line>

3.1 Required prefix

Every command output should begin with:

[AIDRPG]

This helps identify command output for suppression.

3.2 Required non-canon reminder for diagnostics

Diagnostic commands should include a compact note:

Command output is non-canon and does not change story state.

Normal player-facing commands do not need to repeat this every time unless helpful.

3.3 No raw giant dumps

Commands must not dump full raw state by default.

Allowed:

* concise summary
* counts
* important records
* warnings
* recent audit entries

Forbidden by default:

* full state.aidrpg JSON
* huge arrays
* every audit line
* every operation key
* every old log
* every card body

3.4 Empty-state output

Every command must handle empty state gracefully.

Example:

No active quests.

not:

undefined
null
[object Object]

3.5 Unknown/malformed state output

If a bucket is missing or malformed, commands should say:

Warning: <bucket> data was missing or repaired. Run /stateaudit for details.

Commands should not crash.

⸻

7. Alias command output rules

Old aliases should route safely.

If an alias maps to an active command, output may show the active command name and alias note.

Example:

[AIDRPG] Quest Log
Alias: /questlog -> /quests
Status: Active

If an alias maps to a disabled system, output the disabled command format.

8. /help format

8.1 Purpose

Show what the current build can do and what is disabled.

8.2 Required format

[AIDRPG] Help
Status: Core MVP v0.1 Foundation
Active Player Commands:
- /sheet — show player identity, level, stats, and build summary
- /status — show HP, MP, EP, injuries, conditions, fatigue
- /inventory — show equipped, owned, nearby, and unavailable items
- /abilities — show stable, unstable, candidate, passive, and sealed abilities
- /quests — show quest states and reward status
- /actors — show important actors, companions, presence, and social notes
- /location — show current location, scene, hazards, exits, and visible key items
- /time — show current time text, last time advance, and deadlines
Diagnostic Commands:
- /version — show build and feature flags
- /debuglast — show last runtime/proposal/validation summary
- /cardaudit — show Story Card sync status
- /contextaudit — show context packet status
- /stateaudit — show schema and integrity status
- /ledger — show duplicate-prevention ledger summary
- /dirty — show pending mirror/context update targets
- /migration — show migration status
- /quarantine — show unsafe legacy data held for review
- /releasecheck — run readiness checks
- /startupaudit — show startup import and setup-lock status
Disabled in MVP:
- generated cards
- economy, shop, buying, selling
- crafting and materials projects
- investigation cases/evidence
- reputation and faction automation
- domain/labor systems
- absorption/evolution mechanics
- advanced combat, warfare, and multi-protagonist systems
- manual mutation commands
Safety Notes:
- Commands inspect only.
- Command output is non-canon.
- Story Cards mirror state only.
- Context is read-only.
- Candidate abilities are not stable abilities.
- Promised rewards are not paid rewards.
- Visible items are not inventory until acquired.

8.3 Required honesty

/help must not claim disabled systems are active.

If a system is shell-only, say shell-only.

31. Formatting edge cases

31.1 Missing bucket

If a command needs a missing bucket:

Warning: <bucket> data was missing or unavailable. StateManager should repair this. Run /stateaudit.

31.2 Empty bucket

Say:

none

or:

No active records.

Do not show undefined/null.

31.3 Too many records

Say:

Showing <shown> of <total>. Lower-priority entries omitted for command length.

31.4 Malformed record

Say:

Warning: one record could not be displayed safely and was omitted. Run /stateaudit.

Do not crash.

32. Command renderer ownership

Command renderers may read state and format output.

They may not:

* call reducers
* call EventScanner
* call ProposalBuilder
* call CanonValidator to commit anything
* call CardSync live writes
* call cleanup destructive actions
* resolve quarantine
* enable features

The only acceptable mutation from a command path is diagnostic metadata such as command suppression and optional audit that the command ran.

⸻

33. ReleaseCheck requirements for command formats

/releasecheck must verify command safety.

It must fail if:

* command output suppression missing
* commands can mutate gameplay state in MVP
* /help claims disabled systems are active
* /releasecheck is missing
* /version is missing build stage
* /inventory cannot separate visible/owned items
* /abilities cannot separate candidate/stable abilities
* /quests cannot separate promised/paid rewards
* disabled commands activate deferred systems

It may warn if:

* command output is too long
* aliases are incomplete
* diagnostic commands are shell-only
* command cap behavior is not fully implemented

37. Final Build Chunk 4 doctrine

Commands are the player’s window into the system.

If commands lie, the player cannot trust the script.

If commands mutate state, the script becomes unsafe.

If command output is parsed as story, old bugs return.

Final rule:

Commands must be honest.
Commands must be readable.
Commands must be non-canon.
Commands must not mutate gameplay.
Commands must clearly separate active, unavailable, promised, candidate, visible, and confirmed states.

With command formats locked, the next safe step is to plan StateManager.
