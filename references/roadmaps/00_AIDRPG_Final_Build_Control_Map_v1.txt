AIDRPG Final Build Control Map v1

0. Document status

Document name: AIDRPG Final Build Control Map v1
Purpose: Stabilize the final build process by mapping old tested failures, old patch intentions, and necessary new design decisions into one core-integrated construction plan.
Status: Active control document.
Applies before: Build Chunk 10 and any future script code.
This document does not contain final script code.

This document exists because AIDRPG has already been built and patched multiple times. The old work is not discarded. The old work is evidence.

The goal is not to make another slightly cleaner patch pile.

The goal is to turn every important old failure and every useful old fix intention into:

core owner module
state field
parser/proposal/validator/reducer boundary
audit surface
command surface
regression test
releasecheck gate

AIDRPG must not restart from the same old bugs.

⸻

1. Current project goal

The current goal is:

Build one final core-integrated AIDRPG script architecture that uses old tested failures and new design decisions to prevent the known patch-loop failure classes before implementation begins.

This means:

* old reports are treated as requirements evidence
* old patches are not pasted blindly
* old patch intentions are salvaged
* brittle old implementation behavior is rewritten into core architecture
* new ideas are allowed when they solve a known gap
* every new idea must have an owner, rule, test, and release gate
* no known failure category is allowed to remain vague

⸻

2. What this document is not

This document is not:

* a new 34-chunk restart
* a replacement for the 32/33 design chunks
* a replacement for Gap Chunks A–G
* a replacement for Build Chunks 1–9
* a script code file
* a vague roadmap
* another patch note

This document is the control map that explains how existing work and new decisions merge into the final build.

4. Final authority doctrine

The final build follows this doctrine:

Old fixes are evidence.
Old patches are not automatically architecture.
New ideas are allowed only when they close a known gap.
Every protection must be owned.
Every owned protection must be testable.
Every testable protection must have a release gate.

If an old system solved a real problem but caused brittle behavior, the final build keeps the rule and discards the brittle method.

If a new design idea is added, it must answer:

What old failure or missing planning detail does this solve?
Why does it belong in the core instead of being a patch?
Which module owns it?
What test proves it works?
What releasecheck gate blocks the build if it is missing?

6. Final build core pipeline

The final build must use this pipeline:

Input Hook
  -> command route OR player intent only
Context Hook
  -> read-only context reminders only
Output Hook
  -> EventScannerLite ParserHit
  -> ProposalBuilder EventProposal
  -> CanonValidator eligibility decision
  -> ReducerRegistry owner route
  -> OwnerReducer state mutation
  -> OperationLedger dedupe key
  -> DirtyQueue mirror/context target
  -> AuditLogger explanation
  -> ReleaseCheck gate coverage

Forbidden paths:

ParserHit -> direct inventory change
ParserHit -> direct ability change
ParserHit -> direct quest reward payment
Context text -> gameplay mutation
Story Card text -> gameplay mutation
Command output -> gameplay mutation
Debug/audit/help text -> gameplay mutation
Old card prose -> canon import

⸻

7. Core non-canon doctrine

The final root rule is:

Mentioned is not confirmed.
Attempted is not confirmed.
Quoted is not confirmed.
Dreamed is not confirmed.
Rumored is not confirmed.
Revoked is not retained.
Denied is not acquired.
Visible is not owned.
Promised is not paid.
Heading toward is not arrival.
Candidate is not stable.
Only validated outcome becomes canon.

This doctrine must apply across inventory, abilities, quests, rewards, time, actor presence, body/death, transformation, scene state, and cards.

8. Known Failure Register

Each known failure below must be mapped into the final core. None may be silently dropped.

⸻

F001 — Broad helper patch broke unrelated systems

Evidence pattern: Ability-name cleanup was first placed in a shared intent-cleaning helper. That helper was also used for item, destination, weapon, and target hints, so aggressive phrase stripping risked breaking unrelated systems.

Old patch intent: Strip suffixes from ability names such as:

Ember Ward to protect allies
Frost Step by moving
Stoneguard until my stance holds

Old patch risk: Shared cleanup changed behavior outside ability naming.

Final core rule: Shared intent cleanup must stay conservative. Aggressive cleanup must live in the owner-specific sanitizer.

Final owner modules:

AbilityNameSanitizer
ItemNameSanitizer
PlaceNameSanitizer
ActorNameSanitizer
CardNameSanitizer
IntentParser conservative shared helpers

Required tests:

I train Ember Ward to protect allies from heat -> ability name Ember Ward
I practice Frost Step by moving across slick stones -> ability name Frost Step
I drill Stoneguard until my stance holds under impact -> ability name Stoneguard
I travel to the smithy -> no smithy ability
I inspect the old wooden door -> no door ability
I use the iron key on the cellar door -> no iron key/cellar door ability

ReleaseCheck gate: Fail if shared sanitizer contains ability-specific aggressive stripping that affects travel/item/place/target parsing.

You pretend to use Azure Dragon Step.

ReleaseCheck gate: Fail if output-only ability names can become stable without validated source.
