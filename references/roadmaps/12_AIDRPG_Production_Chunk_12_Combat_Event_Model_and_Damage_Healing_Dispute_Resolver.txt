# AIDRPG Production Chunk 12 — Combat Event Model and Damage/Healing Dispute Resolver

## 0. Document status

**Document name:** AIDRPG Production Chunk 12 — Combat Event Model and Damage/Healing Dispute Resolver  
**Production sequence:** 12 of 25 remaining production chunks  
**Build target:** WorldLedger V0.17.11 stats/invariants accepted build / AIDRPG Core MVP expansion path  
**Purpose:** Add a conservative combat event model, attack/result separation, damage/healing dispute resolution, duplicate-safe combat operation keys, body/resource integration, combat display support, and combat regression gates without activating full advanced combat automation.  
**Status:** Core systems production chunk.  
**Follows:** Production Chunk 11 — Stats, Derived Values, Conditions, and Invariant Checker.  
**This document does not contain final script code.**

Production Chunk 12 exists because combat is where AI Dungeon scripts can break the fastest.

Old and rough builds often risked:

```text
player input attack automatically damaging enemies
model narration applying damage twice
miss/block/graze text still applying full damage
healing from item names without validated use
healing from /status or context text
armor/equipment bonuses applying without formulas
ability names becoming damage rules
NPC death from rumor/threat/metaphor
player death from dramatic wording
combat victory granting XP automatically
duplicate combat output repeating damage, healing, loot, XP, and death
```

This chunk creates combat as a structured event system. It does **not** build the full advanced combat engine. It does **not** attempt full tactical AI, encounter balancing, party combat, warfare, absorption, or creature-specific advanced logic. It creates the safe baseline needed before those systems can exist.

---

# 1. Chunk doctrine

```text
An attack attempt is not a hit.
A hit is not damage until validated.
Damage is not death until the death boundary validates it.
Healing is not recovery unless a healing/recovery event validates it.
A miss is not damage.
A block is not full damage.
A graze is not full damage unless validated.
Input intent cannot force outcome.
Output contradiction beats input prediction.
Duplicate output cannot repeat damage or healing.
Combat victory is not XP unless exact XP is separately validated.
```

Combat truth must be proposal-based, outcome-aware, duplicate-safe, and integrated with Body/Stats without bypassing them.

---

# 2. Why this chunk comes now

Production Chunk 11 made stats, resources, conditions, derived values, and invariants safer.

Combat comes now because it uses:

```text
body resources
injuries
conditions
stat/derived labels
inventory/equipment records
ability status/evidence
actor presence
place/scene context
XP/progression boundaries
operation ledgers
invariant checks
```

If combat is built before these layers, it becomes a pile of special cases. This chunk makes combat an event model that can later be expanded into advanced combat, creature ecology, party/summon handling, and warfare.

# 5. Combat state model

Combat should have a bounded state area.

Recommended shape:

```text
combat: {
  active: false,
  sceneState: null,
  events: [],
  recentAttempts: [],
  recentOutcomes: [],
  disputes: [],
  warnings: [],
  notes: []
}
```

If no dedicated combat root exists, records may live in audits initially, but PC12 should prepare a stable `combat` bucket or equivalent. Combat state is not a full turn engine yet. It is an event ledger and dispute model.

# 7. Combat CanonValidator expansion

CanonValidator must enforce combat safety.

## 7.1 Accept attack attempt when

```text
safe input/output includes attack/swing/shoot/cast/use-hostile intent
target is bound enough
source is not command/context/card/audit/debug
```

Result:

```text
attack_attempt only
no damage yet unless output also confirms hit/damage
```

## 7.2 Accept miss/block/dodge when

```text
safe output directly says miss/dodge/parry/block/deflect/no effect
attacker/defender target can be bound
```

Result:

```text
combat outcome records miss/block
damage blocked/rejected unless separate accepted damage clause exists
```

## 7.3 Accept hit when

```text
safe output directly confirms hit/strike/connects/lands
not metaphor/quote/dream
not command/context/card source
```

Result:

```text
hit confirmed
no numeric damage unless damage clause validates
injury/severity may be proposed if direct physical consequence exists
```

## 7.4 Accept damage when

```text
safe output directly confirms wound, HP loss, injury, burn, bleeding, etc.
target is bound
not denied/blocked/missed/no effect
operation key not duplicate
```

## 7.5 Accept healing when

```text
safe output directly confirms HP restored, wound closes, bleeding stops, poison fades, etc.
target is bound
not failed/no effect/attempt only
operation key not duplicate
```

```text
threat/intimidation only
metaphor only

```

Examples:

```text

The goblin blocks your sword. -> block, no damage unless separate injury says otherwise
```

# 9. Damage/healing owner contract

Combat should not bypass BodyReducer.

Preferred owner contract:

```text
CombatReducer records combat event/outcome.
DamageResolver creates validated body.damage_candidate or actor.damage_candidate.
BodyReducer owns player HP, injuries, conditions, and death boundary.
ActorReducer owns actor presence/status memory; NPC body depth remains conservative unless NPC body system exists.
ProgressionReducer owns XP and must not auto-award combat XP.
InventoryReducer owns item consumption, not CombatReducer.
AbilityReducer owns ability evidence, not CombatReducer.
```

If a target owner system is not ready:

```text
record combat outcome and defer effect safely
```

Do not apply damage/healing by writing random fields.

# 10. DamageResolver behavior

DamageResolver should:

```text
read validated combat outcome
read target type
read amount/severity/body part if known
create DamageRecord
route player body effects to BodyReducer
route NPC damage conservatively to actor/status pending unless NPC body owner exists
apply no effect if miss/block/no-effect wins dispute
add operation key
mark dirty targets
```

DamageResolver should not:

```text
invent numeric damage from dramatic prose
kill target from damage unless death boundary validates
apply armor/equipment math unless rules active
apply ability damage formulas unless rules active
award XP/loot
```

# 11. HealingResolver behavior

HealingResolver should:

```text
read validated healing/recovery outcome
read target type
read resource/condition/injury target if known
create HealingRecord
route player body effects to BodyReducer
route NPC healing conservatively if owner exists
skip if failed/no effect/attempt only
add operation key
mark dirty targets
```

HealingResolver should not:

```text
heal from item name alone
consume item automatically unless InventoryReducer receives validated consume/use event
revive dead target unless revival policy active
clear all conditions broadly
heal above max
```

# 12. Dispute resolver behavior

CombatDisputeResolver should run before reducers commit combat consequences.

Priority rules:

```text
1. Command/context/card/debug source blocks effect.
2. Duplicate output blocks repeated effect.
3. Explicit miss/dodge/parry/no effect blocks damage.
4. Explicit block/armor blocks or defers damage unless damage clause says partial/graze.
5. Explicit hit permits hit outcome but not automatic numeric damage.
6. Explicit wound/injury/HP loss permits damage candidate.
7. Explicit healing success permits healing candidate.
8. Explicit healing failure blocks healing.
9. Death requires death-boundary validation.
10. Ambiguous target blocks damage/healing until resolved.
```

This makes combat robust against AI Dungeon contradictions.


```text

```
