AIDRPG Build Chunk 6 — Runtime Hook Contract Implementation Plan

0. Document status

Document name: AIDRPG Build Chunk 6 — Runtime Hook Contract Implementation Plan
Build target: AIDRPG Core MVP v0.1
Purpose: Define the exact runtime hook behavior, hook flow, valid return handling, command suppression, duplicate output protection, and fail-soft rules before runtime code is generated.
Status: Practical build document.
Follows: Build Chunk 5 — StateManager Plan.
This document does not contain final script code.

This chunk is useful because the runtime hooks are where AI Dungeon actually touches the script.

If the hooks are unsafe, every later system becomes unsafe.

If Input commits success, the player gets items or quest progress too early.

If Context mutates state, reminders become hidden gameplay writers.

If Output replays are not blocked, rewards, XP, items, time, cards, and damage duplicate.

If command output is scanned as story, commands become corrupting narration.

If fail-soft behavior is missing, a single error can crash the whole script or partially mutate state.

Build Chunk 6 turns the runtime plan into exact implementation rules.

⸻

1. Runtime doctrine

The runtime doctrine is:

Input may intend.
Context may remind.
Output may propose.
Commands may inspect.
Runtime may protect.
Runtime may not decide gameplay truth.

Runtime owns the safety of the hook surfaces.

Runtime does not own gameplay consequences.

⸻

2. Runtime responsibilities

Runtime owns:

* hook entry safety
* hook metadata
* current hook name
* current turn number
* hook depth / recursion guard
* input hash tracking
* context hash tracking
* output hash tracking
* last applied output hash
* command suppression flags
* command hash tracking
* duplicate output replay detection
* valid return shapes
* fail-soft behavior
* runtime warning/error records
* hook trace records

Runtime does not own:

* item acquisition
* reward payment
* XP gain
* ability creation
* quest activation/completion
* actor promotion
* location arrival
* Story Card canon
* Context packet truth
* parser validation decisions

⸻

Runtime belongs in:

Section 06 — Runtime Hook Contract

Runtime depends on:

Runtime must not depend on:

Hook entry points orchestrate modules later, but Runtime itself stays focused on hook safety.

5. Valid hook surfaces

The implementation must support three conceptual hook surfaces.

Input hook
Context hook
Output hook

Actual platform names may be different.

Possible AI Dungeon-style wrappers may be:

inputModifier(text)
contextModifier(text)
outputModifier(text)

or equivalent.

The internal contract remains the same even if the platform wrapper names differ.

⸻

6. Universal hook wrapper flow

Every hook should follow the same safety shell.

1. Capture original text.
2. Convert text to safe string.
3. Call StateManager.init.
4. Call Runtime.beginHook.
5. Run hook-specific logic inside try/catch.
6. Prevent forbidden mutation based on hook role.
7. Call Runtime.endHook.
8. Return valid text shape.
9. If error occurs, call Runtime.failSoft and return valid text shape.

No hook may return undefined.

No hook may leave runtime.hookDepth stuck above zero after success or fail-soft.

⸻

7. Valid return shape

7.1 Preferred internal return

All hook logic should internally normalize to:

{ text: string }

7.2 Platform adaptation

If AI Dungeon requires a plain string or another shape, the platform-facing entry point may adapt at the final boundary.

Internal logic must still use the safe return contract.

7.3 Forbidden returns

Runtime must avoid:

undefined
null
false
true
number
object without text
uncaught thrown error

7.4 Return text rule

If the script does not need to alter text, return the original safe text.

For story hooks, fail-soft should usually return original text.

For command failures, fail-soft should return a safe command error message.

9. Hook trace behavior

Every hook should create a trace record.

9.1 Start trace

At hook start:

turn
hook
textHash
startedAt
status = 'started'
notes

9.2 End trace

At hook end:

endedAt
status = 'completed' | 'failed' | 'fail_soft'
notes

9.3 Trace cap

Keep most recent 30 trace records.

Do not let hookTrace grow forever.

9.4 Trace safety

Trace is diagnostic only.

Trace does not create gameplay truth.

⸻

10. Hook depth and recursion guard

10.1 Hook depth rule

At beginHook:

runtime.hookDepth += 1

At endHook or failSoft:

runtime.hookDepth = max(0, runtime.hookDepth - 1)

10.2 Reentry rule

If hookDepth is already greater than zero before entering a new hook:

* record runtime warning
* allow safe diagnostic continuation if necessary
* block gameplay mutation
* return safe text if recursion is unsafe

10.3 Why this matters

Nested hook behavior can happen through platform quirks, commands, cards, context generation, or failed tool-like behavior.

The script must not recursively parse its own output.

⸻

11. Turn counting policy

11.1 Gameplay turn increment

A new gameplay turn begins on non-command Input hook.

Recommended:

Input hook receives non-command text -> runtime.currentTurn += 1

11.2 Commands do not advance gameplay turn

Commands should not advance gameplay time or turn consequences.

They may record command metadata.

11.3 Context and Output turn use

Context and Output use the current turn created by Input.

If Output arrives without prior Input, Runtime should still fail softly and use existing currentTurn.

Do not invent gameplay consequences due to unusual hook order.

⸻

12. Input hook implementation plan

12.1 Input hook responsibilities

Input hook owns:

* state initialization
* runtime begin/end
* command detection
* command routing
* command suppression
* non-command input hash
* pending intent shell only, if included

Input hook must not own:

* completed item pickup
* combat victory
* quest completion
* reward payment
* XP gain
* stable ability creation
* confirmed travel arrival
* Story Card updates

12.2 Input hook flow

1. originalText = safeText(text)
2. root = StateManager.init(state)
3. Runtime.beginHook(root, 'input', originalText)
4. If CommandRouter.isCommand(originalText):
   a. commandOutput = CommandRouter.route(root, originalText)
   b. Runtime.setCommandSuppression(root, commandName, commandOutput)
   c. Runtime.endHook(root, 'input', commandOutput, 'completed')
   d. return Runtime.makeReturn(commandOutput)
5. Else:
   a. Runtime.markInput(root, originalText)
   b. increment currentTurn if appropriate
   c. optionally create pending input intent shell only
   d. StateManager.markGameplayStarted(root) if first gameplay input
   e. Runtime.endHook(root, 'input', originalText, 'completed')
   f. return Runtime.makeReturn(originalText)
6. Catch errors through failSoft.

12.3 Input intent shell

Input may create a pending intent shell later, but in early v0.1 this can be inert.

If it exists, it must not become success.

Example:

Player input:

I take the crown.

Input may record:

pending intent: attempt_take_crown

Input must not add Crown to inventory.

12.4 Input command suppression

When a command is handled, Runtime must set:

commandActive = true
suppressEventScanForCommandOutput = true
lastCommandName = commandName
lastCommandHash = hash(commandOutput)
lastCommandTurn = currentTurn

This prevents command output from becoming story.

⸻

13. Context hook implementation plan

13.1 Context hook responsibilities

Context hook owns:

* state initialization
* runtime begin/end
* context hash
* read-only ContextBuilderLite call
* context audit
* valid context return

Context hook must not own:

* gameplay mutation
* proposal creation
* reducer commits
* Story Card updates
* cleanup mutation
* command routing

13.2 Context hook flow

1. originalText = safeText(text)
2. root = StateManager.init(state)
3. Runtime.beginHook(root, 'context', originalText)
4. Runtime.markContext(root, originalText)
5. packets = ContextBuilderLite.buildPackets(root) if active, read-only
6. contextText = ContextBuilderLite.serialize(packets, root) or originalText/minimal safe context
7. ContextBuilderLite.audit(root, packets, skipped)
8. Runtime.endHook(root, 'context', contextText, 'completed')
9. return Runtime.makeReturn(contextText)
10. Catch errors through failSoft.

13.3 Context no-write guard

Runtime cannot perfectly prevent every code path from mutating state, but the design must enforce:

* ContextBuilderLite does not call reducers
* ContextBuilderLite does not call CardSync writes
* ContextBuilderLite does not import card text
* ContextBuilderLite only writes context audit metadata if needed

ReleaseCheck must fail if ContextBuilderLite is capable of gameplay mutation.

13.4 Early v0.1 context behavior

If full context packets are not active yet, Context hook may return original text or minimal safe context.

It must honestly report through /contextaudit:

Context packet system shell present; gameplay mutation disabled.

⸻

14. Output hook implementation plan

14.1 Output hook responsibilities

Output hook owns:

* state initialization
* runtime begin/end
* output hash
* command output suppression check
* duplicate output replay check
* parser/proposal/validator/reducer orchestration later
* dirty targets later
* card sync dry-run/shell later
* cleanup safe shell later

Output hook must not directly own:

* parser direct mutation
* command output consequences
* Context text consequences
* Story Card text consequences
* generated card creation in MVP

14.2 Output hook flow

1. originalText = safeText(text)
2. root = StateManager.init(state)
3. Runtime.beginHook(root, 'output', originalText)
4. outputHash = Runtime.markOutput(root, originalText)
5. If Runtime.shouldSuppressEventScan(root, originalText):
   a. audit suppression
   b. Runtime.clearCommandSuppression(root) if safe
   c. Runtime.endHook(root, 'output', originalText, 'completed')
   d. return Runtime.makeReturn(originalText)
6. If Runtime.isDuplicateOutput(root, outputHash):
   a. runtime.outputReplayDetected = true
   b. audit duplicate output skip
   c. Runtime.endHook(root, 'output', originalText, 'completed')
   d. return Runtime.makeReturn(originalText)
7. If parser pipeline active:
   a. hits = EventScannerLite.scanOutput(originalText, root)
   b. proposals = ProposalBuilder.fromHits(hits, root)
   c. validationResults = CanonValidator.validateAll(proposals, root)
   d. ReducerRegistry.applyAccepted(validationResults, root)
8. If parser pipeline inactive:
   a. audit shell state if needed
9. Runtime.markOutputApplied(root, outputHash) only after safe processing decision.
10. CardSyncLite dry-run/safe shell if enabled.
11. CleanupManagerLite lightweight safe caps if enabled.
12. Runtime.endHook(root, 'output', originalText, 'completed')
13. return Runtime.makeReturn(originalText)
14. Catch errors through failSoft.

14.3 Early v0.1 output behavior

Early v0.1 may not have full parsing active.

In that case Output hook should:

* track output hash
* suppress command output
* block duplicate output reprocessing
* not create gameplay consequences
* honestly report parser shell status in /debuglast and /releasecheck

This is useful because it proves runtime safety before automation.

⸻

15. Command output suppression implementation

15.1 Suppression markers

Command output should be identifiable by:

* runtime.suppressEventScanForCommandOutput = true
* runtime.lastCommandHash
* command prefix [AIDRPG]
* last command name
* last command turn

15.2 Suppression check

Output hook should suppress scanning if:

runtime.suppressEventScanForCommandOutput = true

and any of the following are true:

hash(outputText) === runtime.lastCommandHash
outputText begins with [AIDRPG]
runtime.commandActive is true and output appears immediately after command

15.3 Suppression result

If suppressed:

* do not scan as story
* do not create proposals
* do not run reducers
* do not update gameplay state
* record suppression audit
* clear command suppression if safe
* return original output

15.4 Suppression must protect command content

Examples:

/inventory output showing:

Rusty Dagger

must not add another dagger.

/quests output showing:

Reward: 15 gold promised

must not pay gold.

/abilities output showing:

Shadow Step — candidate

must not stabilize Shadow Step.

⸻

16. Duplicate output replay implementation

16.1 Hash-level replay

Output hook must compare:

outputHash
runtime.lastAppliedOutputHash

If equal:

* skip consequence processing
* audit replay skip
* return safe text

16.2 lastOutputHash versus lastAppliedOutputHash

lastOutputHash records the most recent output observed.

lastAppliedOutputHash records the most recent output that was allowed through consequence processing.

These are different for safety.

16.3 When to mark output applied

Mark output as applied only after:

* command suppression check passes or skips appropriately
* duplicate check passes
* parser/proposal/validator/reducer stage completes safely or intentionally shell-skips

Do not mark output applied before a crash-prone step unless fail-soft policy accounts for it.

16.4 OperationLedger remains second layer

Hash replay only catches exact repeats.

OperationLedger later catches semantic duplicates.

Example:

Old Bren pays you 15 gold.
Old Bren hands you the promised fifteen gold.

These may have different hashes, but same reward key.

⸻

17. Fail-soft implementation

17.1 Fail-soft purpose

Fail-soft prevents one bug from crashing the script or corrupting state.

17.2 Fail-soft flow

1. Catch error.
2. Convert error to safe message.
3. Record runtime error.
4. Increment failSoftCount.
5. Mark hook trace fail_soft.
6. Reset hookDepth safely.
7. Preserve original text for story hooks.
8. Return command failure text for command hooks.
9. Do not continue optional mutation after error.

17.3 Story hook fail-soft return

For Input/Context/Output story text:

return original text

or safe context fallback for Context if required.

17.4 Command fail-soft return

For commands:

[AIDRPG] Command Error
Status: Failed Safely
The command failed safely. Gameplay state was not intentionally changed.
Run /debuglast or /stateaudit for details.

17.5 Fail-soft must not

* erase state
* reset player
* clear inventory
* enable generated cards
* retry Story Card writes endlessly
* continue reducer commits after critical error
* return undefined

⸻

18. Partial commit protection boundary

Runtime itself should not perform gameplay commits.

But it must define when processing stops after an error.

18.1 Early v0.1

Since reducers may be inactive or shell-only, partial gameplay commits should not happen yet.

18.2 Later reducer era

Once reducers commit proposals, the safe unit is:

validated proposal -> owner reducer apply -> operation key -> dirty target -> audit

If an error happens mid-processing:

* Runtime fail-soft stops further optional processing
* AuditLogger records partial commit risk
* ReleaseCheck may warn/fail if partial commit protection is incomplete

18.3 Runtime must not pretend rollback exists

If rollback is not implemented, do not claim rollback.

Say:

Partial commit protection is limited to proposal-level commit ordering and fail-soft interruption.

⸻

19. Runtime warnings and errors

19.1 Runtime warning examples

Runtime warning: Context hook received non-string text and converted it safely.
Runtime warning: Duplicate output replay detected; consequence scanning skipped.
Runtime warning: Command output suppression triggered.
Runtime warning: Hook reentry detected; gameplay mutation blocked.

19.2 Runtime error examples

Runtime error: output hook failed during EventScannerLite.scanOutput.
Runtime error: command route failed while rendering /inventory.
Runtime error: StateManager.init failed; returned safe text.

19.3 Caps

Use Build Chunk 3 caps:

runtimeWarnings max 25
runtimeErrors max 20
hookTrace max 30

20. Runtime and AuditLogger relationship

Runtime may write to:

runtime.runtimeWarnings
runtime.runtimeErrors
runtime.hookTrace
audits.runtimeWarnings
audits.debugMessages

Runtime should not duplicate every message into every bucket.

Recommended:

* runtime-specific warnings/errors in runtime
* user-visible summaries in audits
* /debuglast reads both

⸻

21. Runtime and CommandRouter relationship

Input hook uses CommandRouter for slash commands.

CommandRouter returns command output text.

Runtime then marks suppression.

Recommended order:

CommandRouter.route -> commandOutput
Runtime.setCommandSuppression(commandName, commandOutput)
return commandOutput

Do not scan command output as player intent.

Do not route commands from Output hook.

⸻

22. Runtime and StateManager relationship

Every hook starts with:

root = StateManager.init(state)

If StateManager repairs state, Runtime proceeds.

If StateManager fails, Runtime fail-soft returns safe text.

Runtime assumes StateManager has ensured required runtime fields exist.

⸻

23. Runtime and ReleaseCheck relationship

ReleaseCheck must verify:

* runtime bucket exists
* hook depth field exists
* duplicate hash fields exist
* command suppression fields exist
* fail-soft count exists
* hook trace exists and capped
* runtime error arrays capped
* command output suppression rule active
* duplicate output protection active
* Context read-only guard declared

ReleaseCheck must fail if:

* command output can be scanned as story
* duplicate output can apply consequences twice
* hooks can return undefined
* generated cards can activate during runtime in MVP

⸻

24. Runtime and parser shells

Runtime may call EventScannerLite only from Output hook and only after:

* command suppression check
* duplicate output hash check
* feature/parser flag check

Runtime must not call EventScannerLite for:

* command output
* context packets
* Story Card text
* debug/audit/help text

In early v0.1, EventScannerLite may be inactive.

Runtime must be honest about that.

⸻

25. Runtime and ContextBuilderLite

Context hook may call ContextBuilderLite.

Runtime must enforce the design expectation:

ContextBuilderLite is read-only.

Early implementation may not fully enforce with snapshots, but ReleaseCheck and code boundaries must identify it.

If a future test detects Context mutated gameplay state, releasecheck fails.

⸻

26. Runtime and CardSyncLite

Runtime may orchestrate CardSyncLite from Output hook only, and only in safe/dry-run mode for early v0.1.

Runtime must not run CardSyncLite from Context hook.

Runtime must not let CardSyncLite parse cards into gameplay state.

Generated cards remain disabled.

⸻

27. Runtime and CleanupManagerLite

Runtime may call CleanupManagerLite after safe Output processing.

Early v0.1 cleanup should be limited to:

* cap audits
* cap runtime arrays
* cap dirty queue

Runtime must not call destructive cleanup that can remove important truth.

If cleanup fails, fail-soft should not crash story output.

⸻

28. Hook-specific mutation permissions

28.1 Input hook may mutate

* runtime metadata
* command suppression metadata
* startup gameplayStarted/lock flags
* audit warnings
* pending input intent shell if implemented

Input hook may not mutate gameplay outcomes.

28.2 Context hook may mutate

* runtime metadata
* context audit metadata
* context hash

Context hook may not mutate gameplay outcomes.

28.3 Output hook may mutate

Early v0.1:

* runtime metadata
* output hash
* duplicate replay audit
* command suppression clearing
* audit shell entries
* card/cleanup dry-run metadata if safe

Later:

* validated reducer commits through owner reducers only

Output hook may not directly mutate gameplay outside validated reducer path.
