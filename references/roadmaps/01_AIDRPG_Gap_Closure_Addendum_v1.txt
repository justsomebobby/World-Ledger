AIDRPG Gap Closure Addendum v1

0. Document status

Document name: AIDRPG Gap Closure Addendum v1
Purpose: Lock the missing safety plans that must exist before coding so old AIDRPG/TASIS problems do not reappear.
Status: Pre-code blocker and planning addendum.
Applies after: Script Build Roadmap v1.
Applies before: Script v0.1 coding begins.
This document does not contain final script code.

This addendum exists because the master package already defines the dream, architecture, MVP, tests, formulas, and roadmap, but the old versions show many specific repairs that must not be lost.

The old systems tried to fix:

* duplicate card creation
* wrong Story Card API assumptions
* live card writes happening too early
* polluted protected cards
* generated junk cards
* command/help dishonesty
* quoted/rumored/pretend text becoming canon
* failed ability attempts becoming real abilities
* visible items becoming owned inventory
* handoff wording being parsed incorrectly
* absent companions acting
* player identity drift
* player setup being overwritten
* quest reward duplication
* vague quest setup becoming active quest
* context mutating state
* Story Cards mutating state
* parser false positives
* over-awarded XP
* dirty queue bloat
* state migration damage
* long-run save rot
* runtime hook failures
* testing gaps

This document turns those old repair goals into exact planning requirements.

2. Core gap-closure doctrine

The old patches must not be copied blindly.

The old problems must not be forgotten.

The rule is:

Keep the tested fix intention.
Discard brittle patch behavior.
Rebuild each protection inside the new canon pipeline.

Every old fix must be classified as one of:

* Keep in MVP
* Rewrite in MVP
* Defer with mini-spec
* Discard because dangerous/redundant
* Keep as test only

No old module should be pasted directly into the new build unless the build chunk explicitly says it has been rewritten to match the new architecture.

4. Runtime and Hook Contract Spec requirement

Before coding starts, create a Runtime and Hook Contract Spec.

The script must not rely on vague hook behavior.

Must define

Input hook

* validates runtime
* initializes state
* starts turn safely
* routes commands
* suppresses command output scanning
* records player intent only
* never completes normal player actions from input alone
* returns valid { text } shape
* fail-softs on errors

Context hook

* validates runtime
* initializes state
* builds context packets
* never mutates gameplay state
* never creates cards
* never creates proposals
* returns valid { text } shape
* fail-softs on errors

Output hook

* validates runtime
* initializes state
* ignores command-output replay
* scans AI output only
* creates proposals
* validates proposals
* routes accepted proposals to reducers
* writes ledger keys
* marks dirty targets
* updates protected cards if allowed
* returns valid { text } shape
* fail-softs on errors

Must define hook state fields

currentHook
currentTurn
lastInputHash
lastOutputHash
lastAppliedOutputHash
hookTrace
commandActive
suppressEventScanForCommandOutput
runtimeWarnings

Must define fail-soft behavior

If a hook fails:

* do not erase state
* do not create partial gameplay commits
* log error in audit
* return original text if safe
* set diagnostic warning

Required tests

* hook returns valid shape
* Input does not complete actions
* Context does not mutate state
* Output duplicate replay does not double-apply
* command output suppression works
* runtime exception does not break scenario
* lastAppliedOutputHash prevents duplicate output consequences

35. Final addendum doctrine

AIDRPG must not restart from the same old bugs.

The new plan must preserve the lessons from the old versions without copying their unstable patch pile.

The final rule is:

No old bug category is considered handled until it has:
1. a named safety rule,
2. an owner module,
3. a validator rule or non-canon rule,
4. a reducer boundary,
5. an audit surface,
6. a regression test.

If a feature has no test, it is not safe.

If a parser rule has no rejection case, it is not safe.

If a card system has no duplicate policy, it is not safe.

If a command cannot explain what happened, it is not safe.

If cleanup can delete important truth, it is not safe.

If a future system does not have a mini-spec, it is not ready to code.

This addendum closes the planning gap between the high-level rebuild plan and the old tested repair history.

The next step should be:

Create Gap Chunk A — Old Fix Salvage Matrix

Only after Gap Chunks A–G are done should Script v0.1 Phase 1 begin.
