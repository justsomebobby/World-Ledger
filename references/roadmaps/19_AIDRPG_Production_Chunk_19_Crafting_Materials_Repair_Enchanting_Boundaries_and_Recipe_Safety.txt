# AIDRPG Production Chunk 19 — Crafting, Materials, Repair, Enchanting Boundaries, and Recipe Safety

## 0. Document status

**Document name:** AIDRPG Production Chunk 19 — Crafting, Materials, Repair, Enchanting Boundaries, and Recipe Safety  
**Production sequence:** 19 of 25 remaining production chunks  
**Build target:** WorldLedger V0.17.18 economy/trade accepted build / AIDRPG Core MVP expansion path  
**Purpose:** Add safe crafting, material, recipe, repair, upgrade, and enchanting boundaries without false item creation, false material consumption, unsafe enchantment powers, duplicate crafted items, or Story Card/context recipe mutation.  
**Status:** Core gameplay production chunk.  
**Follows:** Production Chunk 18 — Economy, Shops, Trade, Debt, and Service Contracts.  
**This document does not contain final script code.**

Production Chunk 19 exists because crafting is one of the fastest ways to corrupt an RPG ledger.

Old and rough builds can fail by treating every crafting phrase as a completed item, every material mention as owned, every recipe as known, every repair attempt as success, every enchantment word as a real magic power, and every repeated output as another crafted item.

This chunk makes crafting useful for AI Dungeon gameplay while keeping it strict enough to avoid false inventory changes.

The system should support:

```text
known recipes
unknown recipes
recipe hints
owned materials
visible materials
shop stock materials
custody materials
workstations
tools
crafting attempts
partial progress
failures
successes
material consumption
repair quotes
repair attempts
repair completion
upgrade boundaries
enchanting proposals
enchanting failures
enchanting success only when explicitly validated
duplicate-safe craft outputs
```

But the system must not allow:

```text
"I craft a sword" -> sword appears automatically
"I need iron" -> iron appears automatically
"The recipe says dragonfire blade" -> weapon created
"The blacksmith can repair it" -> item repaired
"The sword glows" -> permanent enchantment granted
Story Card recipe text -> live recipe/state mutation
context summary -> material/item/enchantment mutation
command output -> crafting result mutation
```

---

# 1. Chunk doctrine

```text
Recipe known is not item crafted.
Recipe hint is not recipe known.
Material mentioned is not material owned.
Visible material is not owned material.
Shop stock is not owned material.
Crafting intent is not crafting success.
Crafting attempt is not crafted output.
Repair quote is not repair completion.
Upgrade plan is not upgrade result.
Enchanting description is not magic power.
Failure can consume materials only when validated.
Success creates items only through InventoryReducer.
Every material consumed and item created must be duplicate-safe.
```

Crafting must be a transaction/effect pipeline, not a string-matching shortcut.

---

# 2. Why this chunk comes now

Production Chunk 18 locked economy, shops, trade, debt, deposits, services, and transaction safety.

Crafting comes next because it depends on:

```text
owned inventory and custody from PC05
ability status and training evidence from PC06
quest objectives and rewards from PC07
actors/trainers/blacksmiths from PC08
place/workstation/location state from PC09
progression/stat boundaries from PC10/PC11
combat/equipment consequences from PC12
form/equipment constraints from PC13
world lore and recipe authority from PC15
context/card non-canon safety from PC16
economy/service contracts from PC18
```

If crafting is added before these owner boundaries are respected, it will duplicate items and consume the wrong materials.

# 21. Crafting source and owner boundaries

Crafting must respect owner systems.

Owner boundaries:

```text
InventoryReducer owns item/material ownership, consumption, creation, condition, equipment state.
CraftingReducer owns attempts, recipes, progress, and result proposals.
EconomyReducer owns paid crafting/repair service contracts and currency payments.
QuestReducer owns crafting quest objectives.
AbilityReducer owns ability evidence from crafting-related training only.
ProgressionReducer owns XP and must not award crafting XP by default.
ContextBuilder/CardSync cannot create recipes/items/results.
```

Default split result for successful craft:

```text
craft.result.success -> CraftingReducer records success
inventory.consume_materials -> InventoryReducer removes materials if validated
inventory.create_item -> InventoryReducer adds output if validated
```

All shared operations must carry linked keys.

# 22. Recipe authority and lore boundary

Recipe data may come from gameplay or lore, but it must not bypass knowledge and ownership.

Allowed recipe sources:

```text
structured setup recipe before lock
gameplay output where player reads/learns recipe
teacher/NPC instruction if validated
world bible lore as hidden/reference recipe only
quest-given recipe if QuestReducer/Knowledge validates it
```

Rejected or blocked recipe sources:

```text
Story Card recipe text as active known recipe
context recipe summary
command output recipe list
rumor as known recipe
hidden recipe before discovery
```

Rules:

```text
Recipe existence is not player knowledge.
Player-known recipe is not material ownership.
Material ownership is not crafting success.
```

# 23. Crafting CanonValidator expansion

CanonValidator must enforce crafting safety.

## 23.1 Accept crafting intent when

```text
safe input says player tries/starts/plans to craft/repair/upgrade/enchant
recipe/output target can be bound enough
source is not command/context/card/audit/debug
```

Result:

```text
CraftingAttemptRecord intent_only or in_progress
no materials consumed
no output created
```

## 23.2 Accept crafting success when

All are true:

```text
safe output directly confirms successful creation/completion
output item target is bound
required material/tool/workstation checks pass or output provides validated override/source
not dream/quote/metaphor/planning only
not command/context/card source
operation key not duplicate
```

Result:

```text
CraftingResultRecord success
material consumption and output item handoff routed to InventoryReducer
```

## 23.3 Accept crafting failure when

```text
safe output directly confirms failure/interruption/waste/breakage
attempt target can be bound
```

Result:

```text
failure record
no material consumption unless output validates materials were wasted/consumed
```

## 23.4 Accept recipe learned when

```text
safe output says player reads/learns recipe through valid in-world action
source is player-known, not hidden/card/context/command
operation key not duplicate
```

Result:

```text
RecipeKnowledgeRecord known/partial/hinted according to source
no item output
```

# 25. Enchanting CanonValidator expansion

Enchanting must be extra conservative.

Accept enchanting attempt when:

```text
safe source says player begins/attempts enchantment
item target bound
```

Result:

```text
EnchantingRecord attempted/in_progress
no mechanical power
```

Accept cosmetic/descriptive enchant success when:

```text
safe output confirms glow/rune/aura without mechanical effect
```

Result:

```text
cosmetic_success or lore_success
Inventory item description may update only through owner contract
no combat/stat/ability mechanics
```

Accept mechanical enchant success only when:

```text
future owner rules for equipment/ability/stat effects are active
specific effect is validated
gates/tests pass
```

Default PC19 result:

```text
mechanical_success_deferred or descriptive_only
```

Reject powers when:

```text
recipe/card/context says fire sword
item name implies power
NPC rumor claims power
command output lists enchantment
```

# 28. CraftingReducerLite behavior

CraftingReducerLite owns:

```text

crafting.attempts
crafting.progress
crafting.results
crafting.repairs

crafting.enchantments

```

## 28.1 Intent commit

Accepted crafting intent should:

```text
create CraftingAttemptRecord
status intent_only/in_progress
not consume materials
not create output
mark crafting/context dirty
```

## 28.2 Progress commit

Accepted progress should:

```text
create/update CraftingProgressRecord
not create output unless result validates
```

## 28.3 Success commit

Accepted success should:

```text
create CraftingResultRecord
create material consumption proposals if needed
create output item proposal if player receives item
route actual consume/create to InventoryReducer
record handoff status
mark crafting/inventory/context dirty
```

## 28.4 Failure commit

Accepted failure should:

```text
create CraftingFailureRecord or result failure
only create consumption proposals if waste/consumption validated
not create output item unless partial_success validates it
```

## 28.5 Repair/upgrade/enchant commit

Accepted repair/upgrade/enchant should:

```text
record appropriate attempt/result
defer mechanics unless owner rules active
route item condition/description changes through InventoryReducer/equipment owner
```
