What you want built

You want a single AI Dungeon-native RPG framework that combines the strengths of the scripts we discussed, while fixing their weaknesses.

It needs to work inside AI Dungeon’s actual scripting model, not just be valid JavaScript.

It needs to support a freeform story while also enforcing enough mechanical structure that the world, character progression, inventory, time, and consequences stop falling apart.

The goal is not to make AI Dungeon feel like a rigid menu-based RPG.
The goal is to make it feel like a freeform RPG with real persistence, real scaling, and real consequence tracking.

⸻

What “freeform” means in your design

You do not want a system where:

* the player must choose from narrow classes
* the player can only use approved abilities
* every effect must be phrased in one exact way
* every world change must be entered with a command
* every skill or passive has to be manually predefined

You do want a system where:

* the player can write naturally
* the script can infer intent from many kinds of phrasing
* the script can detect patterns and recurring concepts
* the world can evolve from story context
* skills, talents, passives, locations, buildings, and reputations can form and grow dynamically
* but once something becomes important, it is stored in a stable, structured way so the story stops forgetting it

So the system must be freeform at the surface and structured underneath.

You are not asking for:

What the system must solve mechanically

1. Real character progression

You want a real level, XP, and growth system.

It should cover a huge power range, roughly 1 to 1600, without collapsing.

It should allow:

* weak beginnings
* gradual growth
* specialization
* mastery
* mythic/godlike late-game states for those who truly earn them

It should not hand out rapid growth for doing almost nothing.
Average people in the world should usually remain far below the top end.
Extreme power should require real effort, training, danger, specialization, and long-term development.

2. Level is not everything

You do not want level alone deciding every outcome.

You want:

* matchup differences
* specialization differences
* style differences
* surprise factor
* creativity
* situational advantage
* target-specific preparation

So a lower-level character may defeat a higher-level opponent in a favorable matchup, while losing to a lower-level opponent in an unfavorable one.

That principle should apply broadly across:

* monsters vs humans
* duelists vs hunters
* anti-mage vs brute force
* beast slayers vs armored knights
* unusual styles vs familiar styles

3. Skills, talents, and passives as different systems

You want distinct progression families, not one blurred pile.

Broadly:

* skills are active, deliberate abilities
* talents are active or semi-active techniques and developed applications
* passives are always-on or conditionally-on traits that grow through relevant use/exposure rather than constant manual activation

You want passives to matter deeply:

* resistances
* martial styles
* body adaptations
* magical tolerances
* regeneration-style growth
* anti-magic effects
* unusual combat evolutions

You want them to:

* level naturally
* preserve their intended meaning
* gain new applications over time
* remain balanced through growth requirements rather than being useless forever or overpowered immediately

4. Abilities must preserve context, not just names

This is one of your biggest priorities.

When a new skill/talent/passive is created or discovered, the system must remember what the player was actually building it to do, not reduce it to the most generic interpretation of its name.

So ability storage must capture:

* training context
* intent
* function
* use pattern
* limitations
* target profile
* associated keys/phrases
* observed behavior
* future discovered applications

The system must preserve meaning, not just labels.

The system must detect those changes from freeform story context and update the remembered state accordingly.

8. Current scene truth must be immediate

You do not want the system to wait around for some delayed memory effect before the AI starts respecting what changed.

The current room/building/location state needs to be immediately available to the story.

So the system must have a way to make immediate current-scene truth available now, while also preserving it long-term.

1. Core design rules

Canonical truth order

This engine should always treat truth in this order:

1. state.aidrpg = canonical mechanics and world state
2. Context packets = immediate AI-facing truth for this turn
3. Story Cards = long-term memory mirrors and linked entity records
4. Plot Essentials = always-relevant global truths and compact summaries

This matters because Story Cards are not guaranteed to be present every turn, while Plot Essentials is always considered.  

Design philosophy

The framework should be:

* freeform in expression
* structured in storage
* deterministic in canon
* generative in narration
* AI Dungeon-safe in execution

What the system must never do

It should never:

* require one exact phrasing for actions or consequences
* let raw prose alone become final canon
* depend on Story Cards alone for current room/building state
* depend on unsupported hook behavior
* do expensive whole-world scans every turn
* hardcode user examples as literal built-in content

5. Event flow blueprint

Step 1: Input produces intent candidates

The player writes naturally.
The parser produces structured guesses like:

* likely action family
* likely target
* likely weapon/style/ability
* likely training focus
* likely travel/rest intent

Step 2: Context injects current truth

The AI gets:

* who the player is now
* where they are now
* what the current room/building is like
* what damage or state changes persist
* what is equipped
* what major rules of the world matter now

Step 3: Output produces consequences

The AI narrates.

The system then reads:

* likely injury
* likely damage/deformation
* likely item transfer
* likely environmental change
* likely ability training
* likely reputation shift
* likely time advancement

Step 4: Validation resolves canon

The engine decides:

* what to save
* what to ignore
* what to mark tentative
* what to ask the AI to reinforce next turn

Step 5: Sync and mirror

Canonical state updates first.
Story Cards and summaries update second.

9. AI Dungeon safety rules for implementation

These are non-negotiable build constraints:

Keep hook tabs thin

The docs are explicit that Library is shared code and the other tabs are hook scripts whose last line must be modifier(text). Keep almost all logic in Library.  

Never depend on unsupported stop flow for normal gameplay

The system should not rely on stop to run ordinary RPG logic. Build around normal hook returns.

Respect the 2-second / 16 MB sandbox

Do not scan every card, every actor, every route, and every inventory item on every turn. Use:

* dirty queues
* local scene focus
* cached indexes
* limited candidate sets

The docs explicitly note the 16 MB memory limit and 2-second timeout.  

Remember Output memory timing

Changes to memory-like fields in Output do not affect the AI until the next player action, so current-scene truth must be injected in Context and not assumed to instantly change the already-finished generation.

AIDRPG Hook-by-Hook Implementation Contract
AI Dungeon-specific design reference

Version: Draft 1
Purpose: Define exactly what each AI Dungeon script hook is responsible for, what it is allowed to read/write, how data moves between hooks, and how the system should behave under small or large context budgets.

====================================================================
1) PRIMARY GOAL
====================================================================

This contract exists to keep the project AI Dungeon-native.

The system must:
- work inside AI Dungeon's Library / Input / Context / Output scripting model
- avoid unsupported hook behavior
- keep canonical truth in state.aidrpg
- use Story Cards as persistent mirrors and references, not as the only source of current truth
- degrade gracefully for small-context users
- remain freeform at the surface while structured underneath

The system must not:
- depend on one exact phrasing for any important action
- treat raw prose as final canon without validation
- flood Plot Essentials or context packets with giant blocks of text
- re-scan the entire world every turn if only the local scene changed
- let newly created card text be the only thing preserving important facts

====================================================================
2) HIGH-LEVEL TURN FLOW
====================================================================

The overall intended turn pipeline is:

1. Input hook
   - read raw player input
   - detect commands and natural-language intent
   - create structured candidate intent
   - apply only safe pre-resolution changes
   - store pending state for later hooks

2. Context hook
   - inspect current canonical state
   - build a compact current-scene truth packet
   - build compact always-relevant player/world packet
   - build optional narrative rule packet
   - inject only the minimum needed for this turn

3. Output hook
   - inspect AI output
   - extract structured or inferred consequence candidates
   - validate consequence candidates against canonical state
   - apply canonical updates to player/world/actors/items/abilities/time/reputation/quests
   - queue and perform Story Card sync for changed important entities

4. Next turn
   - Context reflects the updated truth immediately from state
   - Story Cards help with long-term memory and cross-scene reactivation

Truth order:
1. state.aidrpg
2. current Context packets
3. Story Card mirrors
4. Plot Essentials summaries

====================================================================
3) SHARED RULES FOR ALL HOOKS
====================================================================

Every hook must:
- call CoreState.init() or equivalent before doing work
- identify the current hook in state.aidrpg.meta.currentHook
- operate only on canonical state and short-lived pending/cache objects
- avoid large full-world scans unless explicitly required
- respect dirty queues and local-scene indexes
- keep per-hook work small enough for AI Dungeon's runtime limits

Every hook must avoid:
- writing giant prose logs into state
- storing full story history in state
- rebuilding every Story Card every turn
- making final canon changes without validation

All important writes should set dirty markers.

====================================================================
4) INPUT HOOK CONTRACT
====================================================================

Role of Input:
Interpret what the player is trying to do.

Input is the hook for intent, commands, pre-action setup, and safe state preparation.
It should not be the final judge of major consequences.

--------------------------------------------------
4.1 Input may READ
--------------------------------------------------

Input may read:
- state.aidrpg.meta
- state.aidrpg.player
- state.aidrpg.build
- state.aidrpg.abilities
- state.aidrpg.items
- state.aidrpg.world.currentLocationId / currentEntityId
- state.aidrpg.time
- state.aidrpg.quests.active
- local actor/entity indexes if needed

Input should only read nearby/local world context unless a command explicitly requests a broad lookup.

--------------------------------------------------
4.2 Input may WRITE
--------------------------------------------------

Input may write:
- state.aidrpg.pending.inputIntent
- state.aidrpg.pending.pendingPrompts
- state.aidrpg.pending.pendingSceneClarifications
- safe command responses / debug flags
- equipment intent changes if explicit and valid
- explicit travel/rest/training declarations
- small player-side status changes that are deterministic before narration

Input should not directly finalize:
- damage taken/dealt
- item changes gifted by the AI unless explicitly commanded and deterministic
- building damage
- actor generation results
- final quest completion
- final reputation changes

--------------------------------------------------
4.3 Input responsibilities
--------------------------------------------------

A) Command handling
Input should handle creator/player commands such as:
- /sheet
- /inventory
- /time
- /questlog
- /debug on/off
- /resync (creator/admin only)
- /rebuildentity (creator/admin only)

B) Intent detection
Input should classify likely action families such as:
- attack
- defend
- dodge
- move
- travel
- inspect
- talk
- barter
- loot
- equip
- unequip
- rest
- train
- practice ability
- use ability
- consume item
- interact with structure/object

C) Intent enrichment
Input should try to infer, where possible:
- likely target
- likely weapon/style
- likely ability being used or trained
- likely item referenced
- likely desired destination
- likely training focus
- likely social/reputation context

D) Confidence scoring
Input should create candidate interpretations with confidence values.
If multiple strong interpretations exist, Input should keep a shortlist instead of forcing one too early.

E) Safe pre-resolution
Input may safely do things like:
- set a requested travel destination
- set a requested rest duration
- queue a requested equip/unequip if the item exists
- queue a requested ability training target
- queue a requested inspection focus

--------------------------------------------------
4.4 Input output format (internal)
--------------------------------------------------

The canonical internal result of Input should be something like:

pending.inputIntent = {
  primaryType: "attack",
  targetHint: "bandit captain",
  weaponHint: "spear",
  styleHint: "pressure-fighter",
  abilityHint: null,
  environmentHint: "inside tavern",
  confidence: 0.82,
  alternates: [...],
  tags: [...]
}

This object is not necessarily shown to the player.
It exists for Context and Output follow-through.

--------------------------------------------------
4.5 Input must NOT do
--------------------------------------------------

Input must not:
- assume the player's action succeeded
- declare a wall broken because the player tried to break it
- give XP for training before the story supports it
- apply kill XP or combat XP
- permanently mutate the world from intent alone
- overwrite current scene truth from guesswork

====================================================================
5) CONTEXT HOOK CONTRACT
====================================================================

Role of Context:
Tell the AI what is true right now in the smallest useful form.

Context is the hook for immediate local truth, not the full archive.
This is where the system compensates for Story Cards not always being present in context.

--------------------------------------------------
5.1 Context may READ
--------------------------------------------------

Context may read:
- entire local player state summary
- current scene/location/building state
- local actors
- visible equipment
- active statuses and major body changes
- relevant quests
- current time/day
- immediate hazards
- a small number of relevant abilities or passives
- cache values for the same scene
- info.maxChars / info.memoryLength if available

--------------------------------------------------
5.2 Context may WRITE
--------------------------------------------------

Context may write:
- state.aidrpg.meta.mode (tiny / normal / wide)
- state.aidrpg.cache.scenePacket
- state.aidrpg.cache.playerPacket
- state.aidrpg.cache.actorPacket
- other compact caches for reuse

Context should not mutate canonical world/player state except for harmless cache/meta fields.

--------------------------------------------------
5.3 Context budgeting modes
--------------------------------------------------

The script must support adaptive injection.

TINY MODE
Use for very small available context.
Inject only:
- current location/entity name
- one-line player status
- visible gear summary
- 1 to 3 most important local facts
- one urgent time or quest fact if needed

NORMAL MODE
Inject:
- current location/entity
- compact player status
- visible gear
- current local actors
- major local hazards
- current building/room condition
- time/day summary
- one active quest summary if relevant

WIDE MODE
Inject all of NORMAL plus:
- richer atmosphere
- more linked entity detail
- a short relationship/reputation reminder if relevant
- an ability-specific reminder if needed
- a short comparative-power rule if a major mismatch exists

--------------------------------------------------
5.4 Context packet priorities
--------------------------------------------------

Priority order for Context should be:
1. current scene truth
2. current visible player truth
3. immediate danger / condition truth
4. immediate time truth
5. active quest summary if relevant
6. nearby major NPC summaries
7. broader atmosphere or linked-world details
8. optional AI instruction snippets

If budget is too small, lower-priority packets are dropped first.

--------------------------------------------------
5.5 Required Context packet families
--------------------------------------------------

A) Scene packet
Must summarize:
- where the player is
- what kind of place it is
- current structural/environment condition
- immediate exits or movement options if relevant
- immediate hazards if relevant
- notable current objects or changes

B) Player packet
Must summarize:
- current level if relevant
- overall condition (healthy / injured / maimed / altered / exhausted)
- visible equipment or carried weapon
- visible body changes if important
- notable passive/condition states that matter this turn

C) Time packet
Should summarize only what matters now:
- current day / rough time
- recent relevant elapsed-time fact if needed
- travel/rest timing if the scene depends on it

D) Quest packet
Only if relevant to the current scene or decision.
One-line summary preferred.

E) Actor packet
Only nearby/relevant actors.
Must remain compact.

F) Rule packet
Short behavioral instructions for the model, used sparingly.
Examples of things the rule packet may remind the AI:
- maintain comparative power realism
- preserve persistent environmental damage
- respect current time/day
- respect visible equipment and injuries
- low-level abilities are limited, high-level abilities are refined

--------------------------------------------------
5.6 Context must NOT do
--------------------------------------------------

Context must not:
- dump the whole player sheet every turn
- dump full inventory every turn
- dump every active Story Card into context
- assume the AI needs every world detail all the time
- rely on Plot Essentials for giant state serialization

====================================================================
6) OUTPUT HOOK CONTRACT
====================================================================

Role of Output:
Interpret what happened and update canon.

Output is the main mutation hook.
This is where canonical state changes should actually be applied.

--------------------------------------------------
6.1 Output may READ
--------------------------------------------------

Output may read:
- the raw AI output text
- state.aidrpg.pending.inputIntent
- player/build/abilities/items
- current scene/world state
- local actors
- current time
- active quests and local reputation context
- cached scene data

--------------------------------------------------
6.2 Output may WRITE
--------------------------------------------------

Output may write:
- canonical player changes
- canonical ability growth/creation/revision
- canonical item changes
- canonical world/entity changes
- canonical actor generation/revision
- canonical time advancement
- canonical reputation shifts
- canonical quest progress
- dirty queues
- card sync queues
- cache invalidation
- recent logs/debug traces

--------------------------------------------------
6.3 Output responsibilities
--------------------------------------------------

A) Consequence extraction
Output should attempt to extract:
- structured event blocks if the system uses them
- freeform consequence candidates if no structured block exists
- likely injuries, victories, losses, exchanges, and environmental changes
- likely ability training or ability discovery signals
- likely item changes
- likely time advancement
- likely quest progress
- likely reputation changes

B) Validation
Before anything becomes canon, Output must validate candidates against:
- current known player state
- current world/scene state
- actor capability and matchup logic
- time continuity
- inventory possibility
- existing entity identity/state

C) Consequence application
After validation, Output applies canonical changes.

D) Dirty marking
When something changes, mark the relevant dirty flags so only the changed records/cards are refreshed.

E) Card sync scheduling
Output should queue Story Card mirror updates for important changed entities.

F) Cache invalidation
If scene truth changed, invalidate cached scene packets.

--------------------------------------------------
6.4 Output result categories
--------------------------------------------------

Output must be able to distinguish at least these categories:

PLAYER
- damage / healing
- status gain/loss
- mutation / body change
- equipment change
- passive/skill/talent growth
- XP gain
- level-up

ITEMS
- gained
- lost
- consumed
- damaged
- transformed
- equipped/unequipped
- currency changed

WORLD
- structure damaged
- structure repaired
- ownership changed
- occupancy changed
- route altered
- district/town state shifted

ACTORS
- new important actor detected
- actor injured/killed/fled
- actor rank/role clarified
- actor relationship changed

TIME
- hours advanced
- day advanced
- travel completed
- rest completed
- contradiction detected

QUESTS
- accepted
- updated
- completed
- failed
- abandoned

REPUTATION
- faction shift
- location shift
- personal relationship shift
- rumor label/title shift

--------------------------------------------------
6.5 Output must NOT do
--------------------------------------------------

Output must not:
- blindly trust every vivid description as fact
- let one ambiguous sentence permanently rewrite a major location
- generate giant card rewrites for every tiny event
- update everything in the world when only one local object changed
- allow duplicate consequence application on retries

8) STORY CARD CONTRACT
====================================================================

Story Cards are mirrors, not sole truth.

--------------------------------------------------
8.1 Card creation policy
--------------------------------------------------

Create or maintain cards for:
- important locations
- important buildings
- important actors
- important factions
- important routes
- meaningful abilities
- central quest log / reputation summary if useful

Do not create cards for everything.

--------------------------------------------------
8.2 Card sync policy
--------------------------------------------------

Sync cards when:
- an important new entity becomes persistent
- an important entity's current state changes materially
- an ability meaning becomes stable enough to record
- a route/travel baseline becomes meaningful
- reputation or quest summaries need durable memory

Do not sync on every tiny fluctuation.

--------------------------------------------------
8.3 Card content policy
--------------------------------------------------

Every card type should keep a consistent structure.

Minimum conceptual fields:
- identity
- current state
- links
- last confirmed turn/day

Ability cards must include:
- origin context
- intended function
- current behavior
- keys
- discovered applications

Building cards must include:
- materials
- ownership
- layout basics
- district/side-of-town placement
- current condition

====================================================================
9) VALIDATION CONTRACT
====================================================================

The system must validate candidate changes before saving them.

--------------------------------------------------
9.1 Validation categories
--------------------------------------------------

A) Plausibility validation
Does this consequence fit the known state?

B) Continuity validation
Does it contradict current time, place, body state, or known possession?

C) Scale validation
Does it fit comparative power and role/rank logic?

D) Specificity validation
Is the information concrete enough to save now, or should it stay tentative?

--------------------------------------------------
9.2 Tentative state policy
--------------------------------------------------

If a consequence is probable but not certain, the system may:
- mark it tentative in pending/unresolved state
- wait for reinforcement next turn
- save a softer form of the truth

Example:
Instead of "north wall collapsed completely," it may save "north wall appears badly damaged" until reinforced.

--------------------------------------------------
9.3 Hard-save policy
--------------------------------------------------

A change should be hard-saved immediately when:
- it is explicit and concrete
- it affects current scene truth in a major way
- it directly affects player state
- it directly affects possession/equipment
- it directly affects time progression
- it would be harmful to lose before next turn

====================================================================
10) XP CONTRACT
====================================================================

The engine should have multiple XP lanes.

A) Level XP
Sources may include:
- meaningful combat victories
- meaningful survival under threat
- kill XP
- major discoveries
- breakthrough moments
- major quest/world progress

B) Skill/Talent XP
Sources may include:
- direct use
- direct training
- successful difficult execution
- creative or unusual application

C) Passive XP
Sources may include:
- relevant environmental exposure
- repeated relevant strain or practice
- survival-driven adaptation

D) Anti-farm policy
Repeated easy gains should decay.
Novel, risky, or specialized gains should remain valuable.

E) Level vs mastery policy
Level increases raw capacity.
Skills/talents/passives create the real shape and efficiency of a build.
A high-level but undeveloped character should be dangerous but under-realized.

====================================================================
11) BODY-STATE CONTRACT
====================================================================

The player's body must be persistent and world-reactive.

The system must support long-term or permanent effects such as:
- losing limbs
- scars
- mutations
- species changes
- vampirism-like conditions
- blessings/curses
- visible body changes
- sunlight weakness or resistance evolution

These changes should:
- affect later play
- affect narration
- affect build possibilities
- affect visible appearance packets
- update automatically without manual card editing

====================================================================
12) SMALL-CONTEXT SAFETY CONTRACT
====================================================================

This system must remain playable under tight context.

Rules:
- inject only what is needed now
- never serialize the whole state into Context
- use scene-centric packets
- keep long-term details in Story Cards/state, not repeated every turn
- prioritize immediate truth over rich flavor when budget is small

Recommended priority under tight context:
1. current scene condition
2. current visible player state
3. current danger/urgency
4. current time/day
5. current quest if relevant
6. nearby important actor summary
7. richer world detail

====================================================================
13) PERFORMANCE CONTRACT
====================================================================

To stay safe inside AI Dungeon's runtime limits, implementation should:
- use dirty queues
- cache scene packets
- cache local actor/entity ids
- avoid whole-world rebuilds
- limit per-turn card sync count
- keep rolling logs short
- keep pending candidate sets small

The likely runtime risks are:
- excessive entity scans
- giant card sync sweeps
- large cached prose blocks
- repeated reparsing of the entire inventory/world

====================================================================
14) FAILURE-SAFE CONTRACT
====================================================================

If parsing is uncertain, the system should fail soft.

Soft-fail options:
- do nothing
- save tentative low-confidence state
- defer to next-turn reinforcement
- preserve only the most generic safe truth

The system should avoid catastrophic outcomes from noise.

Examples of things that must not happen from weak evidence alone:
- permanent player death
- permanent world collapse
- major item deletion
- huge actor-level rewrites
- impossible time jumps

====================================================================
15) MVP IMPLEMENTATION ORDER
====================================================================

Stage 1
- CoreState
- TurnEngine
- IntentParser
- PlayerSystem
- ProgressionSystem
- BuildIdentitySystem
- InventorySystem
- SceneStateSystem
- PlotPacketSystem

Stage 2
- AbilitySystem
- PassiveResistanceSystem
- Ability cards
- ability meaning preservation

Stage 3
- WorldEntitySystem
- TimeTravelSystem
- ReputationSystem
- QuestLogSystem
- card sync expansion

Stage 4
- CombatResolutionSystem
- NPCGenerationSystem
- matchup scaling and specialization logic

Stage 5
- selective Inner Self-style major NPC memory

====================================================================
16) FINAL SUMMARY
====================================================================

Input decides what the player is probably trying to do.
Context tells the AI what is true right now.
Output decides what probably happened and updates canon.
State holds the truth.
Cards mirror important truth for long-term memory.
Context packets stay compact and scene-focused.
The system remains freeform on the surface but structured underneath.

AIDRPG KEEP-CHANGE-DROP BORROW LEDGER
=====================================

Purpose
-------
This file is the full borrow/remix ledger for the planned AI Dungeon RPG framework.

It answers:
- what concepts are being kept from RPGUI, TAS, Inner Self, and Auto-Cards
- what concepts are being changed or reinterpreted
- what concepts are being dropped entirely
- what brand-new systems are being added that are not being cleanly borrowed from any one source

This is a design reference, not implementation code.


BORROW POLICY
=============

The project should remix concepts and proven patterns, not blindly combine incompatible codebases.

General rule:
- reuse architecture, module ideas, and behaviors where they are strong
- rewrite the actual implementation into one coherent AI Dungeon-native engine
- keep canonical truth in state.aidrpg
- treat Story Cards as long-term mirrors, not the only source of current truth
- keep current-scene truth immediate and context-driven
- keep mechanics deterministic and world/narration generative where appropriate

The project should not:
- directly mash all existing scripts together
- inherit old flaws just because the old scripts were complete
- let one script's philosophy dominate every subsystem
- copy user examples literally into built-in functionality


1) RPGUI / CURRENT UPLOADED SCRIPT
==================================

Summary
-------
RPGUI's strongest contribution is disciplined state ownership.
Its weakest contribution is fragile combat/event parsing from emoji-like markers and a brittle hard-death flow.

KEEP
----

1. Helper/module split
- Keep the idea that shared helpers live in Library and hook tabs remain light.
- Utility helpers like clamp-style functions, bar renderers, and clean display helpers are worth preserving in spirit.

2. Persistent state as source of truth
- Keep the idea that HP, XP, level, death/defeat flags, progression state, and other hard mechanics live in script state.
- Narrative should reflect mechanics, not replace them.

3. Input/Output role separation
- Keep the broad structure where Input handles commands and action setup while Output handles consequences and player-facing updates.

4. Consistent player-facing sheet/HUD philosophy
- Keep the idea that the player should have a stable mechanical readout or summary.
- It does not have to be the same visual format, but the principle is valuable.

CHANGE
------

1. Replace emoji-based authority
- The current system depends on markers like damage/heal/combat symbols as mechanical authority.
- Change this into structured event parsing plus validation, with freeform fallback support.

2. Replace hard death lock
- The current sticky death lock and forced game-over handling are too brittle.
- Change this into a more nuanced defeat/injury/incapacitation system that can represent:
  - defeat
  - death
  - maiming
  - retreat
  - capture
  - unconsciousness
- Permanent death must not fire from noisy output.

3. Replace Output-heavy simulation
- RPGUI pushes too much of the game into Output.
- Change this into a coordinated engine where:
  - Input handles intent
  - Context handles current truth
  - Output validates and applies consequences

4. Keep reset/recovery ideas only as tools
- Reincarnation/reset concepts may survive as optional admin/recovery tools, not as the core design loop.

DROP
----

1. Drop combat-by-emoji counting
- Do not preserve the current core combat parser.

2. Drop hard dependence on fake-HUD stripping
- Cleanup helpers may remain, but this should not be a primary anti-corruption strategy.

3. Drop the current context-stop behavior
- The current Context script behavior is not part of the new design.

BOTTOM LINE
-----------
Keep RPGUI's state discipline and helper separation.
Drop its fragile symbol-authority combat model.
Rebuild its hook responsibilities into a larger AI Dungeon-native architecture.


2) TAS
======

Summary
-------
TAS is the strongest source for freeform action interpretation, emergent growth concepts, and editable ability/inventory structures.
Its biggest flaw is letting broad prose heuristics act too often as final authority.

KEEP
----

1. Freeform player input philosophy
- Keep the idea that the player should be able to write naturally.
- The system should infer intent from many phrasings instead of requiring menu-like commands.

2. Structured data for talents, skills, and inventory
- Keep the principle that learned abilities and inventory entries are stored as structured records, not vague prose alone.

3. Emergent learning concept
- Keep the idea that repeated use, repeated practice, and repeated thematic behavior can produce a real learned ability.
- The engine should notice recurring patterns and elevate them into stable records.

4. Activity families
- Keep broad action families like:
  - attack
  - defend
  - dodge
  - scout
  - rest
  - consume
  - train
  - practice
- These are useful for routing intent and progression.

5. Build-shaping identity inputs
- Keep the idea that player identity can be shaped by origin, species, style, race-like traits, world role, and other long-term modifiers.

CHANGE
------

1. Prose heuristics become proposal engines
- Change TAS's broad prose parsing so it proposes likely intent/effect rather than deciding final canon by itself.
- Freeform interpretation stays broad.
- Canon becomes structured only after validation.

2. Replace fixed race/class framing with tag stacks
- Change rigid or semi-rigid class/race assumptions into layered tags:
  - origin
  - combat
  - method
  - resource
  - defense
  - specialization
  - temperament
  - style
  - archetype summary
- This preserves freedom while keeping the build legible.

3. Split progression into multiple lanes
- Change the progression model into separate lanes:
  - level XP
  - skill XP
  - talent XP
  - passive XP
  - reputation/world progression
- Level should be a major raw-capacity axis, not the sole measure of mastery.

4. Add first-class passives
- TAS had skills/talents; the new framework must explicitly support passives.
- This includes:
  - resistances
  - body adaptations
  - martial styles
  - magical tolerances
  - regeneration-style growth
  - anti-magic passives
  - condition-linked evolution

5. Add outlier-growth support
- The new framework must handle things TAS did not formalize well:
  - absorption builds
  - stat theft
  - body corruption
  - vampirism
  - mutation
  - body-plan changes
  - species shifts
  - nonstandard stat ceilings

6. Make kill XP real but bounded
- Add kill XP as one valid source of level XP.
- Balance it with:
  - threat scaling
  - novelty weighting
  - anti-farm decay
  - competition with training/discovery XP
- The goal is to preserve some video-game feeling without letting grind dominate the system.

DROP
----

1. Drop prose-only combat authority
- The AI's wording alone should not decide exact mechanical truth.

2. Drop weak item-state handling
- Inventory must become condition-aware, reliable, equipment-aware, and mutation-aware.

3. Drop the assumption that level means practiced competence
- Level should mean raw capacity and growth, not automatic skill expression.

BOTTOM LINE
-----------
Keep TAS's freeform spirit, emergent learning ambition, and structured ability records.
Replace its prose-only authority with validation-driven canon.
Expand it with passives, outlier growth, and better inventory/world integration.


3) INNER SELF
=============

Summary
-------
Inner Self is the strongest source for segmented memory, entity-specific persistence, and important-NPC internal state.
It is not the right central model for combat or progression, but it is highly valuable for long-term character/world memory.

KEEP
----

1. Segmented memory by entity
- Keep the idea that important NPCs, factions, buildings, and other major entities should not all blur together in one giant memory pool.

2. Major-NPC mind model
- Keep the idea that important recurring NPCs can preserve:
  - goals
  - grudges
  - attitudes
  - priorities
  - secrets
  - plans
- This should be selective, not universal.

3. Name/entity activation logic
- Keep the idea that important entities can become active when relevant rather than remaining equally active all the time.

4. Configuration-minded design
- Keep the general principle that a script this large should have explicit creator-facing settings and internal organization.

5. Merged world-building mindset
- Keep the idea that memory, entity persistence, and world-building should be part of the same engine, not isolated add-ons.

CHANGE
------

1. Use selective NPC minds only
- Major named actors: yes.
- Every random peasant, extra, or passing traveler: no.
- The system must stay performant and AI Dungeon-safe.

2. Keep minds subordinate to canonical world truth
- An NPC's mind may store beliefs, attitudes, and plans.
- It must not override hard truth such as:
  - whether a building is broken
  - whether the player lost an arm
  - whether a town burned
  - whether a route takes two days
- Canonical world/player state still wins.

3. Integrate NPC minds with reputation/time/world systems
- NPC memory should be grounded in the same world-state engine, not become disconnected improvisational canon.

DROP
----

1. Drop Inner Self as the main mechanical engine
- It should inform memory systems, not replace the stat/combat/progression framework.

2. Drop universal “mind simulation”
- The system should not waste resources simulating internal worlds for everyone.

BOTTOM LINE
-----------
Keep Inner Self for segmented memory, important-NPC persistence, and entity-specific long-term continuity.
Do not use it as the core combat or stat model.


4) AUTO-CARDS
=============

Summary
-------
Auto-Cards is the strongest source for entity detection, automatic card drafting, and long-term memory compression/summarization.
Its biggest weakness is that title-driven generation can flatten meaning or produce overly generic records.

KEEP
----

1. Named-entity detection
- Keep the idea that the script can detect important named things from story context and decide they deserve records.

2. Card generation and later revision
- Keep the idea that creation and maintenance are separate:
  - detect candidate
  - generate initial record
  - revise/update later as more becomes known

3. Memory compression/summarization
- Keep the concept that long-running entity histories can be compressed into more stable summaries.

4. Prompt-driven card drafting
- Keep the idea that the AI can help generate structured summaries from current context.

5. Optional manual nudges
- Keep room for creator/admin/player nudges to force or repair entity records if needed.

CHANGE
------

1. Change prose blobs into typed record mirrors
- Card content should follow typed families such as:
  - location
  - building
  - actor
  - ability
  - route
  - faction
  - reputation
  - quest_log
- Each should preserve identity, current state, links, and timestamps.

2. Change title-only generation into context-plus-purpose generation
- Especially for abilities, items, and buildings:
  - the title alone must never define meaning
  - context, origin, purpose, and observed behavior must all matter

3. Change cooldown-only generation into priority-driven persistence
- If something materially changes now, canonical state updates now.
- Card refinement can happen afterward.
- Important changes should not be delayed just because a timer has not expired.

4. Change world detail generation into interlinked world-state generation
- Buildings should track:
  - materials
  - ownership
  - district/side-of-town
  - layout basics
  - atmosphere
  - clientele/use
  - current damage/occupation state
- Locations should track linked districts/routes/factions.
- Actors should track role/rank/relationships/current condition.

DROP
----

1. Drop Story Cards as the only source of current scene truth
- Current room/building state must be available immediately through Context packets from canonical state.

2. Drop title-driven flattening
- This is what causes generic reinterpretation of items, abilities, and places.

BOTTOM LINE
-----------
Keep Auto-Cards for detection, drafting, updating, and memory compression.
Transform its output into typed card mirrors backed by canonical state.

--------------------------------

- preferred mode is user/creator-selected

1. current scene truth
2. current visible player truth
