# AIDRPG Production Chunk 07 — Quest, Objective, Reward, and Promise/Payment Depth

## 0. Document status

**Document name:** AIDRPG Production Chunk 07 — Quest, Objective, Reward, and Promise/Payment Depth  
**Production sequence:** 07 of 25 remaining production chunks  
**Build target:** WorldLedger V0.17.6 ability-depth accepted build / AIDRPG Core MVP expansion path  
**Purpose:** Deepen quest records, objective states, quest offers, quest acceptance, objective progress, completion, reward promises, reward readiness, reward payment, and duplicate-safe reward behavior without rumor activation or promise/payment confusion.  
**Status:** Core gameplay-depth production chunk.  
**Follows:** Production Chunk 06 — Ability Candidate, Training, Use, Failure, and Stability Depth.  
**This document does not contain final script code.**

Production Chunk 07 exists because quest and reward handling is one of the most dangerous RPG automation areas.

Old systems often blurred:

```text
rumor
offer
accepted quest
active objective
objective progress
objective completion
ready to turn in
quest completion
promised reward
paid reward
duplicate paid reward
```

That cannot happen in the final system.

A quest must move through explicit states.

Rewards must be promised, ready, paid, denied, disputed, or duplicate-skipped with clear audit.

A promised reward is not currency.

A completed objective is not payment.

A command display is not reward collection.

---

# 1. Chunk doctrine

```text
Rumor is not a quest.
Offer is not acceptance.
Acceptance is not completion.
Progress is not completion.
Completion is not payment.
Ready reward is not paid reward.
Promised gold is not currency.
Paid once means paid once.
Quest text is not inventory.
Command display is not reward collection.
```

Quest and reward truth must be stateful, duplicate-safe, and explainable.

---

# 2. Why this chunk comes now

Production Chunk 05 made inventory/currency safe.

Production Chunk 06 made abilities safe.

Quest/reward depth comes next because it depends on both:

```text
quest item custody and ownership
currency payment through InventoryReducer
ability training objectives
body injury/recovery objectives
actor quest givers
location objectives
future progression XP rewards
future reputation/faction/domain consequences
```

If quest and reward states are not safe now, future systems will duplicate rewards, activate rumor quests, auto-complete objectives, and hide broken progression behind command displays.

# 13. Quest CanonValidator expansion

CanonValidator must enforce quest state transitions.

## 13.1 Accept quest offer when

```text
safe story output has NPC/job/board/request offering a task
objective target is bound enough
not quoted hypothetically only
not dream/rumor only unless status = rumored
not command/context/card source
```

Result:

```text
quest offered or rumored
not active unless accepted
```

## 13.2 Accept quest acceptance when

```text
player explicitly accepts in input and output/structure supports quest start
or safe output clearly states quest accepted/started
or structured startup quest starts active before lock
```

Result:

```text
quest active
objectives initialized
```

## 13.3 Accept objective progress when

```text
safe output directly shows partial progress toward active objective
objective exists or can bind to active quest
not merely intent
not command/context/card source
```

## 13.4 Accept objective completion when

```text
safe output directly confirms required objective completed
objective target binds to active quest objective
not duplicate
not merely arriving near objective
not merely seeing target
```

## 13.5 Accept quest completion when

```text
safe output directly confirms quest completed
or all required objectives complete and policy allows status ready/completed
not duplicate
```

Completion should normally lead to:

```text
ready_to_turn_in
```

unless reward/payment is also explicitly validated.

# 17. QuestReducerLite detailed behavior

QuestReducerLite owns:

```text
quests.records
quests.active
quests.offered
quests.rumored
quests.readyToTurnIn
quests.completed
quests.failed
quests.abandoned
quests.rewardLedger
quests.warnings
```

## 17.1 Rumor commit

Accepted rumor should:

```text
create/update quest as rumored
store source/evidence
not activate quest
mark quest_log/context dirty if useful
```

## 17.2 Offer commit

Accepted offer should:

```text
create/update quest as offered
store giver if known
store objective candidates
store promised rewards if present
not activate quest unless accepted separately
```

## 17.3 Acceptance commit

Accepted acceptance should:

```text
create/update quest as active
initialize objectives
preserve promised rewards
record operation key
mark quest_log/context dirty
```

## 17.4 Objective progress commit

Accepted progress should:

```text
update objective progressCurrent/status
append evidence/history
not complete unless threshold/direct completion reached and accepted
```

## 17.5 Objective completion commit

Accepted completion should:

```text
set objective status complete
record completedTurn
check duplicate key
if all required objectives complete, mark quest ready_to_turn_in or completed according to policy
not pay reward automatically
```

## 17.6 Quest completion commit

Accepted quest completion should:

```text
set quest status completed or ready_to_turn_in according to source
preserve reward status as promised/ready unless payment exists
not award currency/items/XP automatically
```

## 17.7 Failure/abandonment commit

Accepted failure/abandonment should:

```text
set status failed/abandoned
record reason/source
preserve history
not delete quest immediately
```

```text

store promisedByActorKey if known
mark quest_log/context dirty
no inventory/currency/progression mutation
```

## 18.2 Reward ready commit

Accepted ready should:

```text
set reward status ready
record readyTurn
no inventory/currency/progression mutation
```

## 18.3 Reward payment commit

Accepted payment should:

```text
check reward payment key
set reward status paid
record paidTurn/paidByActorKey
mark quest_log/context dirty
emit or pair with explicit InventoryReducer currency/item event if reward is currency/item
```

Preferred safe policy:

```text
QuestReducer marks reward paid.
InventoryReducer receives separate accepted currency.gain_candidate or item.reward_handoff_candidate.
Both share a related payment key.
```

If split result cannot be implemented yet, mark payment status and defer currency mutation rather than paying unsafely.

## 18.4 Reward denied/disputed commit

Accepted denial/dispute should:

```text
set status denied or disputed
record reason/source
no payment
no currency/item/XP mutation
```

# 20. Split-owner reward payment contract

Because inventory/currency is owned by InventoryReducer, reward payment needs explicit handoff.

## 20.1 Currency reward flow

Example:

```text
Old Bren pays you the promised 15 gold.
```

Validated results:

```text
reward.payment_candidate -> QuestReducer marks reward paid
currency.gain_candidate -> InventoryReducer adds 15 gold
```

Both should share:

```text
rewardPaymentKey
payerKey
questKey
amount
currencyType
sourceClauseHash
```

## 20.2 Item reward flow

Example:

```text
Bren hands you the silver wolf charm as your reward.
```

Validated results:

```text
reward.payment_candidate -> QuestReducer marks item reward paid/received
item.reward_handoff_candidate -> InventoryReducer adds item
```

## 20.3 XP reward flow

XP reward should remain deferred unless ProgressionReducer exact XP support is active.

If deferred:

```text
reward status can be ready/paid as narrative status
XP mutation deferred/pending
ReleaseCheck warns honestly
```


```text

Quests have states.
```
