AIDRPG Build Chunk 8 — CommandRouter and Command Renderer Implementation Plan

0. Document status

Document name: AIDRPG Build Chunk 8 — CommandRouter and Command Renderer Implementation Plan
Build target: AIDRPG Core MVP v0.1
Purpose: Define the exact command detection, routing, alias handling, disabled-command behavior, command renderer ownership, command output suppression, and command safety tests before command code is generated.
Status: Practical build document.
Follows: Build Chunk 7 — AuditLogger and OperationLedger Implementation Plan.
This document does not contain final script code.

This chunk is useful because commands are the player’s main way to see, test, and debug the system.

If commands mutate state, command output becomes a hidden gameplay system.

If commands lie, the player cannot trust the script.

If command output is parsed as story, old duplication bugs return.

If aliases are inconsistent, old test workflows break.

If disabled commands activate deferred systems, the MVP boundary collapses.

Build Chunk 8 makes command behavior exact before coding.

⸻

1. Command doctrine

The command doctrine is:

Commands inspect state.
Commands explain state.
Commands route safely.
Commands suppress their own output.
Commands do not mutate gameplay state.
Commands do not activate deferred systems.

Commands may update runtime command metadata and diagnostic audit lines.

Commands may not create gameplay truth.

⸻

2. Why this chunk comes before parser/reducer work

Command safety must exist before parser/reducer automation.

Reason:

Once parser/reducer systems become active, command output becomes dangerous unless suppression is already locked.

Examples:

* /inventory displaying Rusty Dagger must not create another dagger.
* /quests displaying Reward: 15 gold promised must not pay the reward.
* /abilities displaying Shadow Step — candidate must not stabilize Shadow Step.
* /actors displaying Mara — elsewhere must not make Mara present.
* /location displaying Travel Intent: chapel must not move the player to chapel.

Build Chunk 8 protects those cases before automation starts.

4. CommandRouter responsibilities

CommandRouter owns:

* slash command detection
* command text normalization
* command argument parsing
* command alias resolution
* active command dispatch
* disabled command dispatch
* unknown command handling
* command output suppression integration
* command audit line if desired
* safe command error handling

CommandRouter does not own:

* gameplay mutation
* state schema repair beyond StateManager call
* command output formatting details beyond dispatch
* releasecheck logic itself
* card sync live writes
* cleanup destructive actions
* manual mutation behavior

⸻

5. Command renderer responsibilities

Command renderers own:

* readable command output text
* state summaries
* empty-state display
* warning display
* disabled system message formatting
* alias note display
* output truncation/summarization

Command renderers do not own:

* command detection
* alias routing
* gameplay mutation
* StateManager repairs
* OperationLedger mutation
* parser/reducer calls
* card API calls
* quarantine resolution

8. Command detection rules

8.1 Command prefix

A command is an input beginning with:

/

followed by at least one command character.

Examples:

/help
/inventory
/releasecheck
/craft sword
/cardsync live on

8.2 Non-command examples

These are not commands:

I swing my sword.
Mara says /help as a joke.
The sign reads: /inventory.
I type the symbol / in the dust.

Only player input beginning with / at the start of the input is a command.

8.3 Whitespace

Leading whitespace may be trimmed for command detection.

Examples:

  /help

should route as /help.

8.4 Case

Commands should be case-insensitive.

Examples:

/HELP
/Inventory
/ReLeAsEcHeCk

should normalize to:

/help
/inventory
/releasecheck

⸻

9. Command parse result schema

CommandRouter should parse command input into a structured object.

ParsedCommand {
  rawText: string,
  commandName: string,
  normalizedName: string,
  argsText: string,
  args: string[],
  isCommand: boolean,
  aliasOf: string,
  routeStatus: 'active' | 'disabled' | 'unknown' | 'error',
  notes: string[]
}

9.1 Example

Input:

/questlog active

Parsed:

rawText = '/questlog active'
commandName = 'questlog'
normalizedName = 'quests'
argsText = 'active'
args = ['active']
isCommand = true
aliasOf = 'questlog'
routeStatus = 'active'

9.2 Args in MVP

Most MVP commands ignore args or treat them as informational.

MVP should not implement mutation args like:

/additem Crown
/setlevel 99

Those remain disabled.

14. Unknown command behavior

If a command starts with / but is not active, aliased, or recognized as disabled, return unknown command output.

Required behavior:

* no crash
* no gameplay mutation
* command output suppression active
* suggest /help

Example:

[AIDRPG] Unknown Command
Status: Not Recognized
Command: /banana
Use /help to see active MVP commands.
No gameplay state was changed.

⸻

15. Command routing flow

Command routing should follow this order:

1. Receive input text from Input hook.
2. Parse command.
3. Normalize command name.
4. Resolve alias.
5. If active command: dispatch active renderer.
6. Else if disabled command/family: render disabled message.
7. Else: render unknown command message.
8. Truncate output if needed.
9. Return command output to Runtime.
10. Runtime marks command suppression.

CommandRouter itself should not return raw undefined/null.

If renderer fails, CommandRouter safeRoute should return fail-soft command error text.

⸻

16. Command output suppression integration

CommandRouter returns command output.

Runtime marks suppression.

Recommended integration:

const output = CommandRouter.safeRoute(root, inputText)
Runtime.setCommandSuppression(root, parsedCommand.normalizedName, output)
return output

16.1 Command output prefix

Every command output should begin with:

[AIDRPG]

Runtime may use this as secondary suppression detection.

16.2 Command output hash

Runtime should hash the final command output after truncation.

This becomes:

runtime.lastCommandHash

16.3 Command output must not be scanned

The Output hook must skip parser/proposal/reducer processing for suppressed command output.

⸻

17. Renderer safety rules

Every renderer must:

* tolerate missing/malformed bucket values
* use safe defaults/display
* show none for empty lists
* avoid full raw JSON dumps
* cap long output
* not call reducers
* not call parser
* not call CardSync live writes
* not call cleanup destructive actions
* not enable feature flags
* not resolve quarantine

Renderers can call read-only helpers.

22. Command non-mutation enforcement

Because JavaScript-like environments do not automatically enforce read-only renderers, the plan must rely on boundaries and tests.

22.1 Required enforcement methods

* renderers do not call reducers
* renderers do not call parser
* renderers do not call CardSync live writes
* renderers do not call Cleanup destructive actions
* commands have tests comparing gameplay buckets before/after
* ReleaseCheck verifies command mutation risk

22.2 Optional future enforcement

A future test harness may snapshot gameplay buckets before/after command rendering.

If any gameplay bucket changes from command rendering, command test fails.

⸻

23. Command audit behavior

CommandRouter may add light audit lines.

Examples:

Command routed: /questlog -> /quests.
Command disabled: /craft requires Crafting Mini-Spec.
Unknown command: /banana.

Command audit must be capped.

Do not audit every command forever unbounded.

Command audit is diagnostic only.

⸻

24. Command error handling

If command rendering throws an error:

CommandRouter safe route should return:

[AIDRPG] Command Error
Status: Failed Safely
The command failed safely. Gameplay state was not intentionally changed.
Run /debuglast or /stateaudit for details.

Runtime should also record runtime error through fail-soft if the exception escapes router.

Command failure must not erase state.

⸻

25. Command output and parser interaction

Command output is explicitly non-canon.

25.1 Parser must not scan command output

Output hook suppression must happen before EventScannerLite.

25.2 Command output prefix

[AIDRPG] is a non-story marker.

Parser should reject text beginning with [AIDRPG] as non-canon source even if suppression flag fails.

25.3 Commands that display dangerous words

Commands may display dangerous words like:

* gold
* XP
* stable ability
* candidate ability
* active quest
* Crown of Dawn
* Mara
* dead
* reward paid

These are display only.

They must not create or modify state.

⸻

26. ReleaseCheck requirements for commands

ReleaseCheck must verify:

* active command list exists
* command output prefix is used
* suppression integration exists
* disabled command families are recognized
* unknown command handler exists
* commands are inspect-only in MVP
* manual mutation commands disabled
* generated CardSync commands disabled
* /help honesty requirements satisfied
* /releasecheck command exists

ReleaseCheck must fail if:

* command output can be scanned as story
* /help claims disabled systems are active
* manual mutation commands are enabled
* generated cards can be enabled by command
* disabled commands mutate gameplay

ReleaseCheck may warn if:

* alias coverage is incomplete
* command output caps are not fully implemented
* some diagnostic commands are shell-only
