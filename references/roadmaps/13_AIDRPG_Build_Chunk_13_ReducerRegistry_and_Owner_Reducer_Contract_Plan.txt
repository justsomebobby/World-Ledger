AIDRPG Build Chunk 13 — ReducerRegistry and Owner Reducer Contract Plan

0. Document status

Document name: AIDRPG Build Chunk 13 — ReducerRegistry and Owner Reducer Contract Plan
Build target: AIDRPG Core MVP v0.1 / final-core architecture path
Purpose: Define the exact ReducerRegistry behavior, owner reducer contracts, accepted-result handoff, operation key ordering, dirty target creation, audit requirements, and reducer safety tests before individual reducer plans are written.
Status: Practical build document.
Follows: Build Chunk 11 — CanonValidator and Build Chunk 12 — Resolver and Owner-Specific Sanitizer Plan.
This document does not contain final script code.

This chunk exists because old versions repeatedly failed when multiple systems could mutate the same truth, when parser patches mutated state directly, or when late repair layers tried to fix already-corrupted state.

The reducer layer is the first layer allowed to commit gameplay state.

Only accepted CanonValidator results may reach reducers.

Each truth family must have exactly one reducer owner.

⸻

1. Reducer doctrine

The reducer doctrine is:

Parser detects.
ProposalBuilder structures.
CanonValidator decides eligibility.
ReducerRegistry routes.
OwnerReducers commit.
OperationLedger dedupes.
DirtyQueue marks mirrors.
AuditLogger explains.

Reducers are not parsers.

Reducers are not validators.

Reducers are not command renderers.

Reducers are not card writers.

Reducers only commit accepted, validated, owner-routed changes.

⸻

2. Why this chunk matters

Previous versions fell into patch loops because different layers could mutate truth:

parser directly added items
ability cleanup created abilities
command output was parsed as story
context reminders became state
Story Cards became canon
late patches repaired old bugs by overwriting state
multiple systems could update actors, scenes, cards, or abilities

This build stops that by enforcing reducer ownership.

If the InventoryReducer owns inventory, no other module directly adds items.

If the AbilityReducer owns abilities, no parser/sanitizer/card/context layer creates stable abilities.

If the PlaceReducer owns current location, weak place mentions cannot update state outside that path.

4. ReducerRegistry responsibilities

ReducerRegistry owns:

* receiving accepted validation results
* rejecting non-accepted results from commit path
* mapping family/eventType to owner reducer
* enforcing one-owner-per-truth-family
* invoking owner reducer apply functions
* handling reducer result objects
* coordinating operation key commit order policy
* coordinating dirty target creation through owner reducer result
* collecting reducer audit summaries
* fail-softing unknown reducer routes
* preventing reducer overlap

ReducerRegistry does not own:

* parsing text
* proposal construction
* canon validation
* target sanitization
* command rendering
* Story Card writing
* context generation
* cleanup deletion
* feature activation

⸻

5. Owner reducer responsibilities

Owner reducers own actual state mutation for their truth family.

Each owner reducer must:

* accept only accepted ValidationResults
* verify the required owner/family before commit
* check the operation key if repeat-sensitive
* mutate only its owned state bucket(s)
* preserve valid existing data
* create dirty targets for mirror/context updates
* record concise audit lines
* return a structured ReducerResult
* fail softly without corrupting unrelated state

Owner reducers must not:

* parse raw story text
* import Story Card prose
* read command output as story
* validate canon from scratch outside CanonValidator
* mutate another reducer’s bucket except through approved cross-bucket contract
* enable deferred systems
* create generated cards

8. ReducerResult schema

Every reducer returns a structured result.

ReducerResult {
  validationId: string,
  proposalId: string,
  family: string,
  eventType: string,
  ownerReducer: string,
  status: 'committed' | 'skipped_duplicate' | 'rejected_wrong_owner' | 'deferred' | 'no_op' | 'failed_softly',
  operationKey: string,
  operationKeyAdded: boolean,
  mutatedBuckets: string[],
  dirtyTargets: DirtyTarget[],
  auditLine: string,
  warnings: string[],
  errors: string[],
  notes: string[]
}

Reducers should never return raw undefined/null.

9. Accepted-result handoff contract

ReducerRegistry may process only:

ValidationResult.status = accepted
ValidationResult.canonAllowed = true
ValidationResult.reducerAllowed = true
ValidationResult.requiredReducer is known

Everything else must be excluded from the commit path:

rejected
pending
deferred
blocked
malformed
duplicate_skipped

These may be audited or displayed, but not committed.

12. Cross-bucket mutation policy

Some accepted events affect more than one bucket.

Examples:

reward payment -> quests + inventory currency
ability training -> abilities + maybe progression/statXP later
arrival -> places + scene actors/items cleanup later
quest completion -> quests + progression XP/reward readiness later
body recovery -> body + time/rest notes later

To avoid overlapping reducers, cross-bucket changes require explicit policy.

12.1 MVP preferred policy

For MVP, keep cross-bucket changes conservative.

A reducer may mutate only its primary bucket and return suggested follow-up dirty targets or follow-up proposals unless a cross-bucket contract exists.

12.2 Allowed MVP cross-bucket contracts

Allowed only when explicitly defined:

QuestReward accepted payment may call Inventory currency helper through RewardReducer contract, or be split into reward payment validation + inventory currency event.
PlaceReducer may update currentScene visibleItems/presentActors references but not actor permanent records unless ActorReducer validates.
BodyReducer may update body resources/status only, not progression.
AbilityReducer may record ability evidence only, not stat gain unless ProgressionReducer handles it.

12.3 Forbidden casual cross-bucket mutation

Forbidden:

InventoryReducer completing quests
AbilityReducer awarding XP
PlaceReducer creating persistent actors freely
ActorReducer changing current location
CardSync changing inventory
ContextBuilder changing anything
Cleanup resolving active quests

⸻

13. Operation key commit ordering

Repeat-sensitive reducer commits must use OperationLedger.

13.1 Standard commit order

Recommended MVP order:

1. Receive accepted ValidationResult.
2. Build or read operation key.
3. Check duplicate key.
4. If duplicate, return skipped_duplicate; do not mutate.
5. Apply state mutation.
6. Add operation key to correct ledger bucket.
7. Mark dirty targets.
8. Audit success.

13.2 If mutation succeeds but key add fails

This is a critical warning.

Reducer should:

* record warning/error
* avoid retry loops
* return committed with operationKeyAdded false and critical audit
* ReleaseCheck should warn/fail depending severity

13.3 If key is added before mutation

Avoid this in MVP unless rollback exists.

If key added first and mutation fails, effect may be permanently skipped.

MVP should generally mutate then add key, while keeping mutation simple and local.

13.4 Duplicate-sensitive key buckets

item pickup/transfer/consume/drop -> recent or permanent depending item
reward payment -> rewardKeys
XP/level/stat gains -> rewardKeys or permanent/progression keys
ability stabilization -> permanentKeys or ability-specific durable key
ability use evidence -> recentKeys unless durable evidence
card writes -> cardKeys
time/age advance -> permanent or recent depending event
startup import -> permanentKeys/startupOperationKeys
migration import/quarantine -> migrationOperationKeys/permanentKeys

15. Audit contract

Every reducer commit or skip must produce a concise audit line.

Examples:

Inventory committed: acquired red_healing_potion from Mara handoff.
Inventory skipped duplicate: item.acquire.red_healing_potion.mara.hash_abc already applied.
Ability evidence added: Ember Ward training intent recorded.
Place updated: current scene set to The Drunken Huntsman from confirmed arrival.
Reward skipped duplicate: quest.reward.clear_mill_wolves.old_bren.15_gold already paid.

Audit must not mutate gameplay state.

Audit must be capped.

Audit must not dump full raw output text.

⸻

16. Reducer fail-soft policy

If a reducer fails:

* do not crash the hook
* do not continue unsafe optional commits
* record runtime/reducer error
* return failed_softly ReducerResult
* preserve existing valid state
* do not reset the whole bucket
* do not enable fallback broad mutation

Reducer fail-soft must not become hidden repair logic.

No owner reducer, no mutation.
