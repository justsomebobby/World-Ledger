# AIDRPG Feature Implementation Wave Map v1

## Purpose

This document is the bridge from WorldLedger V0.17 Foundation Candidate to the full AIDRPG build. It prevents the project from restarting the original Design Bible Chunks 1–32/33 as blind manual testing sessions.

The original Design Bible Chunks remain the full design source. This roadmap converts them into controlled production waves with owners, gates, tests, and forbidden shortcuts.

## Current authority stack

1. Final Build Control Map v1 — old failures become owner/rule/test/release gates.
2. WorldLedger V0.17 — current foundation candidate and hook/export baseline.
3. Build Chunks 1–17 — implementation safety overlay and Code Pass 1 rules.
4. Gap Chunks A–G — old failure protections.
5. Regression Matrix / QA files — pass/fail authority.
6. Formula Appendix — progression/stat math authority.
7. Developer Spec / MVP Spec — intended implementation behavior.
8. Design Bible Chunks 1–32/33 — full game destination.
9. World Bible / Story Cards JSON — lore/reference source, not direct gameplay truth.
10. Old scripts and tester feedback — evidence only, not blind code source.

## Remaining production count

From V0.17 onward:

```text
24 production chunks
+ 1 final packaging/release chunk
= 25 total remaining production chunks
```

This is not 32 manual play/build sessions. It is a finite feature-wave implementation plan.

## Process required for every production chunk

Every production chunk must state:

```text
1. Exact goal.
2. Modules touched.
3. State fields added/changed.
4. Parser/proposal/validator changes.
5. Reducer changes.
6. Command/context/card changes.
7. Operation keys.
8. ReleaseCheck gates.
9. Regression tests.
10. Forbidden shortcuts.
11. Implementation order.
12. Pass/warn/fail criteria.
13. Handoff to the next chunk.
```

No production chunk may end with “just play and see what breaks.” Manual playtesting verifies feel; regression tests protect old failures.

## Final doctrine

```text
No blind 32-session rebuild.
No manual rediscovery loop.
No feature activation without owner/rule/test/gate.
No old patch pasted blindly.
No PASS on uncertainty.
Build the full game through controlled production waves.
```

# AIDRPG Production Chunk 02 — Command Surface and Player Setup Expansion

## Document status

Production sequence: 02 of 25.
Build target: WorldLedger V0.17.1 foundation accepted freeze.
Purpose: Improve command readability, setup inspection, player identity display, and disabled-system messaging without unsafe mutation commands.

## Doctrine

```text
Commands explain truth.
Commands do not create truth.
Setup inspects and confirms.
Setup does not overwrite locked identity.
Displays must separate confirmed, candidate, pending, visible, promised, and deferred states.
```

## Why this comes before gameplay expansion

If commands show visible items as owned, candidates as stable, promised rewards as paid, or travel intent as arrival, later testing becomes unreliable. This chunk makes command outputs honest before deeper systems build on them.

## Allowed changes

```text
CommandRouter
Command aliases
Command renderers
Help text
Version/build status display
Setup/startup inspection display
Sheet/status/inventory/abilities/quests/actors/location/time displays
State audit display
ReleaseCheck command honesty gates
Disabled command messages
```

Forbidden:

```text
manual mutation commands
admin mutation commands
feature activation commands
generated card commands
live card write commands
unsafe character creation mutation flow
```

## Setup philosophy

Allowed read-only setup commands:

```text
/startup /startupaudit /setup /setupcheck /sheet /version /foundationcheck
```

They may show what is known, unknown, locked, confirmed, or pending. They must not overwrite protected identity.

Controlled setup confirmation may only accept structured startup facts before gameplay lock. Post-lock identity changes require a future manual override spec.

Forbidden examples:

```text
/playername Bob mutates locked identity casually
/race Dragon instantly changes body logic
/setform Wolf overwrites true identity
/addlineage Angel-Demon grants powers
```

## Player identity display requirements

`/sheet` must separate:

```text
Confirmed identity
Current form
Body form / body type
Race/species/lineage
Origin / outsider status
Disguise / illusion / temporary presentation
Candidate or pending traits
Unknown fields
Deferred systems
```

True identity is not current form. Current form is not disguise. Disguise is not body truth. Candidate lineage is not confirmed lineage.

## Origin and world knowledge display

Do not assume human, native, chosen, central, powerful, or omniscient. Display:

```text
Origin: unknown / outsider / native / world-emerged / scenario-defined
World knowledge: limited unless discovered
Narrative role: not automatically center of reality
Integration: grows through action, recognition, and consequence
```

## Command output standard

Every command response must:

```text
start with [AIDRPG]
be clearly non-canon
avoid prose that looks like story output
avoid wording that EventScannerLite might treat as a completed event
avoid raw JSON dumps unless diagnostic mode asks
be capped for AI Dungeon context limits
```

Diagnostics should include: `No gameplay state was changed.`

## Shared command formatter

Add/verify helper responsibilities:

```text
prefix command output
standardize section headings
standardize empty-state lines
standardize confirmed/candidate/pending/deferred labels
standardize no-mutation footer
escape or avoid story-like lines
cap command length
```

## Command requirements

`/help` shows active commands, diagnostics, build checks, disabled categories, current stage, and where to start.

`/version` shows WorldLedger engine, AIDRPG project bridge, version, schema, stage, root key, foundation accepted/frozen status, release profile, safe/deferred flag summary.

`/sheet` separates confirmed identity, origin, current form, body truth, race/species, lineage, disguise/illusion, candidate/pending traits, protected fields, unknown fields.

`/status` separates resources, fatigue/exhaustion, active conditions, injuries, recovery/resolved conditions, death boundary, warnings.

`/inventory` separates owned/carried, equipped, stored, visible nearby, available loot, NPC custody, lost/consumed/destroyed history, currency, warnings.

`/abilities` separates stable, unstable, candidate, hints, failed/collapsed attempts, sealed/unavailable, recent evidence, warnings.

`/quests` separates active, offered/rumored, objectives, ready-to-turn-in, completed, failed/abandoned, promised rewards, paid rewards.

`/actors` separates present important actors, scene-only actors, persistent actors, absent/reference-only actors, witness memories, relationship notes.

`/location` separates current location, current scene, travel intent, nearby/visible references, route/interstitial references, known places.

`/time` displays current time text, turn/sequence if used, last accepted time advance, deadlines, pending/nonliteral claims, warnings. It never advances time.

## Disabled command messages

Forbidden commands must return safe disabled messages and no mutation:

```text
/additem /setlevel /payreward /completequest /giveability /teleport
/livecards /generatedcards /craft /buy /sell /reputation /domain
```

# 1. Chunk doctrine

```text
Mentioned is not learned.
Named is not mastered.
Tried is not stable.
Failed is not unlocked.
Pretended is not usable.
Quoted is not known.
Dreamed is not real mastery.
Training is evidence, not automatic mastery.
Output-only “You learned X” is not enough by default.
Only validated stabilization creates a stable ability.
```

Ability truth must be conservative, evidence-based, duplicate-safe, and explainable.

---

# 2. Why this chunk comes now

Production Chunk 05 made inventory reliable. Abilities come next because later combat, progression, race/lineage powers, spellcasting, cooldowns, failures, quest abilities, and world-threat interactions all depend on clean ability state.

If abilities are not safe now, later systems will repeatedly create junk powers, duplicate evidence, false mastery, and broken progression.

# 8. Ability status transition model

## Hint to candidate

Allowed when the ability is mentioned with plausible training/use relevance, the player trains toward it, or a teacher/source discusses it as a real technique. No stable mastery yet.

## Candidate to unstable

Allowed when repeated training evidence exists, first unstable manifestation/use success exists, or validator marks unstable/candidate manifestation.

## Candidate/unstable to stable

Allowed only when CanonValidator accepts `ability.stabilize_candidate` or equivalent.

Strong sources may include:

```text
validated startup structured ability
teacher/training culmination plus demonstration
successful controlled manifestation
validated source-grant/transformation event
future mini-spec source such as absorption/evolution when enabled
```

## Any status to sealed/unavailable

Allowed from direct validated sealing/unavailability event or setup marking. Sealed/unavailable does not delete history.

# 9. AbilityNameSanitizer depth

AbilityNameSanitizer must be owner-specific and must not leak into shared cleanup.

It must clean:

```text
I train Ember Ward to protect allies from heat -> Ember Ward
I practice Frost Step by moving across slick stones -> Frost Step
I drill Stoneguard until my stance holds under impact -> Stoneguard
I train Moonblade by practicing careful crescent cuts -> Moonblade
I refine Crimson Lotus Fang through repeated strikes -> Crimson Lotus Fang
```

It must preserve meaningful ability names:

```text
Shield Against Dawn
Step Across Stars
Song for the Dead
Blade of the North
Ward from Below
```

It must not create abilities from non-ability actions:

```text
I travel to the smithy -> no smithy ability
I inspect the old wooden door -> no door ability
I use the iron key on the cellar door -> no key/door ability
I ask Mara about Moonblade -> hint/reference only unless training/use context exists
```

# 11. Ability CanonValidator expansion

Accept training evidence only when:

```text
source is safe input intent or safe story output
local clause has clear training/practice/refinement intent
ability target is bound by AbilityNameSanitizer
not pretend-only
not quoted-only
not dream-only
not denied/no usable technique
not command/context/card/audit/debug source
```

Training normally creates or updates candidate/evidence. Training does not create stable mastery by default.

Accept use success evidence only when:

```text
safe story output confirms ability use or manifestation succeeded
ability target is bound
not dream/quote/pretend/metaphor only
not failed/collapsed/no effect
operation key not duplicate
```

Use success may add evidence and reliability, but it does not automatically stabilize unless a separate stabilize result is accepted.

Accept use failure evidence when:

```text
safe input/output states attempt/failure/collapse/no effect
ability target is bound
not command/context/card source
```

Failure evidence must not create stable mastery.

Accept stable ability only when:

```text
structured startup ability before lock
validated teacher/training culmination
successful controlled demonstration with stabilization wording
validated grant/source event
future enabled mini-spec event
```

Reject stable ability when:

```text
output-only unsupported “You learned X”
quoted instruction only
dream/vision only
pretend use
failed/collapsed/no effect
scroll/book/title only
rumor only
manual command output
context/card/audit/debug source
input attempt only with no output support
non-ability target
wrong sanitizer used
```

# 12. Critical old-failure rules

## Output-only learning rule

Example:

```text
You learned Moonblade.
```

Default result:

```text
pending or rejected unsupported learning claim
no stable ability
no direct AbilityReducer stable commit
```

It may become evidence only if surrounding context supports it through training arc, teacher confirmation, demonstration, startup, or source-grant.

## Failed ability rule

Examples:

```text
You attempt Void Lantern Veil, but it collapses.
Azure Dragon Step flickers and fails.
Your spell fizzles with no effect.
```

Expected:

```text
failure evidence recorded
status may remain candidate/unstable/failed_only
stable ability not created
```

## Pretend / quote / dream rules

```text
You pretend to use Azure Dragon Step. -> no real ability use
Mira says, "Use Hollow Star Palm." -> hint/reference only
In a dream, you master Star Chain. -> no real stable ability
```

# 15. AbilityReducer detailed behavior

```text

abilities.stable
```

Hint commit:

```text
create/update ability hint record

record evidence type hint
not make usable/stable
mark abilities/context dirty

```

Training commit:

```text
create/update ability record

increment trainingCount
record sourceOperationKey
mark abilities/context dirty

```

Use success commit:

```text
append use_success evidence

```

Use failure commit:

```text
append use_failure evidence
increment useCount and failureCount
set or keep status candidate/unstable/failed_only as appropriate
not create stable ability
mark abilities/context dirty
```

Stabilize commit:

```text
require validationResult.eventType = ability.stabilize_candidate or equivalent
check durable operation key
set status stable
add to stable list
remove from candidate/unstable display lists if needed
preserve evidence history
mark abilities/context dirty
audit high-importance line
```

Sealed/unavailable commit:

```text
set status sealed or unavailable
record reason
preserve evidence/history
mark abilities/context dirty
```

# AIDRPG Production Chunk 07 — Quest, Objective, Reward, and Promise/Payment Depth

## 0. Document status

**Document name:** AIDRPG Production Chunk 07 — Quest, Objective, Reward, and Promise/Payment Depth  
**Production sequence:** 07 of 25 remaining production chunks  
**Build target:** WorldLedger V0.17.6 ability-depth accepted build / AIDRPG Core MVP expansion path  
**Purpose:** Deepen quest records, objective states, quest offers, quest acceptance, objective progress, completion, reward promises, reward readiness, reward payment, and duplicate-safe reward behavior without rumor activation or promise/payment confusion.  
**Status:** Core gameplay-depth production chunk.  
**Follows:** Production Chunk 06 — Ability Candidate, Training, Use, Failure, and Stability Depth.  
**This document does not contain final script code.**

Production Chunk 07 exists because quest and reward handling is one of the most dangerous RPG automation areas.

Old systems often blurred:

```text
rumor
offer
accepted quest
active objective
objective progress
objective completion
ready to turn in
quest completion
promised reward
paid reward
duplicate paid reward
```

That cannot happen in the final system.

A quest must move through explicit states.

Rewards must be promised, ready, paid, denied, disputed, or duplicate-skipped with clear audit.

A promised reward is not currency.

A completed objective is not payment.

A command display is not reward collection.

```text
Rumor is not a quest.
Offer is not acceptance.

Completion is not payment.

Paid once means paid once.
Quest text is not inventory.
Command display is not reward collection.
```

Quest and reward truth must be stateful, duplicate-safe, and explainable.

Production Chunk 05 made inventory/currency safe.

# AIDRPG Production Chunk 08 — Actor Presence, Social Memory, Witnessing, and Relationship Depth

## 0. Document status

**Document name:** AIDRPG Production Chunk 08 — Actor Presence, Social Memory, Witnessing, and Relationship Depth  
**Production sequence:** 08 of 25 remaining production chunks  
**Build target:** WorldLedger V0.17.7 quest/reward-depth accepted build / AIDRPG Core MVP expansion path  
**Purpose:** Deepen actor records, actor presence, scene-only actors, reference-only actors, absent actors, witness memory, direct-informed memory, relationship evidence, and social continuity without false presence, duplicate actors, or unsafe reputation automation.  
**Status:** Core gameplay-depth production chunk.  
**Follows:** Production Chunk 07 — Quest, Objective, Reward, and Promise/Payment Depth.  
**This document does not contain final script code.**

Production Chunk 08 exists because actors are where AI Dungeon continuity can either feel alive or become badly corrupted. Old rough attempts showed the same risks repeatedly: duplicate actors from titles/names, absent actors treated as present, reference-only names treated as scene participants, private witness memory becoming global reputation, generic guards becoming permanent major NPCs, command/card/context text creating memories, and actor harm being applied to a statue, painting, title, or training dummy named after someone.

This chunk turns actors into structured, useful, bounded state. The goal is not full reputation, faction, romance, party, summon, or NPC combat automation yet. The goal is reliable actor presence, source-bound memory, and relationship evidence that future systems can safely build on.

# AIDRPG Production Chunk 09 — Place, Travel, Time, Scene, and Deadline Depth

## 0. Document status

**Document name:** AIDRPG Production Chunk 09 — Place, Travel, Time, Scene, and Deadline Depth  
**Production sequence:** 09 of 25 remaining production chunks  
**Build target:** WorldLedger V0.17.8 actor/social-depth accepted build / AIDRPG Core MVP expansion path  
**Purpose:** Deepen current location, current scene, travel intent, visible/nearby references, route/interstitial handling, time passage, time claims, deadlines, and age-safety behavior without weak mention overwrites or fake time/age canon.  
**Status:** Core gameplay-depth production chunk.  
**Follows:** Production Chunk 08 — Actor Presence, Social Memory, Witnessing, and Relationship Depth.  
**This document does not contain final script code.**

Production Chunk 09 exists because place and time continuity determine whether AI Dungeon gameplay feels like a real world or a constantly-resetting hallucination.

Old attempts often failed by:

```text
weak place mentions overwriting current location
visible places becoming arrival
travel intent becoming arrival
roads/path/interstitial phrases beating named destinations
context/card/command location text becoming canon
quoted or narrated time skips changing age
long time passage duplicating on output replay
deadlines being forgotten or completed from vague text
scene actors/items not matching current scene after movement
```

This chunk makes location and time persistent, conservative, duplicate-safe, and readable. The goal is not full world simulation yet. The goal is to make current place, current scene, intended travel, known references, time passage, and deadlines safe enough for later world bible, region, faction, encounter, and long-run persistence systems.

```text

```

Place and time truth must be local, source-aware, duplicate-safe, and conservative.

# 19. Place CanonValidator expansion

Accept travel intent when safe input/output says the player heads/goes/travels toward a destination but has not arrived. Result: update travelIntent, currentLocation unchanged.

Accept strong arrival when safe output directly confirms arrival/entry/entering/reaching destination, target is bound, and it is not command/context/card source, dream/quote only, hypothetical, or merely visible/nearby. Result: update currentLocation/currentScene and clear/mark matching travelIntent.

Accept scene confirmation when safe output confirms current scene/location details and target matches current place or is strong current-scene phrase. Result: update scene/confirm location without overwriting from weak reference.

Accept weak reference when safe source mentions visible/nearby/known/background place with no direct arrival. Result: reference record only.

---

# 20. Time CanonValidator expansion

Accept time advance when safe output directly narrates literal time passage, not quote/dream/metaphor/hypothetical/planning, not command/context/card, and operation key is unique.

Reject or pending when time wording is quoted, storytelling/narration practice, metaphorical, planning intent, hypothetical, prophecy, card/context/command text, or dream/vision.

Examples to reject or keep pending:

```text
You say, "Twenty years pass."
You feel like years pass.
In a dream, a century passes.
If a week passed, the town would change.
[AIDRPG] Time: three days passed.
```

Exact age update requires a stricter policy. Default safe result for long passage is accepted/pending time advance with age update pending/deferred unless age policy is active.

**Production sequence:** 10 of 25 remaining production chunks

