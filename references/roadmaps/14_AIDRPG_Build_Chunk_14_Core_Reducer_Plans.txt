AIDRPG Build Chunk 14 — Core Reducer Plans

0. Document status

Document name: AIDRPG Build Chunk 14 — Core Reducer Plans: Inventory, Ability, Body, Quest/Reward, Actor, Place/Scene, Time, Progression
Build target: AIDRPG Core MVP v0.1 / final-core architecture path
Purpose: Define exact behavior for the current-stage owner reducers before context, cards, cleanup, releasecheck, and code-pass planning.
Status: Practical build document.
Follows: Build Chunk 13 — ReducerRegistry and Owner Reducer Contract Plan.
This document does not contain final script code.

This chunk exists because Build Chunk 13 locked reducer ownership, but each reducer still needs exact behavior.

A reducer is where accepted canon becomes state.

That means this layer must be precise.

Reducers are not allowed to guess.

Reducers do not parse raw story text.

Reducers do not validate canon from scratch.

Reducers only apply accepted validation results from CanonValidator.

⸻

1. Core reducer doctrine

Accepted validation result in.
Owned state mutation only.
Operation key checked.
Dirty targets marked.
Audit written.
No extra guessing.

Every reducer must obey:

No accepted validation, no mutation.
No ownership, no mutation.
No duplicate-safe key for repeat-sensitive event, no repeat-safe commit.
No dirty target, no mirror/context update.
No audit, no trust.

3. Universal reducer input contract

Every reducer receives a ValidationResult from CanonValidator.

Required input:

status = accepted
canonAllowed = true
reducerAllowed = true
requiredReducer matches reducer
source
localClause
safety flags
targetKey
targetDisplayName
operationKey or operation suggestion when repeat-sensitive
dirtyFamiliesIfAccepted
reasons

If any required field is missing:

return failed_softly or rejected_wrong_owner
mutate nothing
audit warning

⸻

4. Universal reducer output contract

Every reducer returns a ReducerResult.

ReducerResult {
  validationId,
  proposalId,
  family,
  eventType,
  ownerReducer,
  status,
  operationKey,
  operationKeyAdded,
  mutatedBuckets,
  dirtyTargets,
  auditLine,
  warnings,
  errors,
  notes
}

No reducer may return raw undefined/null.

5. Universal duplicate policy

Repeat-sensitive reducer events must check OperationLedger before mutation.

5.1 Standard repeat-sensitive flow

1. Build/read operation key.
2. Check duplicate.
3. If duplicate: no mutation, return skipped_duplicate.
4. If not duplicate: mutate owned bucket.
5. Add operation key.
6. Mark dirty targets.
7. Audit.

5.2 Repeat-sensitive event families

item acquisition
item transfer
item consumption
item destruction
currency payment
reward payment
XP gain
stat gain
level up
time advance
age update
ability stabilization
durable ability evidence
quest objective completion
quest completion
actor death/status change
location arrival
startup import
migration import/quarantine
card create/update

6. Universal dirty target policy

Reducers do not write context or Story Cards directly.

Reducers mark dirty targets.

Common dirty mappings:

inventory -> inventory_equipment, current_location, context
abilities -> abilities, context
body -> body_status, context
quests -> quest_log, context
actors -> social_memory, current_location, context
places -> current_location, context
time -> current_location, quest_log, context
progression -> player_sheet, context

Dirty targets are not gameplay truth.

8. InventoryReducer detailed plan

8.1 Owned buckets

InventoryReducer owns:

inventory.items
inventory.equipped
inventory.currency only through explicit accepted currency/reward contract
inventory.sceneItems
inventory item access/custody state
inventory.inventoryWarnings

8.2 Accepted event types

InventoryReducer may handle:

inventory.acquire_candidate
inventory.handoff_candidate
inventory.transfer_candidate
inventory.drop_candidate
inventory.lose_candidate
inventory.consume_candidate
inventory.destroy_candidate
inventory.visible_candidate as scene item only
inventory.available_loot_candidate as scene item only
inventory.equip_candidate later if accepted
inventory.unequip_candidate later if accepted
currency.gain_candidate only through explicit reward/currency validation
currency.spend_candidate deferred until economy spec

8.3 Inventory acquisition behavior

For accepted acquisition/handoff:

1. Confirm accepted validation result.
2. Confirm item target key/display name.
3. Confirm not visible-only/available-only/denied/revoked/dream/quote/abstract.
4. Check item acquisition operation key.
5. If duplicate, skip.
6. Add item or increase quantity according to unique/stack policy.
7. Set accessState = held unless equipped/stored explicitly validated.
8. Set owner = player and custody = player.
9. Add sourceEventKey/createdTurn.
10. Mark inventory_equipment and context dirty.
11. Audit.

8.4 Scene item behavior

Visible and available-loot are not owned inventory.

Accepted visible/available scene events go to:

inventory.sceneItems

not:

inventory.items

Scene item access states:

visible
available_loot
inaccessible

8.5 Custody behavior

If item is in NPC/place custody:

accessState = npc_custody or inaccessible
custody = actor/place/unknown
custodyId = resolved target if known

InventoryReducer must not transfer custody unless validation result is an accepted transfer/handoff.

8.6 Drop/loss/consume/destroy behavior

Accepted events update accessState rather than deleting records when possible.

dropped -> scene item or accessState lost/stored depending context
lost -> accessState lost
consumed -> accessState consumed and quantity decreases
destroyed -> accessState destroyed
sold -> deferred until economy spec unless manually validated later

Do not erase unique item history unless cleanup policy later allows archival.

8.7 Currency behavior

Currency may change only from accepted currency/reward payment event.

Reward promise does not change currency.

Economy buy/sell/spend is deferred.

8.8 Inventory operation keys

Suggested keys:

item.acquire.<itemKey>.<sourceOrScene>.<clauseHash>
item.handoff.<itemKey>.<fromActor>.<toPlayer>.<clauseHash>
item.transfer.<itemKey>.<from>.<to>.<clauseHash>
item.consume.<itemKey>.<clauseHash>
item.destroy.<itemKey>.<clauseHash>
item.drop.<itemKey>.<clauseHash>
currency.gain.<amount>.<sourceKey>.<clauseHash>

8.9 Inventory old-failure protections

InventoryReducer must never acquire items from:

denied acquisition
failed grab
revoked handoff
abstract item idea/concept/title
quoted instruction
NPC says take it without actual transfer
dream/vision handoff
visible-only item
available loot before acquisition
command output
context text
Story Card text

CanonValidator should already reject those, but InventoryReducer must reject if such flags slip through.

8.10 Inventory tests

Accepted red healing potion handoff -> item held by player
Duplicate red healing potion handoff -> one item or one quantity change only
Visible silver ring -> sceneItems only, not inventory.items
Goblin drops rusty dagger -> available_loot scene item, not owned
Reward promise 15 gold -> no currency
Accepted reward payment 15 gold -> currency +15 once
Denied key result accidentally routed -> reducer rejects / no key
Command output item accidentally routed -> reducer rejects / no item

9.1 Owned buckets

9.2 Accepted event types

9.3 Ability status model

Ability statuses:

unknown
hint
candidate
unstable
stable
sealed
unavailable

Rules:

candidate is not stable
hint is not usable
failed evidence does not stabilize
output-only claim does not stabilize by default
training evidence may create/update candidate
stable requires validator-approved source or repeated/tracked mastery condition

9.4 Training behavior

Accepted training:

1. Resolve ability key.
2. Check duplicate durable training key if needed.
3. If ability exists, append/update evidence.
4. If ability missing, create candidate record.
5. Set status candidate or unstable, not stable, unless validation says stabilize.
6. Record evidence type training.
7. Mark abilities and context dirty.
8. Audit.

9.5 Use success behavior

Accepted use success may:

append success evidence
update reliability
update lastUsedTurn
apply cooldown/cost only if validated and resource system active

It must not create stable mastery automatically unless validator event type is stabilize and conditions are met.

9.6 Use failure behavior

Accepted failure may:

append failure evidence
lower reliability
keep as candidate/unstable
record no effect/fizzle/collapse notes

It must not create stable ability.

9.7 Stability behavior

Stable ability creation requires explicit accepted stabilize event.

Allowed sources may include:

startup structured ability before lock
teacher/training culmination
successful controlled demonstration
validated transformation/grant
future absorption/evolution spec when enabled

9.8 Ability operation keys

ability.train.<abilityKey>.<clauseHash>
ability.evidence.<abilityKey>.<evidenceKind>.<clauseHash>
ability.use.<abilityKey>.<eventKind>.<outputHash>
ability.stabilize.<abilityKey>.<sourceKey>
ability.seal.<abilityKey>.<sourceKey>

9.9 Ability old-failure protections

AbilityReducer must reject if routed with flags:

quoted instruction only
pretend use
failed/no usable technique as stable
output-only learned claim as stable
non-ability object/travel/inspect target
wrong sanitizer used

9.10 Ability tests

I train Ember Ward to protect allies -> candidate/evidence Ember Ward
I practice Frost Step by moving -> candidate/evidence Frost Step
You learned Moonblade -> no stable ability unless validator approved stabilize
Void Lantern Veil collapses -> failure evidence, no stable
Mira says "Use Hollow Star Palm" -> no stable ability
Repeated Ember Ward use -> deduped evidence, no spam

10.1 Owned buckets

body.trait_loss_candidate only if validated

10.3 Status behavior

Accepted status gain:

1. Resolve condition/status key.
2. Check duplicate if durable/repeat-sensitive.
3. Add or update condition record.
4. Set severity from validation.
5. Set status active.
6. Mark body_status and context dirty.
7. Audit.

Accepted status loss/recovery:

update condition status to resolved/healing/fading
or remove/compact only through cleanup later

10.4 Fatigue/exhaustion behavior

Rules:

fatigued/worn out -> fatigue tired or condition fatigued
exhausted/collapsed/drained completely -> fatigue exhausted/collapsed if validated
mild fatigue does not auto-upgrade to exhausted

10.5 Injury behavior

Accepted injury creates or updates InjuryRecord.

Fields:

injuryId
name
location
severity
status
sourceEventKey
createdTurn
notes

10.6 Resource behavior

Accepted resource change may update HP/MP/EP.

Rules:

clamp current between 0 and max
do not alter max unless max-change validated
state repair clamping is not healing
resource state candidate like exhausted may set EP current low/0 only if validator approved numeric/state rule

10.7 Death boundary behavior

DeathBoundary changes are high-risk.

Allowed values:

alive
unconscious
dying
dead
captured
unknown

Rules:

rumor death rejected before reducer
quote death rejected before reducer
dream death rejected before reducer
metaphor dead tired rejected before reducer
nonfatal hostile act cannot set dead

If death candidate reaches reducer with unsafe flags, reject/fail softly.

10.8 Body operation keys

body.status.add.<statusKey>.<clauseHash>
body.status.resolve.<statusKey>.<clauseHash>
body.injury.<injuryKey>.<clauseHash>
body.resource.<resource>.<deltaOrState>.<clauseHash>
body.deathboundary.<status>.<clauseHash>

10.9 Body tests

exhausted by climb -> fatigue exhausted/condition exhausted visible
fatigued and worn out -> fatigue tired/fatigued, not exhausted
bleeding stops -> bleeding resolved
Mara says "you are dead" -> reducer not called or rejects
People say you died -> no deathBoundary change
wolf bite arm -> injury active

Accepted offer:

Accepted acceptance:

Accepted objective progress:

update objective progressCurrent/status

Accepted objective complete:

11.6 Reward promise behavior

Accepted reward promise:

set reward.status = promised

11.7 Reward payment behavior

Accepted reward payment:

Preferred design:

Alternative safer shell:

QuestReducer marks reward ready/paid status only; separate accepted inventory currency result must add currency.

The final code pass must choose one policy and test it.

In either case:

reward key must prevent duplicate payment
promise does not pay
objective completion does not pay
command /quests display does not pay

16. Cross-reducer contracts for MVP

The final code must choose exact cross-reducer policy before implementing reward/payment and quest/XP.

16.1 Reward payment policy options

Option A — Split result policy

CanonValidator emits two accepted results:

reward.payment_candidate -> QuestReducer updates reward paid
currency.gain_candidate -> InventoryReducer adds currency

Both share a related reward key and must not duplicate.

Option B — Reward contract helper policy

QuestReducer handles reward payment and calls a narrow InventoryCurrencyHelper.

This is more complex and can blur ownership.

16.2 Recommended MVP choice

Use Option A where possible:

one accepted result per owner bucket

This preserves one-owner-per-truth-family.

16.3 Quest XP policy

Quest completion should not directly award XP unless separate ProgressionReducer result exists.

16.4 Place actor cleanup policy

PlaceReducer should not delete or promote actors.

Scene actor expiration belongs to CleanupManagerLite or ActorReducer with explicit scene-change event.
