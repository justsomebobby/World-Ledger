AIDRPG Build Chunk 10 — EventProposal, Local Clause Binding, and ProposalBuilder Plan

0. Document status

Document name: AIDRPG Build Chunk 10 — EventProposal, Local Clause Binding, and ProposalBuilder Plan
Build target: AIDRPG Core MVP v0.1 / final-core architecture path
Purpose: Define the exact EventProposal schema, local clause binding rules, target binding rules, operation key suggestions, and ProposalBuilder behavior before CanonValidator and reducers are planned.
Status: Practical build document.
Follows: AIDRPG Final Build Control Map v1 and Build Chunk 9 — EventScannerLite Parser Shell Plan.
This document does not contain final script code.

This chunk exists because old versions repeatedly failed when raw parser detections were treated too close to truth.

The parser can notice a phrase.

The proposal layer must preserve what was noticed, where it was noticed, what local clause it came from, what safety flags were present, what target it appears to affect, and which owner system should judge it next.

A proposal is not canon.

A proposal is not a reducer commit.

A proposal is structured evidence waiting for CanonValidator.

⸻

1. Chunk 10 doctrine

The doctrine is:

ParserHits are observations.
EventProposals are structured claims.
CanonValidator decides eligibility.
Reducers commit truth.

The ProposalBuilder must never mutate gameplay state.

It must never decide final canon.

It must never bypass CanonValidator.

Its job is to make the dangerous middle layer exact enough that validators and reducers do not guess.

⸻

2. Why this chunk matters

Old versions had failures where positive words were enough to create state:

You decide not to take the key.
You try to grab the key, but the goblin snatches it away.
You pick up the idea of a brass key.
Mara says, "Take the key."
In a dream, you receive the Crown of Dawn.
You learned Moonblade.
The scroll title says "You learned Crimson Lotus Fang," but you learn nothing.
The road to the chapel is visible from the market lane.
"Twenty years pass," you say while practicing narration.

The parser may detect item, ability, place, or time language in those examples.

The proposal layer must preserve enough local evidence so CanonValidator can reject the false outcome.

Without local clause binding and target binding, the validator is forced to guess.

4. ProposalBuilder responsibilities

ProposalBuilder owns:

* converting ParserHits into EventProposals
* preserving source hook
* preserving local clause text
* preserving safety flags
* identifying proposed event family
* identifying proposed event type
* creating target-binding candidates
* assigning owner module hint
* assigning preliminary truth status
* assigning preliminary confidence
* suggesting operation keys
* assigning proposal risk flags
* capping proposals
* auditing proposal summaries

ProposalBuilder does not own:

* canon approval
* gameplay mutation
* inventory ownership
* ability stability
* quest activation
* reward payment
* actor promotion
* location update
* time advance
* card writing
* context mutation

6. EventProposal core schema

Every EventProposal must use a consistent schema.

EventProposal {
  proposalId: string,
  source: ProposalSource,
  family: string,
  eventType: string,
  ownerModule: string,
  localClause: LocalClauseBinding,
  target: TargetBinding,
  secondaryTargets: TargetBinding[],
  safety: SafetyFlagSet,
  evidence: ProposalEvidence,
  proposedChange: ProposedChangeSummary,
  operation: OperationSuggestion,
  confidence: number,
  truthStatus: string,
  riskFlags: string[],
  validatorRequired: boolean,
  reducerRequired: boolean,
  status: 'proposed' | 'malformed' | 'blocked_prevalidation' | 'deferred',
  proposalNotes: string[]
}

No proposal should be reduced directly.

All proposals require CanonValidator unless explicitly marked malformed and discarded.

7. ProposalSource schema

ProposalSource {
  sourceHook: 'input' | 'output' | 'manual' | 'migration' | 'setup',
  parserHitId: string,
  inputHash: string,
  outputHash: string,
  textHash: string,
  turn: number,
  commandSuppressed: boolean,
  duplicateOutput: boolean,
  nonCanonSource: boolean,
  sourceLabel: string
}

7.1 Required source rule

If source is command, context, story card, debug, audit, help, releasecheck, or unknown non-canon source, ProposalBuilder must not create a gameplay proposal.

The parser should already reject those sources, but ProposalBuilder must treat this as a second safety layer.

7.2 Input source rule

Input proposals are intent/attempt proposals only unless they come from an explicit startup/setup/manual-confirmed path.

Normal player input does not create completed success.

7.3 Output source rule

Output proposals may describe possible completed consequences, but they are still not canon.

⸻

8. LocalClauseBinding schema

Local clause binding is required for every proposal.

LocalClauseBinding {
  fullWindowPreview: string,
  localClauseText: string,
  localClauseHash: string,
  clauseIndex: number,
  sentenceIndex: number,
  beforeTextPreview: string,
  afterTextPreview: string,
  matchedText: string,
  matchedTextHash: string,
  clauseRole: 'main' | 'subordinate' | 'quoted' | 'conditional' | 'unknown',
  denialScope: string,
  revocationScope: string,
  targetScope: string,
  notes: string[]
}

8.1 Why local clause binding exists

Local clause binding prevents broad false decisions.

Example:

Mira refuses to give you the jeweled crown, but she hands you the red healing potion.

The proposal layer must create separate local target proposals:

crown -> local clause has refusal/denial
red healing potion -> local clause has handoff confirmation

If it produces one broad proposal for the whole sentence, the validator cannot safely decide.

⸻

9. TargetBinding schema

Every proposal must bind a target or explicitly state that target is unknown.

TargetBinding {
  targetFamily: 'item' | 'ability' | 'quest' | 'reward' | 'actor' | 'place' | 'time' | 'body' | 'status' | 'progression' | 'card' | 'unknown',
  rawTargetText: string,
  cleanedTargetText: string,
  canonicalKey: string,
  displayName: string,
  targetId: string,
  targetStatus: 'known' | 'candidate' | 'new_candidate' | 'ambiguous' | 'generic' | 'reference_only' | 'unknown',
  targetConfidence: number,
  sanitizerUsed: string,
  resolverNotes: string[]
}

9.1 Owner-specific sanitizer rule

TargetBinding must use the correct sanitizer family.

Examples:

AbilityNameSanitizer for ability targets
ItemNameSanitizer for item targets
PlaceNameSanitizer for place targets
ActorNameSanitizer for actor targets
QuestObjectiveSanitizer for quest/objective targets
CardNameSanitizer for card targets

Shared cleaners may normalize spacing and punctuation only.

They must not perform destructive family-specific stripping.

Every proposal must carry all parser safety flags forward.

SafetyFlagSet {
  negated: boolean,
  hypothetical: boolean,
  quotedSpeech: boolean,
  dreamOrVision: boolean,
  rumorOrClaim: boolean,
  failedOrRevoked: boolean,
  conditional: boolean,
  futureIntent: boolean,
  attemptOnly: boolean,
  commandOutput: boolean,
  contextText: boolean,
  storyCardText: boolean,
  debugOrAuditText: boolean,
  abstractOrMetaphorical: boolean,

10.1 Safety flags are sticky

ProposalBuilder may add safety flags.

If a hit was dream/vision, quoted, negated, failed, or hypothetical, the proposal must carry that forward.

12. ProposedChangeSummary schema

The proposed change summary should describe what would happen if CanonValidator and owner reducer accepted it.

ProposedChangeSummary {
  action: string,
  targetFamily: string,
  targetKey: string,
  targetDisplayName: string,
  quantity: number,
  direction: 'gain' | 'loss' | 'update' | 'resolve' | 'observe' | 'none' | 'unknown',
  currentStateHint: string,
  proposedStateHint: string,
  reversible: boolean,
  repeatSensitive: boolean,
  dirtyFamiliesIfAccepted: string[],
  notes: string[]
}

ProposalBuilder does not apply this change.

It only describes it.

13. OperationSuggestion schema

Operation suggestions help later validators/reducers/ledger create stable dedupe keys.

OperationSuggestion {
  suggestedKey: string,
  keyFamily: 'recent' | 'permanent' | 'reward' | 'card' | 'sourceUse' | 'none',
  repeatSensitive: boolean,
  durable: boolean,
  reason: string,
  requiredBeforeCommit: boolean,
  notes: string[]
}

13.1 Key suggestion rule

ProposalBuilder may suggest a key.

OperationLedger commits keys only after validation/reducer flow approves or skips according to owner policy.

ProposalBuilder must not add ledger keys for gameplay effects by itself.

15.2 Inventory target binding

16. Ability proposal rules

Ability proposals must distinguish training, attempt, manifestation, failure, stability, and mention.

16.1 Ability proposal event types

ability.train_intent

16.2 Ability name binding

Ability proposals must use AbilityNameSanitizer.

Examples:

I train Ember Ward to protect allies from heat -> Ember Ward
I practice Frost Step by moving across slick stones -> Frost Step
I drill Stoneguard until my stance holds under impact -> Stoneguard
I train Moonblade by practicing careful crescent cuts -> Moonblade

16.3 Explicit training priority

If the local clause begins with:

train/practice/drill/work on/refine/meditate on/spar with + named phrase

then the proposal family is ability training even if purpose words include:

protect/shield/defend/against/for/from

16.4 Output-only ability learning safety

Output-only learning claims must be proposed as risky, not canon-ready.

Examples:

You learned Moonblade.
You unlocked Star Chain.
New skill: Mirror Guard.

Proposal type:

ability.output_only_learning_claim

CanonValidator will normally reject or downgrade unless supported by training/source context.

16.5 Blocked ability proposal cases

quoted "Use Hollow Star Palm"
pretend to use Azure Dragon Step
attempt Void Lantern Veil, but it collapses
scroll title says "you learned X" but learn nothing
do not know X
no usable technique remains
X fizzles
X cannot manifest

16.6 Ability operation key suggestions

ability.evidence.<abilityKey>.<evidenceKind>.<clauseHash>

25. Proposal status meanings

proposed

Means the proposal is structurally valid and needs CanonValidator.

malformed

Means the parser hit lacked necessary structure and should be audited/skipped.

blocked_prevalidation

Means source was non-canon or proposal is obviously impossible before validation.

deferred

Means event belongs to a disabled system such as economy, crafting, investigation, domain, generated cards, or advanced combat.

⸻

26. Malformed hit handling

ProposalBuilder must not crash on malformed ParserHits.

If a hit is missing required fields:

* create no gameplay proposal
* record rejected/malformed summary
* audit if useful
* continue processing other hits

Examples of malformed hits:

missing sourceHook
missing eventFamily
no local clause or matched text
unsafe source
no target for target-required family

⸻

27. Proposal caps

Recommended caps:

maxProposalsPerOutput = 20
maxProposalsPerInput = 10
maxMalformedHitAuditsPerTurn = 5
maxProposalAuditLinesPerTurn = 10
maxSecondaryTargetsPerProposal = 5
maxLocalClausePreviewLength = 180

If proposals exceed caps:

* keep current-stage mandatory families first
* prefer high-confidence, direct-output consequences
* preserve rejection/audit for skipped high-risk items if possible
* do not crash
* do not scan history to compensate

⸻

28. Proposal audit format

Proposal audit should be concise.

Example:

Proposal: inventory.acquire_candidate target=red_healing_potion source=output risk=DUPLICATE_SENSITIVE confidence=0.74.

Example:

Proposal blocked prevalidation: inventory.acquire_candidate target=jeweled_crown reason=local clause refusal.

Example:

Proposal: ability.train_candidate target=ember_ward source=input risk=INPUT_ATTEMPT_ONLY confidence=0.62.

Do not dump full raw text.

⸻

29. ProposalBuilder and CanonValidator handoff

Every structurally valid proposal must go to CanonValidator.

Handoff object:

{
  proposals: EventProposal[],
  malformedHits: RejectedHitSummary[],
  skippedBySource: number,
  skippedByCap: number,
  auditSummary: string[]
}

CanonValidator must receive all safety flags, local clause binding, target binding, proposed change summary, and operation suggestion.

⸻

30. ProposalBuilder and OperationLedger relationship

ProposalBuilder may suggest keys.

It must not commit keys for gameplay effects.

Exceptions:

* source-use audit keys may be handled by Runtime or OperationLedger outside ProposalBuilder
* ProposalBuilder should not add permanent/reward/card keys

Reducers or commit controller later add keys after validation according to owner policy.

33. Required proposal tests

BC10-001 — ParserHit does not mutate state

Given ParserHit for:

You pick up the rusty dagger.

* EventProposal may be created
