AIDRPG Build Chunk 16 — ReleaseCheck and Regression Matrix Lock

0. Document status

Document name: AIDRPG Build Chunk 16 — ReleaseCheck and Regression Matrix Lock
Build target: AIDRPG Core MVP v0.1 / final-core architecture path
Purpose: Define the exact ReleaseCheck gate system, regression matrix, old-failure coverage gates, deferred-system gates, and no-code-until-covered policy before Foundation Code Pass 1 planning.
Status: Practical build document.
Follows: Build Chunk 15 — ContextBuilder, CardSyncLite, Migration, DirtyQueue, and Cleanup Integration Plan.
This document does not contain final script code.

This chunk exists because previous AIDRPG builds passed normal checks while still failing under old patch-loop problems, adversarial wording, command/card/context contamination, repeated effects, and cross-system regressions.

A final build cannot rely on hope.

ReleaseCheck and the regression matrix are the gate that prevents old failures from being forgotten.

⸻

1. ReleaseCheck doctrine

If a current-stage system is active, ReleaseCheck must know how to inspect it.
If a known old failure is current-stage relevant, ReleaseCheck must know whether it is covered.
If a system is deferred, ReleaseCheck must verify it is actually disabled.
If a reducer can mutate state, ReleaseCheck must verify its owner boundary.
If a parser can detect events, ReleaseCheck must verify it cannot commit them.
If a support layer can mirror or summarize, ReleaseCheck must verify it cannot invent canon.

ReleaseCheck is not decoration.

ReleaseCheck is the final planning and runtime safety gate.

⸻

2. Regression matrix doctrine

Every known failure becomes a test.
Every old patch goal becomes a regression requirement.
Every new design decision gets a proof case.
Every deferred system gets a disabled-behavior test.
Every active reducer gets commit, duplicate, no-op, and fail-soft tests.
Every non-canon source gets a rejection test.

The regression matrix is not just for future QA.

It tells the script builder exactly what must not break.

4. ReleaseCheck result statuses

ReleaseCheck returns one of four top-level results.

PASS
WARN
FAIL
BLOCKED

4.1 PASS

All current-stage mandatory gates pass.

Deferred systems are disabled safely.

Known current-stage failure classes have owner/rule/test coverage.

4.2 WARN

Current-stage core can operate, but non-blocking limitations exist.

Allowed WARN examples:

parser family detection is limited but honestly shell-only
CardSync live writes are dry-run only
progression formula automation is shell/deferred
WorldStructure deferred
reputation automation deferred

WARN must not hide unsafe active behavior.

4.3 FAIL

A current-stage safety requirement is broken.

Examples:

command output can be parsed as story
context can mutate gameplay
generated cards enabled in MVP
parser can write inventory directly
CanonValidator missing for active proposals
rejected results can reach reducers

FAIL means do not ship / do not proceed to code-finalization.

4.4 BLOCKED

A requested active system lacks required spec, tests, or gates.

Examples:

crafting enabled without Crafting Mini-Spec
economy enabled without Transaction Ledger Mini-Spec
generated cards enabled without Generated CardSync Beta Spec
manual mutation commands enabled without Manual Override Spec

BLOCKED means the system cannot be activated in the current build.

⸻

5. ReleaseCheck record schema

ReleaseCheck should produce a structured record.

ReleaseCheckRecord {
  turn: number,
  result: 'PASS' | 'WARN' | 'FAIL' | 'BLOCKED',
  buildName: string,
  buildVersion: string,
  schemaVersion: string,
  checkedAtTurn: number,
  passCount: number,
  warningCount: number,
  failureCount: number,
  blockerCount: number,
  passes: ReleaseCheckLine[],
  warnings: ReleaseCheckLine[],
  failures: ReleaseCheckLine[],
  blockers: ReleaseCheckLine[],
  deferredSystems: ReleaseCheckLine[],
  knownFailureCoverage: KnownFailureCoverageSummary[],
  notes: string[]
}

5.1 ReleaseCheckLine schema

ReleaseCheckLine {
  gateId: string,
  gateName: string,
  status: 'PASS' | 'WARN' | 'FAIL' | 'BLOCKED',
  severity: 'info' | 'low' | 'medium' | 'high' | 'critical',
  message: string,
  ownerModule: string,
  relatedFailureIds: string[],
  requiredAction: string
}

5.2 KnownFailureCoverageSummary schema

KnownFailureCoverageSummary {
  failureId: string,
  title: string,
  currentStage: boolean,
  ownerModule: string,
  ruleDefined: boolean,
  testDefined: boolean,
  releaseGateDefined: boolean,
  status: 'covered' | 'partial' | 'missing' | 'deferred'
}

45. ReleaseCheck must not fake readiness

ReleaseCheck must not return PASS if:

it cannot inspect a mandatory gate
mandatory gate is shell-only but active system depends on it
known failure is current-stage and has no test
unsafe feature flag is true
reducer ownership is unknown
command output suppression is missing
ContextBuilder can mutate state
CardSync generated cards are enabled

If uncertain, use WARN or FAIL depending current-stage risk.

Do not use PASS for uncertainty.
