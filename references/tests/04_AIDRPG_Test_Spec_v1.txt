AIDRPG Test Spec v1

0. Document status

Document name: AIDRPG Test Spec v1
Purpose: Define the required tests for AIDRPG Core MVP v0.1.
Status: Required pre-code testing specification.
Applies to: AIDRPG MVP Build Spec v1.
Next step after this: Formula Appendix v1, then Script v0.1 Phase 1.

This document defines the exact tests the MVP must pass before the build can expand.

The goal is not to test every future feature.

The goal is to prove the first script foundation is stable:

* state initializes safely
* commands inspect state without mutating it
* parser output becomes proposals, not direct canon
* CanonValidator blocks unsafe changes
* OperationLedger prevents duplicates
* inventory custody is respected
* actor presence is respected
* candidate abilities stay candidates
* quest rewards do not duplicate
* context stays compact
* protected cards mirror state only
* generated cards remain disabled

If these tests fail, the MVP is not stable enough for advanced systems.

⸻

1. Authority order

Testing authority order:

1. AIDRPG Test Spec v1
2. AIDRPG MVP Build Spec v1
3. AIDRPG Developer Spec v1.1 Correction Pass
4. AIDRPG Developer Spec v1
5. Chunk 33 Final Pre-Build Lockdown
6. Design Bible Chunks 1–32

If this Test Spec says a test must pass, the implementation is not complete until it passes.

If a feature is deferred by MVP Build Spec v1, do not test it as active gameplay in Test Spec v1.

⸻

2. Test philosophy

AIDRPG must be tested like a canon engine, not like a normal RPG damage calculator.

The most important question is not:

Did the story sound cool?

The important questions are:

Did state change only when it should?
Did the correct owner reducer commit the change?
Did duplicates get blocked?
Did uncertain information stay uncertain?
Did commands avoid mutating state?
Did Context and Story Cards avoid creating truth?

The MVP must prefer safe partial behavior over clever but unstable automation.

⸻

Every test case should use this structure.

Not every field is needed for every command-only test, but every test must clearly define:

* setup
* action
* expected result
* what must not happen

⸻

4. Required test harness assumptions

The test harness should be able to:

1. Initialize a fresh AIDRPG state.
2. Load a specific starting state.
3. Run a command input.
4. Run a normal player input.
5. Run an AI output through the Output hook.
6. Run the same AI output twice.
7. Inspect final state.
8. Inspect recent proposals.
9. Inspect validation results.
10. Inspect OperationLedger buckets.
11. Inspect audit output.
12. Inspect generated context packets.
13. Inspect protected card registry and dirty card queue.

If the platform does not support a formal test runner, these tests can be run manually through controlled stories and debug commands.

6. Gate 1 — State and command tests

Gate 1 proves the script can initialize state and show it without accidental mutation.

⸻

T001 — Fresh state initializes

Gate: 1
Purpose: Prove StateManager creates a complete MVP state.

Starting State:

state.aidrpg is missing

Input:

/help

Expected Proposals:

None.

Expected Validation:

None required.

Expected State Changes:

* state.aidrpg is created.
* version = '0.1.0-mvp'.
* all required root fields exist.
* generated cards are disabled.
* debug command output is safe.

Expected No-Changes:

* no inventory item created.
* no quest created.
* no actor created.
* no generated card created.

Expected Audit:

* initialization message or debug-safe notice.

Pass Conditions:

State exists and all required MVP fields are present.

Fail Conditions:

Missing root fields, generated cards enabled by default, or command creates gameplay state.

⸻

T002 — Missing fields repair safely

Gate: 1
Purpose: Prove migration/default repair does not erase valid state.

Starting State:

State exists but is missing:

operationLedger.rewardKeys
cards.dirtyCards
body.ep

State already has:

inventory.items = [{ name: 'Old Knife', owner: 'player', custody: 'player', access: 'held' }]

Input:

/status

Expected State Changes:

* missing fields are added with defaults.
* existing Old Knife remains unchanged.

Expected No-Changes:

* no inventory reset.
* no player reset.
* no quest reset.

Pass Conditions:

Defaults are repaired without deleting existing valid records.

Fail Conditions:

Any valid existing state is erased.

⸻

T003 — /help lists only MVP-supported systems

Gate: 1

Input:

/help

Expected Output Behavior:

Shows MVP commands:

* /help
* /sheet
* /status
* /inventory
* /abilities
* /quests
* /actors
* /location
* /time

* /cardaudit
* /contextaudit

Shows disabled/deferred systems:

* economy
* crafting
* investigation
* reputation/factions
* domain/labor
* absorption/evolution
* generated cards
* multi-protagonist

Expected No-Changes:

No gameplay state changes.

Pass Conditions:

Help text is accurate and does not claim future systems are active.

Fail Conditions:

Help text claims full economy/crafting/investigation/generated cards are implemented.

T005 — /debuglast works with no prior events

Gate: 1

Starting State:

7. Gate 2 — Pipeline and OperationLedger tests

Gate 2 proves proposals, validation, reducer routing, duplicate skipping, and audits work.

⸻

T006 — Output creates proposal, not direct state

Gate: 2

Starting State:

Default clean state.

AI Output:

You pick up the small pebble from the ground.

Expected Proposals:

One proposal:

eventType: inventory.item_pickup
completedAction: true
ownerReducer: InventoryReducer

Expected Validation:

If pebble was not visible/available, result should be pending or soft_fail unless the implementation allows simple pickup creation from clear output.

Expected State Changes:

Only after validation.

Expected Audit:

Shows proposal and validation result.

Pass Conditions:

No direct state mutation occurs before validation.

Fail Conditions:

Item appears in inventory without proposal/validation/audit.

⸻

T007 — Duplicate operation key skips repeated output

Gate: 2

Starting State:

Scene has available loot:

sceneItems = [{ id: 'scene_dagger_1', name: 'Rusty Dagger', access: 'available_loot' }]

AI Output:

You pick up the rusty dagger.

Run same output twice.

Expected First Run:

* proposal accepted
* dagger added to inventory
* operation key added to recentKeys

Expected Second Run:

* duplicate detected
* no second dagger
* audit records duplicate skip

Pass Conditions:

Exactly one dagger exists after both runs.

Fail Conditions:

Two daggers exist.

⸻

T008 — Unknown owner reducer rejected

Gate: 2

Starting State:

Default clean state.

Injected Proposal:

Expected Validation:

Expected State Changes:

None.

Pass Conditions:

Fail Conditions:

17. Pass/fail policy

17.1 Test pass

A test passes only if:

* expected state changes occur
* expected no-changes remain unchanged
* audit records important decisions
* duplicate prevention works when relevant
* no deferred system activates

17.2 Test fail

A test fails if:

* state changes without proposal/validation
* duplicate items/rewards/XP appear
* command output mutates gameplay state
* Story Card or Context text creates canon
* generated card appears while disabled
* actor presence/custody rules are violated
* rumors/claims become confirmed facts
* protected cards create state

17.3 Soft pass

A soft pass is allowed only when the exact state implementation differs but the safety rule holds.

Example:

For a visible ring, implementation may store it as sceneItems.visible or as a scene note, as long as it does not enter inventory.

Soft passes must be recorded.

17.4 Blocker fail

These failures block further development immediately:

* duplicate reward payment
* generated card creation while disabled
* command output parsed as story
* Story Card creates state
* context creates state
* item custody ignored
* absent companion acts
* state reset during migration

21. Final Test Spec doctrine

AIDRPG MVP must prove stability before ambition.

The first tests are not about making the game huge.

They are about proving the system does not lie to itself.

If the MVP can keep inventory, actors, quests, abilities, context, protected cards, and audits stable, then the advanced systems can be built safely later.

If the MVP cannot pass these tests, adding more systems will only multiply the failure points.

Therefore:

No advanced systems until Test Spec v1 passes.

That is the purpose of AIDRPG Test Spec v1.
