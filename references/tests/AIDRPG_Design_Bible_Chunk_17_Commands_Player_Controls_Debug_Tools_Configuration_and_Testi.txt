AIDRPG Design Bible — Chunk 17: Commands, Player Controls, Debug Tools, Configuration, and Testing Interface

1. Purpose of this chunk

Chunk 17 defines how the player interacts with AIDRPG directly.

Earlier chunks defined the game systems.

Chunk 17 defines the command layer that lets the player inspect, correct, test, configure, and control those systems.

This chunk answers:

What commands should exist?

Which commands are read-only?

Which commands can change state?

How should commands avoid being mistaken for story actions?

How should commands explain what the system believes?

How should commands support debugging without overwhelming normal play?

How should manual override work?

How should settings work?

How should /help stay honest?

How should the user test the system after each build?

The central rule is:

Commands are the player’s control panel, not the story itself.

A command can inspect or intentionally edit state, but it must not be confused with normal narrative text.

⸻

2. Core philosophy

AIDRPG is too large to operate blindly.

The player needs commands because the system tracks many things:

* player sheet
* body state
* stats
* resources
* abilities
* inventory
* equipment
* quests
* contracts
* cases
* reputation
* party
* actors
* places
* factions
* routes
* time
* travel
* weather
* domain projects
* cards
* audits
* quarantine
* migration
* cleanup

Without commands, the user cannot tell whether the system is working or silently drifting.

Commands should make the system trustworthy.

They should answer:

* What does AIDRPG think is true?
* Why does it think that?
* What changed last turn?
* What was rejected?
* What was skipped as duplicate?
* What is pending?
* What is active?
* What is archived?
* What is broken?
* What needs manual correction?

Commands should not become clutter.

Normal gameplay should not require constant command use.

The player should be able to play naturally, then use commands when they want clarity, correction, or debugging.

⸻

3. Command ownership boundaries

The command layer should not own gameplay truth.

Commands are interfaces into owner systems.

CommandRouter owns

* detecting command input
* parsing command names
* parsing command arguments
* routing to the correct command handler
* blocking command text from narrative parsing
* formatting command output
* command permission/safety level
* command help registry

Command handlers read or request changes from owners

Examples:

* /inventory reads InventoryReducer state
* /quests reads QuestReducer state
* /debuglast reads AuditSystem
* /cardaudit reads CardSync audit
* /sethp requests BodyReducer update through manual override
* /restoreitem requests InventoryReducer update through manual override
* /cleanup requests CleanupSystem action
* /releasecheck reads ReleaseCheck results

Reducers still own state

A command should not bypass reducers unless it is a carefully logged manual override path.

Even manual override should route through owner authority.

Example:

/sethp 50

This should not directly mutate random player fields.

It should call a body/player owner path that logs:

* old HP
* new HP
* source: manual override command
* dirty targets

5. Command authority levels

Commands need authority levels.

Read-only

These commands only display state.

Examples:

* /sheet
* /inventory
* /quests
* /actors
* /debuglast

They should never mutate gameplay state.

Safe action

These commands perform low-risk maintenance.

Examples:

* /cardaudit
* /stateaudit
* /releasecheck
* /cleanup preview

They may scan or report, but should not alter important canon unless explicitly run in fix mode.

Controlled maintenance

These commands can change memory surfaces or cleanup noise.

Examples:

* /cleanup run
* /cardfix
* /rebuildcards
* /neutralizecard

They should not create gameplay truth.

Manual override

These commands intentionally edit canon.

Examples:

* /additem
* /setlocation
* /sethp
* /markquest complete
* /restorequarantine

They must log the change.

Dangerous manual override

These commands can heavily alter canon.

Examples:

* deleting key items
* killing major actors
* completing major quests
* importing card text
* mass merging actors
* wiping cards
* resetting state

These should require very explicit command syntax later.

They should never happen from natural prose.

⸻

6. Command detection rules

Command input must be clearly separated from story input.

Recommended rule:

A command begins with /.

Examples:

* /sheet
* /inventory
* /debuglast
* /sethp 70

The command router should intercept slash commands before normal event parsing.

This prevents command text from becoming story action.

Example:

Input:

/additem rusted iron key

This should be treated as a command.

It should not be parsed as the player narratively finding a key.

Example:

Input:

“I type /additem sword into my journal.”

This is narrative text, not necessarily command execution, unless the system explicitly treats slash at beginning only as command.

Best rule:

Only messages that begin with / are commands.

⸻

7. Command output should not become canon

Command output is diagnostic/interface text.

It should not be parsed back as story events.

Example command output:

“Inventory: rusted iron key.”

This should not create another rusted iron key.

Example command output:

“Quest completed: Missing Ring.”

This should not re-trigger quest completion rewards.

Command outputs should be tagged internally as command output or diagnostic output.

Parser should ignore them as gameplay source.

This prevents command loops.

⸻

8. Command honesty rule

Commands must not lie.

If a feature is not implemented, the command should say so.

If a feature is partial, the command should say partial.

If a command is read-only, it should not imply it changed anything.

If a command failed, it should explain why.

If a command skipped something as duplicate, it should say so.

If a command cannot determine something, it should say unknown.

Bad command output:

“Everything is working.”

Good command output:

“Release check passed 42/47 tests. Five card audit tests are not implemented yet.”

Bad /help output:

“Use /crafting to manage full crafting.”

if crafting commands only display partial state.

Good /help output:

“/crafting currently displays active crafting projects. It does not yet start projects by command.”

Command honesty is one of the main safeguards against confusion during testing.

⸻

9. Display formatting philosophy

Command output should be clear and compact.

It should use:

* section headers
* short labels
* plain language
* warnings when relevant
* uncertainty labels
* no raw JSON unless debug mode asks
* no giant dumps in normal commands
* no internal IDs unless debug mode asks

Normal command output should be readable by a player.

Debug command output may be technical.

Example normal output:

/status

Current Status:

HP: 72 / 100
MP: 18 / 50
EP: 9 / 100

Warnings:

You are exhausted. Physical actions are risky.
Your left arm is bleeding. Weapon use may be impaired.

Example debug output:

/debuglast

Proposed events:

* body.damage: accepted
* body.injury.add: accepted
* progression.xp.gain: rejected, reason: trivial repeated action
* inventory.item.gain: hard-denied, reason: quoted text

This is useful without dumping entire state.

10. /help

/help is the command index.

It should show:

* available commands
* command category
* whether command is implemented
* whether command is read-only or mutating
* short usage
* warning for dangerous commands

/help should not claim unfinished systems are complete.

Recommended /help sections:

* Core Status
* Inventory & Equipment
* Progression & Abilities
* Quests & Objectives
* Investigation & Reputation
* Party & World
* Time & Travel
* Debug & Safety
* Manual Corrections
* Settings

Example:

Core Status:

* /sheet — show player sheet
* /status — show body state, injuries, conditions, resources
* /progression — show level, XP, stat training, domain ranks

Debug & Safety:

* /debuglast — show last turn’s parsed events and validation results
* /stateaudit — scan active state for contradictions
* /cardaudit — scan Story Cards for duplicates, stale facts, and unsafe triggers
* /releasecheck — show whether the script passes safety checks

Manual Corrections:

* /additem <name> — manually add an item through override
* /setlocation <place> — manually correct current location
* /restorequarantine <id> — restore quarantined data through override

If not implemented, label it.

11. /sheet

/sheet shows the main player sheet.

It should display:

* character name
* race/species
* age
* appearance summary
* level
* XP / XP-to-next
* total XP
* core stats
* HP / max HP
* MP / max MP
* EP / max EP
* major abilities
* major passives
* current build identity
* active major conditions
* active major injuries
* equipped weapon/armor summary

It should not display:

* every stat XP detail
* every domain rank
* every item
* every audit entry
* every hidden debug field

/sheet is the player-facing character overview.

12. /status

/status shows immediate body and resource state.

It should display:

* HP / max HP
* MP / max MP
* EP / max EP
* body state
* injuries
* conditions
* fatigue
* unconsciousness/death-boundary warning if relevant
* recovery blockers
* current effective penalties
* recent body/resource changes

Example:

Status:

HP: 41 / 105
MP: 8 / 62
EP: 0 / 116

Warnings:

* Exhausted: physical actions are high-risk.
* Left arm injury: two-handed weapon use is impaired.
* Low MP: spellcasting may fail or cause backlash.

Recovery:

A safe rest could restore EP.
The arm injury needs treatment or time.

15. /abilities

/abilities shows stable abilities and developing candidates.

It should display sections:

Stable abilities

* name
* category
* rank/stage
* cost
* effect
* limits
* reliability

Candidates

* name
* stage
* evidence summary
* last attempt
* failure pattern
* stabilization status

Passives / talents

* name
* scope
* limits
* trigger

The command must clearly separate stable abilities from candidates.

Bad output:

“Mana Slash — ability”

when it is only a candidate.

Good output:

“Mana Slash — candidate, unstable manifestation, not reliable yet.”

This prevents the player and AI from treating candidates as stable powers.

51. Manual correction commands

Manual correction commands should be explicit and logged.

/setname <name>

Sets player name.

/setrace <race/species>

Sets player race/species.

/setage <age>

Sets player age.

/setappearance <description>

Sets appearance summary.

/setlocation <place>

Corrects current location.

Should create or link place record if needed.

Should log manual override.

/sethp <value>

Sets HP within safe bounds unless override allows otherwise.

/setmp <value>

Sets MP.

/setep <value>

Sets EP.

/additem <name>

Adds item manually.

Should require item name hygiene.

Optional syntax later:

* /additem Rusted Iron Key type key
* /additem 5 healing potion
* /additem Royal Seal keyitem

/removeitem <name>

Removes or marks item lost manually.

Key item removal should require explicit force syntax later.

/setcustody <item> <holder>

Changes item custody.

Example:

/setcustody Iron Sword Mira

/equip <item>

Equips accessible item.

Should validate access.

/unequip <slot/item>

Unequips item.

/markquest <quest> <status>

Changes quest status.

Should be careful with rewards.

Manual completion should not automatically pay rewards unless command says so.

/mergeactor <actor A> <actor B>

Merges actors only through manual override.

Should preserve aliases and links.

/renameactor <actor> <new name>

Renames actor.

/mergeplace <place A> <place B>

Merges places.

/renameplace <place> <new name>

Renames place.

/restorequarantine <id>

Restores quarantined data through controlled conversion.

Manual commands are necessary, but they must be auditable.

⸻

52. Manual override logging

Every manual override should log:

* command text
* source: manual override
* user-facing target
* old value
* new value
* owner system
* validation result
* dirty targets
* operation key
* timestamp/turn

Example:

Manual override:

Command: /setlocation Old Chapel
Old location: Blackwood Road
New location: Old Chapel
Owner: PlaceReducer
Reason: user correction
Dirty: scene context, travel context, place cards
Operation: manual.location.set.old_chapel.turn_341

Manual correction should never be invisible.

⸻

53. Manual override limits

Manual override should not be too broad.

Avoid commands like:

* /fix everything
* /import all cards
* /delete all bad stuff
* /complete all quests
* /clean all state
* /trust card canon

unless they are carefully designed as preview-first tools.

Broad commands are dangerous.

Prefer narrow commands:

* restore this one item
* merge these two actors
* set this location
* neutralize this card
* rebuild protected cards
* mark this quest abandoned

The player should be able to correct errors without accidentally destroying state.

55. Settings safety

Settings must not corrupt existing state.

Changing progression speed should affect future rewards, not rewrite all past XP unless explicitly recalculated.

Changing card behavior should affect future CardSync and maybe cleanup, not delete cards silently.

Changing death mode should affect future death-boundary handling, not resurrect or kill automatically.

Changing magic level should affect future validation plausibility, not instantly create or remove abilities.

Settings are behavior knobs, not story events.

⸻

56. Command result validation outcomes

Commands can also use the five outcomes.

Accept

Command succeeded.

Example:

/sethp 70

HP set to 70.

Reject

Command understood but cannot execute.

Example:

/equip Iron Sword when sword is with Mira.

Pending

Command creates pending state.

Example:

/cleanup preview

No mutation yet, pending user run.

Soft_fail

Command partially succeeded.

Example:

/cleanup run neutralized 2 cards but skipped 1 due to identity conflict.

Hard_deny

Command is unsafe or malformed.

Example:

/additem the room

Rejected by item name hygiene.

Command output should say which outcome happened.

58. Command safety rules

58.1 Commands must be intercepted before narrative parsing

A slash command should not become story action.

58.2 Command output must not be parsed as gameplay

Displaying inventory should not add inventory.

58.3 Read-only commands must not mutate state

No hidden writes.

58.4 Manual override must be logged

No invisible corrections.

58.5 Dangerous changes require explicit syntax

No accidental deletion of key items or major actors.

58.6 Commands must respect owner boundaries

Commands request changes through proper owners.

58.7 Commands must validate names

No junk item/actor/place through commands.

58.8 Commands must not auto-grant rewards unless designed to

Manual quest completion should not duplicate rewards.

58.9 Commands must show uncertainty

Suspect is not culprit. Rumor is not proof.

58.10 Commands must be honest about implementation

No fake help entries.

58.11 Debug commands should not flood normal play

Technical details only when requested.

58.12 Commands should support testing

Every major system should have a display or audit command.

61. Final Chunk 17 doctrine

Commands are the player’s control panel.

Commands must be clearly separated from story text.

Read-only commands must never mutate state.

Manual override commands must be explicit, validated, and logged.

Command output must never become gameplay canon.

Commands must respect owner boundaries.

Commands must show current truth, uncertainty, blockers, and warnings.

Commands must support debugging without flooding normal play.

/help must be honest about what exists and what is partial.

/debuglast must explain the last turn.

/stateaudit, /cardaudit, and /releasecheck must make system health visible.

/context and /cards must reveal what the AI is being told and what cards are being managed.

Manual correction commands are necessary, but they must be narrow and auditable.

Settings can tune behavior, but they should not rewrite history.

The goal is to let the player trust, inspect, and correct AIDRPG without turning commands into another source of canon corruption.
