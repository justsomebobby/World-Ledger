AIDRPG MVP Build Spec v1

0. Document status

Document name: AIDRPG MVP Build Spec v1
Purpose: Define the first exact script target for AIDRPG.
Status: Build target specification, not code.
Applies after: AIDRPG Developer Spec v1 and Developer Spec v1.1 Correction Pass.
Next document after this: AIDRPG Test Spec v1.

This document answers:

* what the first MVP actually builds
* what stays disabled
* what modules must exist
* what state must exist
* what each AI Dungeon hook should do
* what commands must work
* what event types are allowed
* what validation must block
* what protected cards must update
* what tests must pass before expansion

This document is intentionally narrower than the full Design Bible.

The goal of MVP v1 is not to finish AIDRPG.

The goal is to build the stable canon pipeline that later systems can safely use.

⸻

1. Authority order

Implementation authority order is:

1. AIDRPG MVP Build Spec v1
2. AIDRPG Developer Spec v1.1 Correction Pass

⸻

2. MVP build target

2.1 MVP target name

AIDRPG Core MVP v0.1

2.2 MVP purpose

AIDRPG Core MVP v0.1 must prove that the system can:

1. Initialize stable state.
2. Display state through commands.
3. Detect simple proposed events.
4. Validate those events.
5. Commit accepted changes through owner reducers.
6. Prevent duplicate changes.
7. Enforce item custody and actor presence.
8. Track candidate versus stable abilities.
9. Track simple quest states and promised versus paid rewards.
10. Build compact context packets.
11. Maintain protected summary cards.
12. Provide audits for debugging.

2.3 MVP success definition

The MVP succeeds when:

* commands work
* state does not corrupt itself
* repeated output does not duplicate rewards/items/XP
* visible loot does not become inventory until taken
* inaccessible items cannot be used
* absent companions cannot act
* candidate abilities do not become stable automatically
* active quests can track simple progress
* promised rewards are not paid rewards
* protected cards mirror state only
* generated cards stay disabled
* context stays compact
* audits explain important decisions

These must not be implemented in MVP v0.1 as active systems.

WeatherReducer: disabled

3.2 Allowed inert placeholders

The root state may include flags for disabled systems.

Example:

flags: {
  economyEnabled: false,
  craftingEnabled: false,
  investigationEnabled: false,
  reputationEnabled: false,
  domainEnabled: false,
  absorptionEnabled: false,
  generatedCardsEnabled: false,
  multiProtagonistEnabled: false
}

These flags must not run logic.

3.3 Do not create half-systems

Do not build partial economy, partial crafting, partial investigation, or partial absorption in MVP.

If a feature is deferred, it may only appear as:

* a text note
* an inert flag
* a future hook placeholder
* a command message saying it is not implemented yet

It must not mutate gameplay state.

5. Build modes for MVP

MVP supports mode flags, but only Balanced Mode is fully expected.

5.1 Default mode

mode: 'balanced'

5.2 Supported flags

flags: {
  narrativeMode: false,
  balancedMode: true,
  strictMode: false,
  debugMode: false,
  safeMode: false,
  generatedCardsEnabled: false
}

5.3 Narrative Mode in MVP

Narrative Mode may soften validation messages but must still enforce:

* no duplicate rewards
* no inaccessible item use
* no absent companion actions
* no generated card creation
* no command output parsing as story

5.4 Strict Mode in MVP

Strict Mode may increase audit detail and stricter rejection, but it must not enable deferred systems.

5.5 Debug Mode in MVP

Debug Mode allows more detailed command output from:

* /debuglast
* /cardaudit
* /contextaudit

Debug Mode should not spam normal story output.

5.6 Safe Mode in MVP

Safe Mode:

* keeps generated cards disabled
* limits parsing to commands and core safety checks
* keeps protected cards updating if safe
* prevents cleanup from deleting important records

6. AI Dungeon hook responsibilities

AIDRPG is assumed to run inside AI Dungeon script surfaces.

The implementation may be one script bundle, but behavior should be separated by hook responsibility.

⸻

6.1 Library / shared code

Library/shared code should define:

* constants
* schema defaults
* helper functions
* ID/key helpers
* hashing helpers
* module objects
* reducer registry
* command registry
* validation rules

Library/shared code should not mutate gameplay state by itself.

⸻

6.2 Input hook

Input hook responsibilities:

1. Initialize state if missing.
2. Detect commands.
3. If command found, route to CommandRouter.
4. Mark command output so it is not parsed as story.
5. For non-command input, optionally create intent proposals.
6. Do not complete player attempts from input alone.

Input hook must not:

* add items from player claims alone
* kill enemies from player claims alone
* complete quests from player claims alone
* create stable abilities from player claims alone
* move long-distance locations from player claims alone

Example:

Player input:

I try to grab the gem.

Allowed result:

intent proposal: item_take_attempt
completedAction: false

Not allowed:

gem added to inventory

⸻

6.3 Context hook

Context hook responsibilities:

1. Initialize state if missing.
2. Build compact context packets.
3. Prioritize corrections.
4. Inject current scene/location if useful.
5. Inject item custody warnings if relevant.
6. Inject actor presence warnings if relevant.
7. Inject active quest and ability limit reminders if relevant.
8. Avoid full state dumps.

Context hook must not:

* mutate gameplay state
* create items
* create actors
* create quests
* create cards
* parse its own injected text as canon

⸻

6.4 Output hook

Output hook responsibilities:

1. Initialize state if missing.
2. Ignore command output if suppression flag is active.
3. Scan AI output for simple completed events.
4. Build proposals.
5. Validate proposals.
6. Commit accepted proposals through owner reducers.
7. Record operation keys.
8. Mark dirty targets.
9. Update protected cards if allowed and dirty.
10. Write audit summary.

Output hook must not:

* scan Story Card text as event source
* scan Context text as event source
* create generated cards in MVP
* allow parser output to bypass CanonValidator
* allow non-owner reducers to mutate state

⸻

12. MVP validation rules

12.1 Universal validation rules

Every proposal must pass:

1. source allowed
2. event type allowed
3. owner reducer exists
4. operation key not duplicate
5. confidence high enough
6. not negated
7. not hypothetical
8. not dream/vision unless explicitly allowed
9. does not contradict protected state
10. required actor/item/ability/place exists or can be safely created

12.2 Confidence thresholds

0.00–0.24 = ignore/hard deny if dangerous
0.25–0.44 = pending/reject
0.45–0.64 = validate carefully, usually pending or soft_fail
0.65–0.84 = accept if no contradiction
0.85–1.00 = accept if owner and ledger checks pass

Clear AI output starts around 0.75 before validation.

12.3 Attempt rule

Input attempts do not complete actions.

Examples:

I try to pick up the gem.

Result:

intent only, no inventory add

12.4 Completion rule

Actions complete only when AI output, command, or manual override confirms completion.

Example:

You pick up the gem.

May become:

inventory.item_pickup

if access and duplicate checks pass.

12.5 Quoted speech rule

Quoted speech creates claims, not facts.

Example:

Mara says, "Lord Veyr killed him."

MVP result:

actor.memory_add truthStatus = claimed

No confirmed guilt.

12.6 Rumor rule

Rumor creates rumored quest/actor note only if useful.

No confirmed fact.

12.7 Story Card rule

Story Card text cannot create proposals.

12.8 Context rule

Context text cannot create proposals.

12.9 Command output rule

Command output cannot create proposals.

13. MVP resolver rules

13.1 Resolver result shape

ResolverResult {
  matchedId?: string,
  confidence: number,
  ambiguous: boolean,
  candidates: string[],
  reason: string
}

13.2 Generic names

Generic names only match if there is one clear current-scene candidate.

Generic examples:

* sword
* key
* ring
* guard
* wolf
* road
* shop
* potion

13.3 Similar item rule

If both iron key and iron keyring exist, “iron key” must not select keyring.

13.4 Negated selection rule

If text says:

Take the iron key, not the keyring.

Then keyring must be excluded.

13.5 Actor relation rule

“Mara’s sister” does not resolve to Mara.

13.6 Place substring rule

“Old Chapel Road” does not resolve to “Old Chapel” unless context explicitly says the chapel itself.

13.7 Custody rule

If an item is inaccessible but clearly referenced, resolve it for correction, not use.

Example:

Sword with Mara:

Player says: I draw my sword.
Resolver: matches sword.
Validator: rejects use due to npc_custody.

14. MVP reducer behavior

14.1 BodyReducer MVP

Must support:

* resource cost
* simple damage
* simple healing
* injury add/remove
* condition add/remove
* fatigue change

Must not support:

* final combat matrix
* species-specific body compatibility table
* advanced disease/poison engine
* permanent injury math

14.2 InventoryReducer MVP

Must support:

* visible scene item
* available loot
* pickup
* drop
* equip
* unequip
* custody transfer
* mark lost/sold/destroyed/consumed
* simple currency gain/spend

Must enforce:

* visible is not inventory
* available_loot is not inventory
* npc_custody is not usable
* sold/destroyed/consumed/lost cannot be used

14.3 AbilityReducer MVP

Must support:

* ability record creation

25. Final MVP doctrine

MVP v0.1 is not the whole game system.

MVP v0.1 is the foundation.

It must prove:

* state can exist safely
* commands can inspect it
* output can become proposals
* proposals can be validated
* reducers can commit only their owned truth
* duplicates are blocked
* context can stay compact
* protected cards can mirror state
* obvious AI Dungeon drift can be corrected

The MVP should be boring in the right way:

stable, inspectable, hard to corrupt, and easy to test.

Once that is true, the advanced systems from the Design Bible can be added without repeating the old cycle of patching one feature and breaking three others.
