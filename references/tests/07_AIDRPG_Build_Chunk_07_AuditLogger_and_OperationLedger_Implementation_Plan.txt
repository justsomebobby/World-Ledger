AIDRPG Build Chunk 7 — AuditLogger and OperationLedger Implementation Plan

0. Document status

Document name: AIDRPG Build Chunk 7 — AuditLogger and OperationLedger Implementation Plan
Build target: AIDRPG Core MVP v0.1
Purpose: Define the exact AuditLogger and OperationLedger behavior before their code is generated.
Status: Practical build document.
Follows: Build Chunk 6 — Runtime Hook Contract Implementation Plan.
This document does not contain final script code.

This chunk is useful because two old failure categories keep returning unless they are handled at the foundation level:

1. The script cannot explain what it did or rejected.
2. The script repeats the same operation and duplicates rewards, items, XP, cards, time, or startup imports.

AuditLogger makes the system inspectable.

OperationLedger makes repeated effects idempotent.

Together, they make the script safer to debug, test, and expand.

⸻

1. Audit and ledger doctrine

The doctrine is:

Every important decision should be explainable.
Every one-time effect should have a key.
Every repeated effect should be skipped safely.
Audits explain; they do not mutate gameplay.
Ledger keys dedupe; they do not create gameplay.

AuditLogger is not a hidden gameplay system.

OperationLedger is not a reducer.

They are support systems that make the real pipeline trustworthy.

⸻

2. Why this chunk matters before coding

Without AuditLogger:

* rejected events become mysterious
* command output cannot explain state
* releasecheck cannot prove safety
* parser false positives are hard to detect
* card failures are invisible
* migration/quarantine issues are hidden
* fail-soft errors vanish

Without OperationLedger:

* repeated output duplicates item pickup
* repeated reward output pays twice
* repeated XP output awards twice
* repeated startup import duplicates items/abilities
* repeated card sync creates/updates too often
* repeated time skip ages or advances time twice
* repeated cleanup/audit actions bloat state

Build Chunk 7 prevents those problems from being improvised later.

4. AuditLogger responsibilities

AuditLogger owns:

* debug messages
* runtime warnings surfaced to audits
* proposal summaries
* validation summaries
* duplicate skip messages
* card audit lines
* context audit lines
* cleanup audit lines
* migration audit lines
* releasecheck result storage
* last-turn summary
* capped array handling for audit buckets

AuditLogger does not own:

* gameplay mutation
* validation decisions
* reducer commits
* Story Card writes
* Context packet generation
* parser decisions
* OperationLedger keys, except displaying or logging key use

⸻

5. OperationLedger responsibilities

OperationLedger owns:

* permanent operation keys
* recent operation keys
* reward operation keys
* card operation keys
* source-use keys
* duplicate key detection
* safe key insertion
* recent-key compaction
* duplicate skip audit hooks

OperationLedger does not own:

* applying gameplay effects
* deciding whether a proposal is valid
* rendering commands
* parsing text
* cleaning gameplay state
* writing Story Cards

8. Audit bucket schema recap

AuditLogger writes to the audits bucket locked in Build Chunk 3.

audits: {
  lastTurnSummary,
  recentProposals,
  recentValidationResults,
  debugMessages,
  runtimeWarnings,
  cardAudit,
  contextAudit,
  cleanupAudit,
  migrationAudit,
  releaseCheck
}

Runtime-specific details may also live in:

runtime.runtimeWarnings
runtime.runtimeErrors
runtime.hookTrace

AuditLogger may help cap both audit and runtime arrays.

⸻

9. OperationLedger schema recap

OperationLedger writes to:

operationLedger: {
  permanentKeys,
  recentKeys,
  rewardKeys,
  cardKeys,
  sourceUseKeys,
  maxRecentKeys,
  ledgerWarnings
}

These arrays are not interchangeable.

Each one has a different lifespan and purpose.

10. Audit record style

Audit records should be compact, readable, and capped.

10.1 Good audit lines

Rejected item pickup: "jeweled cup" was hypothetical, not acquired.
Duplicate skipped: quest.reward.clear_mill_wolves.old_bren already used.
Command suppression: /inventory output was not scanned as story.
CardSync skipped generated card: generated cards are disabled in MVP.

10.2 Bad audit lines

bad event
ValidationResult[7].flags.negated true bool reason no write
undefined

Audit lines should be useful to a human testing the script.

12. Audit caps

AuditLogger must cap all audit arrays.

Recommended MVP caps:

recentProposals max = 50
recentValidationResults max = 50
debugMessages max = 50
runtimeWarnings max = 25
cardAudit max = 50
contextAudit max = 50
cleanupAudit max = 50
migrationAudit max = 50
runtime.runtimeWarnings max = 25
runtime.runtimeErrors max = 20
runtime.hookTrace max = 30

12.1 Cap behavior

When capped:

* keep most recent records
* preserve critical recent failures
* avoid expensive deep sorting
* do not crash if bucket malformed
* repair malformed audit bucket safely if needed

12.2 Cap must not touch

AuditLogger must not cap or delete:

operationLedger.permanentKeys
operationLedger.rewardKeys
operationLedger.cardKeys
startup.startupOperationKeys
migration.migrationOperationKeys
active inventory
active quests
important actors
stable abilities

⸻

13. AuditLogger safe append rules

Every append function must:

1. ensure the target bucket exists or fail softly
2. convert message/record to safe format
3. add turn number if relevant
4. cap the target bucket
5. never throw uncaught errors
6. never mutate gameplay state

If audit writing itself fails, the script should fail softly or skip the audit rather than corrupt gameplay.

⸻

14. Audit categories

14.1 Debug messages

Used for general developer-readable notes.

Examples:

* StateManager repaired missing inventory bucket
* CommandRouter routed /questlog to /quests
* Parser shell inactive in v0.1

14.2 Runtime warnings

Used for hook/runtime safety issues.

Examples:

* duplicate output replay detected
* command output suppression triggered
* hook reentry blocked
* non-string hook input converted safely

14.3 Proposal audits

Used later for parser hits and proposed events.

Examples:

* proposed item pickup
* proposed quest reward payment
* proposed actor presence update

In early v0.1, proposal audit may report shell inactive.

14.4 Validation audits

Used later for accepted/rejected/pending proposals.

Examples:

* rejected because hypothetical
* rejected because item in NPC custody
* accepted because output confirmed actual handoff

14.5 Duplicate audits

Used whenever a ledger or hash skip blocks repeated effects.

Examples:

* duplicate output hash skip
* duplicate quest reward key
* duplicate startup import key

14.6 Card audit

Used for CardSync and Story Card safety.

Examples:

* generated cards disabled
* protected card registry dry-run planned
* duplicate Player Sheet detected
* card API unavailable

14.7 Context audit

Used for ContextBuilderLite.

Examples:

* selected current location packet
* skipped low-priority quest packet due to budget
* read-only guard active

14.8 Cleanup audit

Used for CleanupManagerLite.

Examples:

* capped audit logs
* deduped dirty targets
* skipped important actor

14.9 Migration audit

Used for StateManager/migration/quarantine.

Examples:

* old root detected
* old card prose not imported
* malformed field quarantined

⸻

15. Operation key doctrine

Every one-time or repeat-sensitive effect needs an operation key.

A key should answer:

What happened?
To what target?
From what source/context?
Should it ever happen again?

Key examples:

startup.import.player.name
startup.import.item.iron_sword
item.pickup.rusty_dagger.scene_12
quest.reward.clear_mill_wolves.old_bren.15_gold
xp.quest.clear_mill_wolves.complete
card.create.protected.player_sheet
card.update.protected.player_sheet.hash_abcd
cleanup.audit.compact.turn_50
time.advance.five_years.event_77

⸻

16. Operation key normalization

Operation keys must be safe and stable.

16.1 Normalize by

* converting to lowercase
* trimming whitespace
* replacing spaces with underscores
* removing unsafe punctuation
* preserving meaningful colon/dot separators if chosen
* collapsing repeated separators
* limiting length

16.2 Forbidden key contents

Keys should not contain:

* raw full output text
* huge descriptions
* unstable timestamps only
* player-facing prose paragraphs
* unbounded random values

16.3 Length recommendation

Recommended maximum:

operation key max length = 160 characters

If longer, hash the unstable/detail part.

⸻

17. Ledger bucket purposes

17.1 permanentKeys

For operations that should never repeat in this save.

Examples:

* startup imports
* unique quest completions
* unique irreversible transformations
* schema migration steps
* major one-time discoveries if needed later

17.2 recentKeys

For recent operations that should be blocked for a short window but can expire.

Examples:

* repeated minor damage line
* repeated visible item detection
* repeated scene note
* repeated low-risk parser output

17.3 rewardKeys

For rewards/payments/XP that must not duplicate.

Examples:

* quest reward paid
* bounty paid
* explicit XP award
* level milestone reward

Reward keys should be durable.

Do not cap rewardKeys like recentKeys.

17.4 cardKeys

For Story Card create/update/restore/neutralization operations.

Examples:

* protected card created
* protected card updated to render hash
* duplicate card warning
* generated card suppressed/tombstoned later

17.5 sourceUseKeys

For tracking source-specific actions.

Examples:

* output hash consumed
* command output suppressed
* setup source imported
* migration source processed

⸻

18. Ledger add behavior

18.1 Basic add flow

1. Normalize key.
2. Validate non-empty key.
3. Check target bucket exists.
4. If key already exists, return duplicate result.
5. Add key to target bucket.
6. Cap bucket if bucket is recentKeys.
7. Audit add/duplicate if needed.
8. Return result.

18.2 Add result format

LedgerResult {
  ok: boolean,
  duplicate: boolean,
  key: string,
  bucket: string,
  reason: string
}

18.3 Duplicate behavior

If duplicate:

* do not add another copy
* return duplicate result
* optionally audit duplicate skip
* reducer/caller must not apply effect again

Ledger duplicate detection must be easy for callers to use.

⸻

19. Ledger check behavior

19.1 hasAny

Checks all relevant buckets.

Use when the caller does not care where the key lives.

19.2 Specific checks

Use specific checks when bucket matters.

Examples:

* hasReward for quest reward payment
* hasCard for card update/create
* hasPermanent for startup import

19.3 Read-only checks

Checking the ledger must not mutate the ledger.

Only add or tryAdd mutates.

⸻

20. Recent key compaction

Only recentKeys should be capped by count.

Default cap:

maxRecentKeys = 250

When over cap:

* keep newest keys
* drop oldest recent keys
* do not drop permanent/reward/card keys
* audit only if useful

22. Duplicate skip audit format

When a duplicate is detected, audit should be readable.

Format:

Duplicate skipped: <key> — <reason>.

Examples:

Duplicate skipped: item.pickup.rusty_dagger.scene_12 — item pickup already applied.
Duplicate skipped: quest.reward.clear_mill_wolves.old_bren.15_gold — reward already paid.
Duplicate skipped: startup.import.item.iron_sword — starting item already imported.

⸻

23. AuditLogger and OperationLedger interaction

OperationLedger may call AuditLogger for duplicate skip messages.

AuditLogger must not call OperationLedger for normal audit appends.

Reason:

Avoid circular dependency where audit writes require ledger keys and ledger keys require audit writes.

Recommended dependency direction:

OperationLedger -> AuditLogger optional
AuditLogger -> no OperationLedger dependency

If circular dependency risk exists, OperationLedger can return duplicate result and caller logs through AuditLogger.

⸻

24. Ledger and reducers later

Reducers should use OperationLedger in this pattern:

1. Compute operation key.
2. Check ledger duplicate.
3. If duplicate, skip effect and audit.
4. If not duplicate, apply reducer effect.
5. Add key to ledger.
6. Mark dirty targets.
7. Audit success.

Potential stricter future pattern:

1. Check key.
2. Apply effect.
3. Add key.

If adding key after effect fails, audit critical warning.

For MVP, code should keep the pattern simple and safe.

⸻

25. Ledger and startup import

Startup import must use ledger or startup operation keys.

Example:

Setup says:

Starting equipment: iron sword.

Operation key:

startup.import.item.iron_sword

If setup import runs again:

* key already exists
* do not add second sword
* audit duplicate startup import skip

⸻

26. Ledger and command output

Commands usually do not need gameplay operation keys because they do not mutate gameplay.

But command suppression may use sourceUseKeys or runtime hashes.

Example:

source.command.inventory.hash_abc.suppressed

Do not create item/reward keys from command output.

⸻

27. Ledger and Context

Context should not create gameplay operation keys.

Context may use packet hashes later for audit spam prevention.

Context packet hashes are not gameplay operation keys.

Do not use context text to add inventory/reward/XP keys.

⸻

28. Ledger and Story Cards

Story Card operations must use cardKeys.

Story Card text must not create gameplay keys.

Examples:

Allowed:

card.update.protected.inventory_equipment.hash_abc

Forbidden:

item.add.crown_of_dawn.from_story_card_text

unless a future explicit manual import path validates it.

⸻

29. Ledger and releasecheck

ReleaseCheck must verify:

* operationLedger exists
* permanentKeys exists
* recentKeys exists
* rewardKeys exists
* cardKeys exists
* sourceUseKeys exists
* maxRecentKeys exists
* recent key cap is sane

ReleaseCheck must fail if:

* rewardKeys missing
* cardKeys missing while CardSync enabled
* recentKeys unbounded
* duplicate protection unavailable for output replay/rewards

ReleaseCheck should warn if:

* no duplicate skip audit path exists
* sourceUseKeys not used yet in early shell

⸻

30. Audit and command renderers

Command renderers use audit/ledger data.

30.1 /debuglast

Reads:

* lastTurnSummary
* recentProposals
* recentValidationResults
* runtime warnings/errors
* duplicate skip audit lines

30.2 /ledger

Reads:

* counts for permanent/recent/reward/card/sourceUse keys
* recent duplicate skip lines if available
* ledger warnings

30.3 /stateaudit

Reads:

* audit sizes
* runtime errors
* migration warnings
* cleanup warnings

30.4 /releasecheck

Reads audit and ledger health to determine readiness.

Command renderers must never mutate gameplay while showing audits/keys.

⸻

31. Audit and privacy/length safety

Audit should avoid storing full long player/AI text.

Use previews.

Recommended preview max:

160 characters

Full text can be avoided unless absolutely needed.

Do not store giant outputs in audit buckets.

Do not store full Story Card contents in audit logs.

Use hashes/previews instead.

⸻

32. Early v0.1 behavior

In early Core MVP v0.1, full parser/reducer systems may still be inactive.

AuditLogger and OperationLedger are still useful.

They should support:

* command routing audit
* command suppression audit
* duplicate output hash audit
* state repair audit
* releasecheck result storage
* card dry-run audit
* context shell audit
* ledger shell display

They do not need to wait for full gameplay automation.

⸻

33. AuditLogger implementation sequence

When coding begins, implement AuditLogger in this order:

1. safe line/preview helper
2. generic append helper
3. cap helper
4. debug/warn appenders
5. runtime warning/error appenders
6. card/context/cleanup/migration appenders
7. proposal/validation appenders
8. releasecheck storage
9. turn summary storage
10. capAll

Do not start with complex UI formatting.

Command renderers handle display.

⸻

34. OperationLedger implementation sequence

When coding begins, implement OperationLedger in this order:

1. normalizeKey
2. makeKey helper
3. ensure ledger bucket helper
4. bucket-specific has functions
5. bucket-specific add functions
6. tryAdd result object
7. recent key compaction
8. duplicate audit helper
9. summary helper for /ledger

Do not implement gameplay effects inside OperationLedger.

43. Final Build Chunk 7 doctrine

AuditLogger and OperationLedger are not flashy, but they protect the project from two of the most dangerous failure types: invisible behavior and repeated behavior.

Final rule:

If the script does something important, audit it.
If the script might do something twice, key it.
If a duplicate appears, skip it safely.
If an audit grows too large, cap it safely.
If a key protects a permanent outcome, never compact it away as recent noise.

With AuditLogger and OperationLedger planned, the next safe step is to plan CommandRouter and command renderers.
