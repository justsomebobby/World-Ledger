1. Purpose of this chunk

Chunk 32 is the final design-planning chunk.

This chunk explains how all previous systems connect into one stable AIDRPG system.

Earlier chunks defined:

* player identity
* race/species
* level scaling
* XP and progression
* stats and resources
* enemy tiers
* combat math
* abilities and passives
* absorption and anime-style growth
* crafting
* economy
* quests
* investigation
* actors, factions, reputation, and social memory

Chunk 32 answers:

How does the whole system actually work together?

How does AIDRPG decide what is real?

How does it update state safely?

How does it prevent duplicated Story Cards?

How does it prevent junk names?

How does it prevent card triggers from firing constantly?

How does it manage time, travel, weather, recovery, locations, routes, and scene state?

How does it decide what information to inject into AI Dungeon context?

How does it decide what belongs in protected summary cards versus generated cards?

How does it keep freeform AI Dungeon play flexible without losing truth?

The central rule is:

AIDRPG is a canon-state manager for AI Dungeon.

It should not try to replace AI Dungeon’s narration.

It should read the story, validate what happened, update structured state, and inject only the most relevant confirmed context back into the story.

3. The full gameplay loop

AIDRPG should work through a repeated loop.

Step 1 — Player acts

The player writes a freeform action.

Examples:

* “I slash at the wolf.”
* “I ask Mara what she saw.”
* “I inspect the body.”
* “I try to craft a dagger from scrap.”
* “I absorb the slime core.”
* “I travel to Greyford.”
* “I pay the workers.”
* “I use Mana Slash.”

Player input usually creates an attempt, not automatic success.

Step 2 — AI Dungeon narrates

AI Dungeon responds.

It may confirm success, partial success, failure, new facts, or consequences.

Step 3 — AIDRPG reads the output

The script scans the new narration for possible state changes.

Examples:

* damage occurred
* item was gained
* quest progressed
* clue was found
* actor spoke
* reward was paid
* time passed
* location changed
* ability was used
* injury happened
* enemy died
* worker project advanced

Step 4 — AIDRPG proposes updates

The system creates proposed updates.

Examples:

* HP -12%
* wolf injured
* clue discovered
* Mara relationship +trust
* 2 silver spent
* quest objective complete
* Mana Slash evidence gained

Step 5 — CanonValidator checks them

CanonValidator asks:

Is this possible?

Is the source valid?

Is it duplicated?

Does it contradict protected state?

Does the relevant system own this update?

Is it confirmed, rumored, claimed, or only suspected?

Does this require custody, proof, cost, time, or presence?

Step 6 — Owner reducers commit valid changes

Each owner system commits only its own state.

Examples:

* BodyReducer updates HP/injuries.
* InventoryReducer updates items.
* QuestReducer updates objectives.
* InvestigationReducer updates clues.
* ActorReducer updates relationships.
* EconomyReducer updates currency.
* ProgressionReducer updates XP.
* CardSync updates cards.

Step 7 — OperationLedger prevents duplicates

Every committed change gets an operation key.

If the same event is processed again, it is skipped.

Step 8 — Dirty targets are marked

Any changed area is marked dirty.

Examples:

* Player Sheet dirty
* Inventory card dirty
* Quest Log dirty
* Actor card dirty
* Place memory dirty
* Context dirty

Step 9 — ContextBuilder prepares next context

ContextBuilder injects only relevant confirmed facts into AI Dungeon.

Step 10 — Story Cards update safely

Protected summary cards and generated cards update only from structured state.

Cards mirror truth.

Cards do not create truth.

4. State layers

AIDRPG should use several state layers.

4.1 Protected core state

This is the most trusted state.

It includes:

* player sheet
* stats
* resources
* level
* XP
* abilities
* body state
* inventory
* equipment
* active quests
* active cases
* current location
* active companions
* active conditions
* time
* important world flags

Protected core state should be difficult for normal narration to overwrite.

4.2 Structured system state

This includes detailed records for:

* actors
* factions
* places
* buildings
* routes
* cases
* quests
* contracts
* crafting projects
* domain projects
* economy records
* operation ledger
* card registry

4.3 Generated card state

Generated cards are long-term memory surfaces shown to AI Dungeon.

They should be concise mirrors of structured state.

4.4 Context injection state

This is temporary text inserted for the next AI response.

It should contain only what matters right now.

4.5 Archive state

Archives store old but important history.

Examples:

* completed quests
* solved cases
* dead actors
* old locations
* finished contracts
* resolved domain projects

Archives should not flood current context.

5. CanonValidator

CanonValidator is the main safeguard layer.

Every proposed update should pass through it.

CanonValidator checks:

* source validity
* ownership
* duplicate operation
* truth status
* contradiction
* scale
* resource cost
* actor presence
* item custody
* location consistency
* time consistency
* body compatibility
* ability validity
* quest proof
* evidence strength
* card safety
* name hygiene
* anti-farm
* player settings
* death boundary
* manual overrides

CanonValidator should not make the story boring.

It should allow freeform play, but it should prevent unsupported truth from entering state.

6. Canon validation outcomes

Every proposal should resolve into one of these outcomes.

Outcome	Meaning
Accept	update is valid and committed
Reject	update is unsupported and not committed
Pending	possible but unconfirmed
Soft_fail	partial result or consequence
Hard_deny	invalid, unsafe, duplicate, or canon-breaking
Merge	same as existing record; merge/update
Archive	old state becomes inactive
Supersede	new confirmed state replaces older uncertain state
Flag	needs debug/audit warning

Examples:

AI says:

“The wolf dies.”

If wolf had already been killed:

* duplicate / reject.

AI says:

“Mara blocks the arrow.”

If Mara is absent:

* reject or flag.

AI says:

“You find blue wax.”

If scene supports searching victim’s sleeve:

* accept clue.

AI says:

“Lord Veyr is definitely the murderer.”

If evidence is insufficient:

* reject as confirmed fact, maybe record theory.

* Actor Cards
* Place Cards
* Ability Cards
* Item Cards
* Quest Cards
* Contract Cards
* Domain Cards
* Faction Cards
* Context Injection

Dirty targets prevent unnecessary rewriting.

Only update what changed.

Example:

If Mana Slash rank changes:

* Abilities Summary dirty
* Mana Slash card dirty if generated
* Player Sheet maybe not dirty unless ability summary included there
* Quest Log not dirty

If player moves to Greyford:

* Current Location dirty
* Context dirty
* Route/travel state dirty
* Inventory not dirty

9. Reducer ownership doctrine

Each system owns its own truth.

No reducer should directly mutate another reducer’s state.

Instead, it should propose an event.

Examples:

CombatResolver can propose:

* wolf injured
* player takes damage
* XP candidate
* quest target defeated

But:

* BodyReducer commits player damage
* Enemy/Scale system commits enemy state
* ProgressionReducer commits XP
* QuestReducer commits objective progress

CraftingReducer can propose item output.

But InventoryReducer creates the item.

QuestReducer can propose reward.

But EconomyReducer adds money and InventoryReducer adds reward item.

This prevents systems from fighting each other.

18. Travel time estimates

Default travel estimates can be approximate.

Travel Mode	Rough Distance / Day
walking careful	10–15 miles/day
walking normal road	15–25 miles/day
forced march	25–35 miles/day with fatigue
mounted normal	25–40 miles/day
mounted fast	40–60 miles/day with rest needs
wagon/cart	10–25 miles/day
rough terrain	reduce by 25–75%
mountain/swamp/forest	reduce heavily
flying	depends on creature/ability
teleport	ability-specific

The system does not need perfect realism.

It needs consistency.

If a route normally takes two days, the player should not arrive in one minute unless magic or scene compression supports it.

22. Time scale categories

AIDRPG should classify time jumps.

Time Jump	Examples
moment	quick action, glance
combat beat	attack/defense exchange
minute	brief search, short talk
scene	tavern scene, interrogation
hour	crafting, study, travel segment
day	sleep, long travel, workday
week	project progress, long recovery
month	domain development, long training
season	major domain/world changes

Different systems respond to different scales.

Combat uses beats.

Crafting uses minutes/hours/days.

Recovery uses rest/ticks.

Domain projects use days/weeks.

Reputation spread may use days/weeks/months.

25. Injury recovery

Injuries recover by severity.

Injury Severity	Natural Recovery
scratch	minutes/hours
minor	hours/day
moderate	days
serious	days/weeks
severe	weeks/months or magic
critical	special care/magic
permanent	prosthetic, magic, adaptation, or lasting scar

Recovery should not be instant.

Healing magic can speed it, but must respect ability tier.

A minor healing potion should not regrow a severed limb.

Regeneration passives follow their own limits.

30. ContextBuilder

ContextBuilder decides what AI Dungeon needs to know right now.

It should use priority and relevance.

Context should include:

* current player status if relevant
* current location
* active scene state
* present actors
* active combat state
* current quest objective
* relevant case facts
* item custody warnings
* ability limits if used
* resource warnings
* location hazards
* time/deadline warnings
* companion presence/absence
* key social/faction context
* immediate unresolved contradictions
* card correction notes

Context should not include:

* every stat
* every card
* every old quest
* every old clue
* every actor
* every inventory item
* every archived case
* every domain detail
* every known ability
* every rumor
* every transaction
* every old combat event

The strongest Context rule:

Inject only the smallest amount of truth needed to keep the next response consistent.

⸻

31. Context priority order

When space is limited, use this priority:

1. Safety/canon correction
2. Current location and scene
3. Current player body/resource danger
4. Active combat/enemy state
5. Present actors and companion presence
6. Current action-relevant equipment/custody
7. Current quest objective/deadline
8. Current case confirmed facts/leads
9. Active hazards
10. Relevant ability limits/costs
11. Relevant reputation/faction constraints
12. Active domain/project blocker
13. Recent important event
14. Archived memory only if directly relevant

This prevents bloated context.

32. Context correction notes

Sometimes AI Dungeon drifts.

ContextBuilder should inject correction notes.

Examples:

Mara is not present; she is at Greyford smithy with the player’s sword.
Shadow Step is only a candidate and should not work as reliable teleport yet.
Lord Veyr is suspected but not proven guilty.
The player has only 2 silver in their purse; their domain treasury is not accessible here.
The slime core was already consumed and cannot be absorbed again.
Frostmaw is a named spirit wolf; ordinary wolf facts should not replace its established traits.

Correction notes should be direct and concise.

50. Contradiction handling

Contradictions should not be ignored.

When a new fact conflicts with existing state:

1. Identify conflict.
2. Determine source reliability.
3. Check if new fact is confirmed or only claimed.
4. Check if old fact is confirmed.
5. Decide outcome:
    * reject new fact
    * mark new fact as claim
    * update old fact
    * create contradiction record
    * flag audit
    * ask no question unless absolutely necessary
6. ContextBuilder may inject correction.

Examples:

Existing:

Mara is at smithy.

New AI output:

Mara attacks beside player in forest.

Outcome:

* reject or flag unless travel occurred.

Existing:

Sword is broken.

New output:

Player draws pristine sword.

Outcome:

* reject pristine state; maybe player draws broken sword if they have it.

Existing:

Lord Veyr only suspected.

New output:

Everyone knows he is guilty.

Outcome:

* reject public certainty unless proof/spread occurred.

63. Final system safeguards list

The final system requires these safeguards.

Truth safeguards

* Rumors are not facts.
* Claims are not facts.
* Theories are not facts.
* Cards are not facts.
* Commands are not narration.
* Player input is attempt, not automatic success.
* AI output is validated, not blindly trusted.

Duplication safeguards

* OperationLedger dedupes all state changes.
* Card registry prevents duplicate cards.
* Canonical keys prevent duplicate actors/items/quests.
* Alias merging handles spelling drift.
* Source caps prevent repeated absorption.
* Quest rewards pay once.
* XP rewards pay once.
* Items cannot be sold twice.

Naming safeguards

* Reject junk names.
* Reject generic triggers.
* Use specific canonical names.
* Avoid common words like street, wolf, guard, skill, item, quest.
* Use aliases carefully.

Scale safeguards

* Level/tier comparison controls combat.
* Ability effect tier controls cost.
* XP scales by challenge.
* Overleveled farming gives little/no reward.
* Underleveled impossible victories are rejected/softened.
* Bosses need defeat conditions.

Resource safeguards

* MP/EP/HP costs apply.
* Low resources weaken/block actions.
* Overexertion has consequences.
* Healing has limits.
* Recovery needs time/rest.
* Crafting needs materials/tools/time.
* Economy needs funds/availability.
* Labor needs workers/wages/materials.

Presence/custody safeguards

* Actors must be present to act.
* Companions cannot help while absent.
* Items must be accessible.
* Custody matters.
* Quest items must be tracked.
* Currency in distant treasury is not purse money.

Card safeguards

* Generated cards only for important stable entities.
* Protected cards summarize core state.
* Cards mirror state only.
* Card updates come from dirty targets.
* Trigger safety is mandatory.
* Card archive/removal prevents clutter.

Context safeguards

* Inject only relevant current facts.
* Do not dump all memory.
* Do not spoil hidden truth.
* Prioritize corrections.
* Distinguish confirmed/suspected/rumored.
* Keep context compact.

68. Final doctrine

AIDRPG is a freeform RPG continuity system for AI Dungeon.

It should let the player do almost anything.

But it should not let anything become canon without support.

It should reward creativity, danger, risk, cleverness, investigation, crafting, social play, travel, combat, training, and domain management.

It should support anime-style growth, but not infinite free power.

It should support Story Cards, but not let Story Cards create false truth.

It should support generated memory, but not flood the game with junk cards.

It should support long campaigns, but not inject every old detail into context.

It should support mysteries, but not turn rumors into facts.

It should support companions, but not let absent companions act.

It should support economy and labor, but not free money or instant buildings.

It should support combat, but not impossible kills or absurd deaths.

It should support player power fantasy, but with scale, cost, risk, and consequences.

The full final product is:

A structured, auditable, reducer-owned, card-synchronized, context-aware canon engine that keeps AI Dungeon’s freeform story coherent across character growth, combat, abilities, inventory, quests, investigations, relationships, economy, domains, time, travel, weather, locations, and world memory.

That is the end goal.
