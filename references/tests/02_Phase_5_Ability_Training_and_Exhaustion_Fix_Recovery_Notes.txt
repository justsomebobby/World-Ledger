Bottom line

Based on the latest normal/full tester report, v1.3.6 is final-clean by the main tester: 2,686 / 2,686 passed, no current-stage blockers. That means there is no ordinary gameplay patch required from that pass.

But the uploaded Player-Breaker Findings Report is a different kind of test. It is adversarial and specifically looks for ways a player or model wording can trick the script into committing false canon. That report found a real root class: the script still sometimes treats mentioned/failed/quoted/dreamed events as confirmed truth. The report identifies false canonical state changes as the main remaining risk: denied/revoked inventory, noncanonical ability mentions, quoted/dreamed time skips, and repeated ability over-amplification.  

So my honest read is:

v1.3.6 is release-ready for normal AI Dungeon playtesting.
v1.3.6 is not mathematically bulletproof against adversarial player-breaker wording.

If we patch anything, it should be one final root validator patch, not more exact-scenario patches.

⸻

What still may need changing

1. Inventory needs clause-level canon validation

This is the biggest remaining possible issue.

The player-breaker report shows that inventory can still be granted from text like:

* “You never take the black gate key.”
* “You pick up the idea of a brass key…”
* “You pick up the obsidian key, but then it dissolves as an illusion…”
* “You are told to take the sun badge in a dream, then wake empty-handed.”
* “Mira refuses to give you the jeweled crown, but she hands you the red healing potion.”

The root problem is not a missing phrase. It is that the inventory system still sometimes sees a positive acquisition verb, then commits the item before fully checking whether that specific clause denies, abstracts, revokes, dreams, quotes, or invalidates it. The findings report specifically says the script is not consistently doing “deny/revoke wins locally” before item state is committed.  

Needed change

Add a shared clause-level inventory validator before final item grant.

For every item candidate, the script should classify the local clause as:

* confirmed acquisition,
* denied acquisition,
* revoked acquisition,
* abstract/metaphorical mention,
* quoted instruction,
* dream/vision/non-real acquisition,
* unknown.

Only confirmed acquisition should grant.

Must block

* never take
* fail to take
* cannot take
* not an actual item
* idea of / concept of / title of
* pretend to take
* dream / vision / wake empty-handed
* dissolves / illusion / have nothing
* refuses to give X
* told to take X, but no actual handoff
* quoted “take X” without narration confirming transfer

Must still allow

* “Mira hands you the red healing potion.”
* “After searching again, you recover the black gate key.”
* “You receive the rusted iron key.”
* “She places the key in your hand, and you accept it.”

This is very aligned with the AIDRPG goal: detect what happened, decide whether it counts as a real event, then safely apply and save it.  

⸻

2. Ability canon needs the same clause-level confirmation gate

The uploaded player-breaker report shows ability names becoming canonical when they are only mentioned in failed, quoted, pretend, manual/title, or “do not know” wording. Examples include:

* “The scroll title says ‘You learned Crimson Lotus Fang,’ but you only read the title and learn nothing.”
* “You attempt Void Lantern Veil; the veil collapses…”
* “Mira says, ‘Use Hollow Star Palm now,’ but you do not know that technique.”
* “You pretend to use Azure Dragon Step while telling a joke.”  

v1.3.5 and v1.3.6 fixed many ability-denial cases, but this report indicates the broader root still may exist: ability name mentioned in output can still sometimes be treated as ability confirmed by output.

Needed change

Ability confirmation should require one of these:

* ability successfully manifests,
* ability is learned,
* ability is trained,
* ability is retained,
* ability is demonstrated successfully,
* ability is confirmed as usable.

A player input like “I channel Moonlit Thunder Step” should create at most a pending candidate, not a real ability. The Output must confirm it.

Must block

* scroll title says “you learned X”
* quoted “use X”
* pretend to use X
* do not know X
* learn nothing
* no usable technique remains
* collapses
* fails
* fizzles
* cannot manifest
* no X answers your call

Must still allow

* “Moonlit Thunder Step becomes a controlled afterimage dash.”
* “You successfully channel Ember Ward.”
* “After practice, Crimson Lotus Fang becomes stable.”
* “You learn Azure Dragon Step from the manual after hours of training.”

This directly supports the AIDRPG skill identity goal: named skills matter, but they should become real through effort, confirmation, training, inheritance, absorption, ritual, or teaching — not because a name appeared in a failed/quoted sentence.  

⸻

3. Repeated ability use should not over-amplify state/context

The player-breaker report found a repeated Ember Ward case where repeated use appeared to create excessive canonical mentions or inflated use tracking. It suspects multiple layers are processing the same ability mention: input intent, output processing, compatibility confirmation, context priority logic, and specialization.  

Needed change

Use one normalized operation key for ability-use mutation:

turn + hook + abilityKey + eventKind + outputHash

Then all ability mutation paths should call the same apply-once guard.

Intended behavior

If the player uses Ember Ward four times, the system can remember that it was used repeatedly, but it should not create seven context entries, seven records, or overcount the use as if several systems each independently confirmed the same event.

This is the same safeguard pattern the old systems relied on: retry detection and duplicate suppression are core stability controls, not optional polish.  

⸻

4. Time-skip aging needs a nonliteral guard

The player-breaker report found age changes from non-real time phrases:

* “You say, ‘Twenty years pass,’ while practicing narration. No time passes.”
* “In a dream, twenty years pass, but you wake as the same age.”

Both changed age from 19 to 39 in that adversarial run.  

Needed change

Before applying any year-based age change, the script should block nonliteral contexts:

* quoted speech
* dream
* vision
* story/practice narration
* pretend
* “no time passes”
* “same age”
* “wake as the same age”
* “not actually”

Must still allow

* “Twenty years pass in exile.”
* “After twenty years, you finally wake.”
* “Two years pass while the city rebuilds.”

This should be a small guard, not a rewrite of the time system.

⸻

5. Do not add old TASIS race/passive/world chunks right now

Several uploaded roadmaps are clearly old TASIS repair plans, not the current AIDRPG v1.3.6 source-of-truth. They are useful for principles, but not as “must add now” tasks.

For example, the old roadmaps talk about race/passive rebuilds, schema completion, passive reward architecture, and TAS-style hook repair. Those were meant for earlier TASIS builds and partial-merge states, not this current AIDRPG release candidate. The older handoff explicitly warns against creating competing persistence paths and says systems should have one authoritative path.  

So for v1.3.6, I would not add:

* a new race engine,
* new passive spell architecture,
* new combat engine,
* new card-generation system,
* new world simulation layer,
* new wholesale hook structure,
* old TASIS CH-number systems.

That would be dangerous because the current tester-clean build is already stable.

⸻

6. Keep the AI Dungeon runtime discipline unchanged

Even though the new memory limit is 16 MB, the important operational limit is still 2 seconds per hook, and scripts still run through Input, Context, and Output lifecycle hooks. The scripting reference says scripts are sandboxed with 16 MB and 2 seconds, and recommends using state for persistence, storyCards for structured model-visible info, guarding duplicate story card creation, and managing context size with info.maxChars / info.memoryLength.  

So any final patch should stay cheap:

* current output text only,
* small pre/post snapshots,
* no full story-card scan in Input,
* no full-world scan,
* no big context rebuild loops,
* no broad regex sweeps over all history.

Final “remaining work” list

If we decide to patch beyond v1.3.6, this is the full list I would alter:

1. Inventory clause validator
    * classify each item candidate locally;
    * deny/revoke/abstract/dream/quote blocks that specific item;
    * valid later clauses can still grant a different item.
2. Ability clause validator
    * quoted/manual/pretend/failed ability mentions do not commit canon;

    * one apply-once guard for repeated ability use;
    * context dedupes ability lines by normalized ability key.
4. Nonliteral time-skip guard
    * quotes/dreams/pretend/no-time-passes do not age the player.

    * rerun official v1.4 sectioned suites,
    * rerun old true-stress cross-check,
    * rerun the adversarial/player-breaker inventory, ability, and time sections,
    * run one live AI Dungeon playtest.

That is it. I would not add new features.
