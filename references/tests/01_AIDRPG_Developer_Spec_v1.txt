AIDRPG Developer Spec v1

0. Document status

Document name: AIDRPG Developer Spec v1
Purpose: Convert the repaired AIDRPG Design Bible into a buildable technical blueprint.
Status: First official developer-facing specification.
This is not code yet.
This is the source document that the first script build should follow.

This document defines:

* what the first version of the script should build
* what should not be built yet
* which modules exist
* which module owns which truth
* what state should look like
* how AI Dungeon narration becomes validated state
* how duplicate prevention works
* how Context and Story Cards should be handled
* which commands should exist first
* how the build should be phased
* what tests must pass before expansion

The main goal is to stop guessing during implementation.

⸻

1. Implementation goal

AIDRPG is a freeform RPG continuity engine for AI Dungeon.

It should not replace AI Dungeon’s narration. It should stabilize it.

The script should:

1. Read player input and AI output.
2. Detect possible gameplay events.
3. Convert those events into structured proposals.
4. Validate proposals against canon state.
5. Commit only valid changes through owner reducers.
6. Prevent duplicate changes.
7. Update protected summaries and Story Cards safely.
8. Inject compact relevant context back into AI Dungeon.
9. Provide commands and audits so the user can inspect what happened.

The first real build should prioritize truth safety, state consistency, and debuggability over feature quantity.

⸻

2. Non-goals for v1

Developer Spec v1 does not attempt to fully implement the entire 33-chunk design bible immediately.

The first build should not try to fully implement:

* full economy simulation
* full domain/base/labor system
* full crafting system
* full investigation system
* full generated Story Card automation
* full actor/faction/reputation network
* full anime-style absorption/evolution
* full multi-protagonist support
* full marketplace pricing
* full legal/crime system
* full weather simulation
* full route map generation
* full complex boss phase engine
* full automated ability balancing for every possible power

These systems are planned, but they should be staged.

The first build should create the stable foundation those systems will later use.

4. Build modes

AIDRPG should support modes through feature flags.

4.1 Narrative Mode

Purpose:

* lightest gameplay enforcement
* minimal visible numbers
* many soft-fail outcomes
* fewer hard rejections
* best for story-first players

Behavior:

* validates major contradictions
* avoids duplicate items/rewards
* tracks basic state
* combat is mostly narrative severity
* economy/crafting simplified

4.2 Balanced RPG Mode

Purpose:

* default intended mode
* resources, XP, inventory, quests, abilities, and combat matter
* validation is active but not oppressive

Behavior:

* HP/MP/EP tracked
* costs matter
* item custody matters
* quest rewards dedupe
* ability candidates/stable abilities enforced
* soft-fail preferred over hard denial

4.3 Strict Simulation Mode

Purpose:

* stronger system enforcement
* more exact costs, time, injury, crafting, travel, economy

Behavior:

* more frequent audits
* harder validation
* stricter resource and time checks
* more explicit failure states

4.4 Debug Mode

Purpose:

* development and testing

Behavior:

* shows proposals
* shows validation decisions
* shows operation keys
* shows dirty targets
* shows card/context changes
* exposes hidden technical state only when safe

4.5 Safe Mode

Purpose:

* emergency stability mode

Behavior:

* disables generated card creation
* limits card updates
* limits event parsing to core systems
* prevents cleanup from deleting important records
* preserves core protected summaries
* prioritizes commands and audits

Safe Mode should be available if the script begins drifting or over-writing memory.

5. Module map

5.1 StateManager

Owns loading, saving, initializing, migrating, and validating global script state.

Responsibilities:

* create default state
* ensure missing fields are initialized
* run schema migration
* provide read/write access to reducers
* maintain version number
* prevent direct raw mutation from non-owner modules

Does not:

* decide gameplay truth
* parse AI output
* create cards directly

⸻

5.2 EventScanner

Reads player input and AI output for possible events.

Responsibilities:

* identify candidate event phrases
* detect command input
* detect likely item, actor, ability, quest, location, time, damage, reward, and resource events
* mark source hook: input, output, context, command, manual
* avoid scanning card text as event source

Does not:

* commit state
* decide truth
* award XP
* create cards

EventScanner only finds possible events.

⸻

5.3 ProposalBuilder

Converts raw scanner hits into structured event proposals.

Responsibilities:

* normalize event type
* attach source text hash
* attach candidate actor/item/place IDs
* attach confidence score
* attach truth status
* select proposed owner reducer
* create preliminary operation key

Does not:

* commit the proposal
* assume success
* bypass CanonValidator

⸻

5.4 CanonValidator

The central truth gate.

Responsibilities:

* validate proposals
* reject contradictions
* soften unsupported outcomes
* classify facts as confirmed, claimed, rumored, suspected, pending, false, or disputed
* check ownership
* check duplicate ledger
* check actor presence
* check item custody/access
* check ability status
* check resource costs
* check quest proof
* check scale plausibility
* check name hygiene
* assign validation outcome

Does not:

* directly mutate state except through validation record
* create cards
* write context

CanonValidator is the most important module.

⸻

5.5 ReducerRegistry

Routes accepted proposals to the correct owner reducer.

Responsibilities:

* map event types to reducers
* ensure only owner reducer commits final state
* reject direct non-owner writes

⸻

5.14 ContextBuilder

Builds compact context for AI Dungeon.

Responsibilities:

* choose relevant packets
* prioritize correction notes
* enforce budget
* avoid full memory dumps
* distinguish confirmed/suspected/rumored
* inject only relevant current truth

Does not:

* create canon
* update cards
* mutate gameplay state

⸻

5.15 CardSyncLite

First version of card synchronization.

Responsibilities:

* maintain protected summary cards
* update only dirty protected summaries
* optionally create extremely limited generated cards in later stages
* enforce trigger safety
* prevent duplicate card creation
* avoid full card scans every hook

Does not:

* create gameplay truth
* parse cards as events
* create many cards per turn

⸻

5.16 CommandRouter

Handles player commands.

Responsibilities:

* detect commands
* route inspection commands
* route debug commands
* route manual override commands if enabled
* prevent command output from being parsed as story narration

⸻

5.17 AuditLogger

Records recent validation decisions.

Responsibilities:

* last proposals
* accepted changes
* rejected changes
* reasons
* operation keys
* dirty targets
* card/context actions

Must support /debuglast.

⸻

5.18 CleanupManagerLite

Performs conservative cleanup.

Responsibilities:

* remove stale temporary parser candidates
* compact old audit logs
* limit recent operation list size
* prevent dirty queue growth
* never delete active quests, core state, important actors, important items, or protected summaries

Cleanup must never invent gameplay truth.

6. Canon event proposal schema

Every detected possible event must become a proposal with the same shape.

Recommended schema:

EventProposal {
  proposalId: string,
  turnId: string,
  sourceHook: 'input' | 'output' | 'command' | 'manual' | 'migration',
  sourceTextHash: string,
  rawText: string,
  eventType: string,
  subtype?: string,
  actorId?: string,
  targetId?: string,
  itemId?: string,
  placeId?: string,
  questId?: string,
  abilityId?: string,
  ownerReducer: string,
  confidence: number,
  truthStatus: string,
  evidenceType: string,
  proposedChanges: object,
  operationKey: string,
  validation: null | ValidationResult,
  dirtyTargets: string[],
  notes: string[]
}

6.1 Required fields

Every proposal must have:

* proposalId
* turnId
* sourceHook
* sourceTextHash
* rawText
* eventType
* ownerReducer
* confidence
* truthStatus
* evidenceType
* proposedChanges
* operationKey

6.2 Source hooks

Allowed source hooks:

* input: player input
* output: AI Dungeon output
* command: explicit command
* manual: explicit manual override
* migration: state migration

Disallowed as canon event sources:

* Story Card text
* Context text
* debug text
* examples
* old archive summaries

These can inform context, but they cannot create new gameplay events by themselves.

⸻

7. Validation result schema

Every proposal receives a validation result.

ValidationResult {
  outcome: 'accept' | 'reject' | 'pending' | 'soft_fail' | 'hard_deny' | 'merge' | 'archive' | 'supersede' | 'flag',
  reason: string,
  confidenceAfterValidation: number,
  ownerReducer: string,
  committed: boolean,
  operationKey: string,
  duplicate: boolean,
  dirtyTargets: string[],
  auditSummary: string
}

7.1 Outcome meanings

accept

The update is valid and should be committed.

reject

The update is unsupported and should not be committed.

pending

The update may be true but needs more evidence.

soft_fail

The player/story gets a partial result, weaker result, or complication.

hard_deny

The update is invalid, duplicate, unsafe, or canon-breaking.

merge

The proposal matches an existing record and should update/merge with it.

archive

The record should move from active state to archive.

supersede

A stronger confirmed fact replaces older uncertain state.

flag

The event needs audit/context warning but not necessarily state change.

⸻

8. Truth status rules

Every long-term fact should have a truth status.

Allowed statuses:

* confirmed
* observed
* claimed
* rumored
* suspected
* supported
* disputed
* contradicted
* false
* unknown
* candidate
* stable
* sealed
* unavailable

8.1 Global truth rules

* Rumor is not fact.
* Claim is not fact.
* Theory is not fact.
* Candidate ability is not stable ability.
* Promised reward is not paid reward.
* Available loot is not owned inventory.
* Present actor is not the same as known actor elsewhere.
* Story Card text is not evidence.
* Context text is not evidence.

10. OperationLedger rules

OperationLedger prevents repeated output from applying the same change more than once.

10.1 Operation key format

Recommended format:

category.action.target.source.turnOrEvent

Examples:

item.add.iron_dagger.craft_project_002.turn_91
currency.reward.clear_mill_wolves.old_bren.turn_150
xp.quest.clear_mill_wolves.complete.turn_145
ability.evidence.mana_slash.success.turn_44
combat.damage.player.wolf_bite.turn_33
quest.objective.clear_mill_wolves.wolf_count_3.turn_82
actor.relationship.mara.trust.saved_brother.turn_201
card.update.player_sheet.turn_202

10.2 Permanent operation keys

Permanent keys should be kept for:

* quest rewards
* unique item rewards
* major card creation
* major quest completion
* major case solution later
* contract payment later
* source absorption later
* boss defeat
* title grants
* domain project completion later

10.3 Rolling operation keys

Rolling recent keys can be used for:

* ordinary damage
* minor resource costs
* minor XP
* repeated output line protection
* context/card update dedupe
* minor actor mentions

Rolling keys should be compacted after enough turns.

10.4 Duplicate behavior

If duplicate detected:

* do not commit again
* write audit entry
* do not mark unnecessary dirty targets
* do not create another card
* do not pay reward again

11. Parser confidence model

Every proposal needs a confidence score from 0.0 to 1.0.

11.1 Confidence bands

Score	Meaning
0.00–0.19	ignore or hard deny
0.20–0.39	weak, likely pending or reject
0.40–0.59	possible, needs validation
0.60–0.79	likely, validate normally
0.80–1.00	strong, accept if no contradiction

11.2 Confidence increases when

* AI output explicitly confirms event
* event uses known actor/item/place/ability
* event matches player input attempt
* event occurs in current scene
* event has clear subject and object
* event has direct consequence language
* event is not contradicted by state
* event source is command/manual override

11.3 Confidence decreases when

* phrase is hypothetical
* phrase is negated
* phrase is dream/vision/metaphor
* phrase is quoted dialogue
* phrase is rumor or claim
* actor is absent
* item is inaccessible
* location mismatch exists
* event uses generic name
* event contradicts protected state
* event comes from card/context/debug/example text
* similar-name ambiguity exists

11.4 Negation examples

Do not add item:

* “I do not take the sword.”
* “You almost pick up the coin.”
* “The key is not in your hand.”
* “Mara says she never saw the dagger.”

Do not mark death:

* “The wolf looks dead, but then rises.”
* “You think he might be dead.”
* “He nearly dies.”

Do not mark quest complete:

* “You are close to finishing the quest.”
* “Bren says this might be enough.”

12. Resolver rules

Resolvers match names from text to state records.

Resolvers needed:

* ActorResolver
* ItemResolver
* PlaceResolver
* AbilityResolver
* QuestResolver
* CardResolver

12.1 Resolver scoring factors

* exact canonical key match
* exact display name match
* alias match
* current scene presence
* custody/access relevance
* quest/case link
* recent mention
* type compatibility
* spelling similarity
* ambiguity count
* generic-name penalty

12.2 Ambiguity rule

If two records plausibly match, do not guess blindly.

Preferred outcomes:

* choose current-scene accessible object if confidence is high
* mark pending if ambiguous
* create audit warning
* ask user only if absolutely necessary and command cannot resolve

12.3 Similar-name examples

* “iron key” is not automatically “iron keyring.”
* “Mara” is not automatically “Mara’s sister.”
* “Old Chapel Road” is not automatically “Old Chapel.”
* “Captain Mora” and “Captain Morra” may be alias if same role/location/history.
* “Mana Slash” and “Blue Crescent” may be alias or variant depending effect/cost/source.

13. Context budget rules

ContextBuilder must enforce a budget.

The exact character budget depends on AI Dungeon limits, but the system should behave as if context is scarce.

13.1 Context packet order

1. Critical correction packet
2. Current scene/location packet
3. Player danger/status packet
4. Active combat packet
5. Present actors/companions packet
6. Item custody/equipment warning packet
7. Current quest/deadline packet
8. Current ability limit packet
9. Current case/lead packet later
10. Reputation/faction warning packet later
11. Domain/economy blocker packet later
12. Relevant archive callback packet only if needed

13.2 MVP context packets

MVP should support:

* correction packet
* scene/location packet
* status danger packet
* actor presence packet
* inventory custody packet
* active quest packet
* ability limit packet

13.3 Context must not include

* full inventory every turn
* all stats every turn
* every quest every turn
* every actor every turn
* archived cases unless relevant
* all ability descriptions
* old transaction history
* old combat logs
* uncertain facts without labels

13.4 Context correction examples

Mara is not present; she is at Greyford smithy with the player’s sword.
Shadow Step is only a candidate and should not work as reliable teleport yet.
The iron sword is in Mara’s custody for repair and cannot be used right now.
Lord Veyr is suspected, not proven guilty.

14. Story Card rules

14.1 Core doctrine

Story Cards mirror state.

Story Cards do not create state.

14.2 Protected cards

Protected cards are the first supported card type.

Required protected cards:

* AIDRPG Player Sheet
* AIDRPG Body Status
* AIDRPG Abilities
* AIDRPG Inventory/Equipment
* AIDRPG Quest Log
* AIDRPG Social Memory
* AIDRPG Current Location

Optional later:

* AIDRPG Case Log
* AIDRPG Domain Summary
* AIDRPG Economy Summary

14.3 Generated cards

Generated cards should be disabled or extremely limited during early MVP.

When enabled, generated cards require:

* stable entity
* importance threshold
* clean canonical name
* safe trigger
* no duplicate canonical key
* confirmed facts only or clearly labeled uncertainty
* concise text
* dirty target marker

14.4 Generated card write limits

Initial limits:

* maximum 1 generated card creation per turn
* maximum 2 generated card updates per turn
* no full Story Card scan every hook
* no generated cards from low-confidence events
* no generated cards for candidates unless explicitly allowed later
* no generated cards for random background NPCs/items/places

14.5 Bad triggers

Reject triggers like:

* street
* road
* wolf
* guard
* sword
* magic
* skill
* quest
* item
* shop
* town
* forest
* companion
* enemy

14.6 Good triggers

Accept triggers like:

* Mara
* Captain Mora
* Frostmaw
* Mana Slash
* Slimebound Shield
* Old Mill wolves
* Blackwood Road
* Greyford Caravan Escort
* Dalen murder case

19. Testing gates

No phase should be considered complete until its gate passes.

Gate 1 — State and command gate

Must pass:

* state initializes without error
* missing fields repair safely
* commands display current state
* /help only lists supported commands
* command output does not mutate story state unless intended

Gate 2 — OperationLedger gate

Must pass:

* repeated item gain applies once
* repeated XP reward applies once
* repeated quest reward applies once
* repeated damage event does not double apply if duplicate

Gate 3 — Inventory custody gate

Must pass:

* seen item is not owned item
* available loot is not inventory
* item with NPC cannot be used
* sold item cannot be sold again
* equipped item updates correctly

Gate 4 — Ability candidate gate

Must pass:

* candidate ability is not stable
* stable ability can be used if cost/access valid
* sealed ability cannot be used
* unknown ability does not become mastered instantly

Gate 5 — Actor presence gate

Must pass:

* absent companion cannot act
* present actor can speak/act
* duplicate actor name merges or flags
* random NPC does not become generated card

Gate 6 — Quest reward gate

Must pass:

* promised reward is not paid reward
* objective progress dedupes
* quest completion and reward payment are separate
* reward pays once

Gate 7 — Context gate

Must pass:

* context includes current location
* context includes critical correction
* context excludes unrelated archives
* context stays under budget
* context labels suspected/rumored facts

Gate 8 — Protected card gate

Must pass:

* protected cards update from state
* protected cards do not create state
* dirty cards update only when needed
* card audit explains changes

Gate 9 — Generated card beta gate

Must pass before generated cards are allowed:

* generic triggers rejected
* duplicate card keys rejected
* max write limits enforced
* generated card creation disabled in Safe Mode
* random guard/shopkeeper/item not carded

20. Required first regression tests

These are the first tests the script must eventually pass.

Test A — available loot is not inventory

Input/output says:

“The goblin drops a rusty dagger.”

Expected:

* scene item or available loot created
* not in inventory until player takes it

Test B — item pickup applies once

Output says:

“You pick up the rusty dagger.”

Repeated output processed twice.

Expected:

* dagger added once
* operation duplicate skipped

Test C — sword at smith cannot be used

State:

Sword custody = Mara.

Player says:

“I draw my sword.”

Expected:

* blocked or corrected
* no sword attack

Test D — absent companion cannot act

State:

Mara elsewhere.

AI says:

“Mara blocks the arrow.”

Expected:

* rejected/flagged
* no damage prevention from Mara

Test E — candidate ability not reliable

State:

Shadow Step candidate only.

AI says:

“You teleport perfectly behind him.”

Expected:

* reject or soft-fail
* candidate evidence possible
* no stable teleport

Test F — quest reward once

* +15 gold once

* duplicate skipped

25. Development risk rules

The build must avoid these common failures.

25.1 Do not build everything at once

Large feature jumps will cause regression.

25.2 Do not enable generated cards early

Generated CardSync should wait until protected cards, canonical keys, and duplicate prevention pass tests.

25.3 Do not parse Story Cards as events

Cards are memory, not action.

25.4 Do not let commands become story

Command outputs are inspection/mutation tools only.

25.5 Do not trust AI output blindly

AI output proposes events; CanonValidator decides commits.

25.6 Do not over-inject context

Context must stay compact.

25.7 Do not make every NPC permanent

Use importance filters.

25.8 Do not make every clue/card/item/quest generated

Most details stay in protected summaries or internal state.

25.9 Do not hide failures from audit

Every rejected or softened event should be explainable.

25.10 Do not make validation joyless

Prefer soft-fail or partial success over hard denial when possible.

⸻

26. User-facing behavior doctrine

AIDRPG should feel helpful, not hostile.

When something is unsupported, the system should usually produce a softer truth.

Examples:

Unsupported instant boss kill

Do not simply say:

“Rejected.”

Prefer state outcome:

* boss is scratched
* boss is staggered
* boss avoids fatal blow
* player discovers resistance
* attack creates opening

Unsupported unknown ability

Do not simply say:

“You cannot.”

Prefer state outcome:

* ability attempt recorded
* candidate evidence gained
* weak spark/failure/backlash occurs

Unsupported item gain

Do not put item in inventory.

Prefer:

* item is visible nearby
* item is available loot
* player must take it

Unsupported rumor

Do not confirm it.

Prefer:

* rumor recorded as lead
* actor card remains unconfirmed

Hard denial should be reserved for state corruption, duplication, impossible contradictions, or unsafe invalid records.

27. Developer Spec v1 final doctrine

AIDRPG should be built as a staged canon engine.

The first priority is not feature count.

The first priority is stable truth flow:

Input/Output
→ EventScanner
→ ProposalBuilder
→ CanonValidator
→ Owner Reducer
→ OperationLedger
→ Dirty Targets
→ CardSyncLite
→ ContextBuilder
→ AuditLogger

Every system must obey ownership.

Every update must be validated.

Every committed update must be deduped.

Every card must mirror state only.

Every context packet must be relevant and compact.

Every important decision must be auditable.

The first script build should prove that foundation before adding advanced gameplay systems.

Once this Developer Spec is corrected into v1.1, the next document should be:

AIDRPG MVP Build Spec v1

That document will be shorter and will say exactly what to code first.
